# Introduction

Imagine your AI platform has access to multiple models.

```text
GPT-5

Claude

Gemini

Llama
```

A user sends a request.

```text
Translate this sentence into French.
```

Should you always use GPT-5?

Probably not.

A smaller, faster, and cheaper model can perform this task just as well.

Now another request arrives.

```text
Review this 200-page legal contract and identify risks.
```

This task requires a much more capable reasoning model.

Instead of sending every request to the same model,

Enterprise AI systems intelligently decide which model should handle each request.

This process is called **Model Routing**.

---

# What is Model Routing?

Model Routing is the process of automatically selecting the most appropriate LLM for each incoming request.

Instead of manually choosing a model,

a routing system analyzes the request and forwards it to the best model.

---

# Why Do We Need Model Routing?

Different models excel at different tasks.

For example,

one model may be:

- Faster

Another may be:

- Better at coding

Another may be:

- Better at reasoning

Another may be:

- Lower cost

Model Routing ensures that each request is handled by the most suitable model.

# Static Routing

Static Routing follows predefined rules.

Example:

```text
Translation

↓

Gemini

--------------------

Coding

↓

GPT-5

--------------------

Summarization

↓

Small Model
```

The routing rules are fixed.

Advantages:

- Simple
- Predictable
- Easy to implement

Disadvantages:

- Cannot adapt to changing workloads.

---

# Dynamic Routing

Dynamic Routing makes decisions at runtime.

Instead of using fixed rules,

the router evaluates the current request.

Example:

```text
Request

↓

Analyze Difficulty

↓

Compare Models

↓

Choose Best Model
```

Advantages:

- More flexible
- Better cost optimization
- Adapts to different workloads

Disadvantages:

- More complex to implement.

---

# Rule-Based Routing

The simplest router uses predefined rules.

Example:

```python
if task == "coding":
    use GPT-5

elif task == "translation":
    use Gemini

else:
    use Small Model
```

Many production systems begin with rule-based routing.

# The Cost-Quality Frontier

Every routing decision is really a point on a trade-off curve, not a single "correct" answer.

```text
Quality
   ▲
   │           ● GPT-5 (high quality, high cost)
   │
   │      ● Mid-size model
   │
   │  ● Small model (lower quality, low cost)
   │
   └──────────────────────────► Cost
```

A good router doesn't try to find "the best model" in the abstract — it picks the cheapest model that still clears the quality bar the specific request needs.

```text
Does This Request NEED GPT-5-level Quality?

├── Yes → Use It, Cost Is Justified

└── No  → A Cheaper Model on the Same Frontier Is a Better Choice
```

This reframes routing as an optimization problem: minimize cost subject to a quality constraint, rather than always maximizing quality regardless of cost.

# Evaluating Routing Quality: Shadow Traffic & A/B Testing

A routing strategy needs to be measured, not just deployed and assumed to work — this mirrors the Router Pattern chapter's point about measuring routing accuracy, applied specifically to model choice.

```text
Shadow Traffic
Send the same request to BOTH the current router's choice
AND a candidate new model, but only return the current
router's answer to the user.
→ Compare quality/cost offline, with zero user-facing risk.

A/B Testing
Route a small % of real traffic to a new routing strategy.
→ Compare real outcomes (user satisfaction, cost, latency)
  between the two groups.
```

```text
New Routing Strategy Proposed

↓

Test via Shadow Traffic First (no user risk)

↓

Looks Promising?

├── Yes → Graduate to a Small-Percentage A/B Test

└── No  → Discard, Try a Different Approach
```

Without this kind of evaluation, "the router seems to be working" is just an assumption — shadow traffic and A/B testing turn it into a measured fact.

# Fallback Routing on Provider Failure

Routing isn't just about picking the _best_ model — it also needs a plan for when the chosen model's provider is unavailable.

```text
Router Selects: GPT-5

↓

GPT-5 Provider Is Down / Rate Limited

↓

Router Falls Back to the Next-Best Available Model
(e.g. Claude, if it can handle the task adequately)

↓

Request Still Succeeds, Possibly at Slightly Lower Quality
```

This connects directly to the Model Gateway's failover responsibility (covered in the Enterprise Agent Architecture chapter) — the router decides the _preferred_ model, while the gateway executes the actual failover when that choice isn't available.

# Per-Tenant Routing Policies

In a Multi-Tenant platform, different tenants may need different routing rules, not one global policy for everyone.

```text
Tenant A (Free Tier)
→ Routed only to smaller, cheaper models, with strict cost caps

Tenant B (Enterprise Tier)
→ Access to the largest models, higher cost tolerance,
  possibly a dedicated fallback chain

Tenant C (Data Residency Requirement)
→ Routed only to models hosted in an approved region
```

```text
Request Arrives with tenant_id

↓

Load This Tenant's Routing Policy

↓

Apply Tenant-Specific Constraints Before Choosing a Model
```

This ties routing back to the Multi-Tenant Agent Systems chapter — a routing decision isn't just about the request's content, it also has to respect the constraints of whoever is making the request.

---

# Caching Routing Decisions

For very similar or repeated requests, re-running the full routing logic (especially AI-based routing) every time adds unnecessary latency and cost.

```text
Incoming Request

↓

Seen a Nearly Identical Request Recently?

├── Yes → Reuse the Cached Routing Decision

└── No  → Run Full Routing Logic → Cache the Decision
```

This mirrors the same caching idea from the Router Pattern chapter — worthwhile in high-traffic systems where a small number of request types make up most of the volume.

# Python Example

```python
def route(prompt_length):

    if prompt_length < 500:
        return "small-model"

    return "large-model"
```

A version reflecting tenant policy and fallback:

```python
def route(request, tenant_policy):
    preferred = choose_model(request)  # e.g. based on complexity

    if preferred not in tenant_policy.allowed_models:
        preferred = tenant_policy.default_model

    if not is_available(preferred):
        preferred = tenant_policy.fallback_model

    return preferred
```

Production routers evaluate many more signals,

but the idea remains the same.

# Industry Insight

Major AI platforms rarely depend on a single model.

Instead, they maintain a portfolio of models and dynamically route requests based on:

- Task complexity
- Cost
- Latency
- Availability
- Customer requirements

This approach improves scalability while significantly reducing operational costs.

Increasingly, platforms treat routing as a continuously tuned system — using shadow traffic and A/B tests to validate every routing change before it reaches all users, the same discipline applied to any other high-impact production change.

---

# Best Practices

Define clear routing criteria.

Frame routing as minimizing cost subject to a quality bar, not just "picking the best model."

Continuously evaluate routing quality using shadow traffic and A/B testing, not assumptions.

Monitor latency and cost.

Fallback to another model when necessary, and track how often fallback is triggered.

Apply per-tenant routing policies rather than one global rule for every request.

Cache routing decisions for repeated or highly similar requests.

Regularly update routing rules as new models become available.

# Common Beginner Mistakes

### Mistake 1

Sending every request to the same model.

Different tasks require different capabilities.

---

### Mistake 2

Optimizing only for cost.

Very cheap models may reduce response quality.

---

### Mistake 3

Ignoring latency.

The fastest acceptable model often provides the best user experience.

---

### Mistake 4

Keeping routing rules static forever.

Model capabilities evolve rapidly and routing strategies should evolve as well.

---

### Mistake 5

Deploying a new routing strategy directly to all traffic.

Without shadow traffic or a staged A/B test first, a flawed routing change affects every user immediately.

---

### Mistake 6

Using one global routing policy for every tenant.

Different tenants may have different cost tolerances, quality needs, or data residency constraints that a single policy can't satisfy.

# Interview Tip

A common interview question is:

A good answer is:

Model Routing is the process of automatically selecting the most appropriate Large Language Model for each incoming request. Enterprise systems evaluate factors such as task complexity, latency, cost, context size, and model capabilities to route requests to the model that provides the best balance between quality, speed, and operational cost.

A strong follow-up point: mention framing routing as optimizing the **cost-quality frontier** (cheapest model that clears the quality bar), validating routing changes with **shadow traffic and A/B testing**, and that routing needs a **fallback plan** for provider outages as well as **per-tenant policies** in multi-tenant platforms.

# Key Takeaways

- Model Routing automatically selects the best model for each request.
- Different models specialize in different tasks.
- Routing decisions may be static or dynamic.
- Routing can be framed as minimizing cost subject to a quality constraint — the cost-quality frontier.
- Shadow traffic and A/B testing validate routing changes before they affect all users.
- Fallback routing keeps requests succeeding when a preferred model's provider is unavailable.
- Multi-tenant platforms often need per-tenant routing policies, not one global rule.
- Caching routing decisions reduces latency and cost for repeated request types.
- Enterprise systems optimize routing for cost, latency, accuracy, and availability.
- Model Routing is a core capability of modern Enterprise LLM platforms.
