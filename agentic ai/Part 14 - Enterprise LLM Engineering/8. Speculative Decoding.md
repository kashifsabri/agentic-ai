# Introduction

Imagine you ask an AI Assistant:

```text
Explain how Transformers work.
```

Normally,

the LLM generates the response one token at a time.

```text
Token 1

↓

Token 2

↓

Token 3

↓

Token 4

↓

...
```

The larger the model,

the longer this process takes.

Wouldn't it be faster if a smaller model could **predict several upcoming tokens in advance**, and the larger model simply verified them?

That is exactly the idea behind **Speculative Decoding**.

---

# What is Speculative Decoding?

Speculative Decoding is an inference optimization technique where:

- A **small, fast model** predicts multiple future tokens.
- A **large, accurate model** verifies those predictions.
- If the predictions are correct, they are accepted immediately.
- If not, the large model corrects them.

This allows responses to be generated much faster without sacrificing quality.

---

# Why Do We Need Speculative Decoding?

Large Language Models are powerful,

but generating text token-by-token is computationally expensive.

Instead of asking the large model to generate every token,

we allow a smaller model to do most of the prediction work.

The large model only needs to verify the predictions.

# The Two Models

### Draft Model

The Draft Model is:

- Small
- Fast
- Low Cost

Its job is to predict several future tokens quickly.

---

### Target Model

The Target Model is:

- Larger
- More Accurate
- More Expensive

Its job is to verify whether the Draft Model's predictions are correct.

The Target Model always determines the final output.

---

# Example

Suppose the response begins with:

```text
Artificial Intelligence is...
```

The Draft Model predicts:

```text
changing the world.
```

The Target Model checks:

```text
✓ Correct
```

The predicted tokens are accepted immediately.

If instead the Draft Model predicts:

```text
a type of database.
```

The Target Model rejects those tokens and generates the correct continuation.

# How Speculative Decoding Works

```text
User Prompt

↓

Draft Model

↓

Predict Next Tokens

↓

Target Model

↓

Verify

├── Accept

└── Reject & Regenerate

↓

Final Response
```

This process repeats until the response is complete.

# Why Verification Is Fast: Parallel, Not Sequential

The part that surprises most people: verifying 5 speculated tokens with the Target Model doesn't cost anywhere near 5x the work of generating 1 token normally.

```text
Normal Generation (Sequential)
Generate Token 1 → Generate Token 2 → Generate Token 3
(each step must wait for the previous one — 3 separate passes)

Speculative Verification (Parallel)
Given all 5 draft tokens at once, the Target Model can compute
the probability of EACH position in a SINGLE forward pass
(the same way it would score a full existing sentence)
```

```text
Target Model Processes All 5 Draft Tokens Together

↓

Costs Roughly the Same as ONE Normal Generation Step,
Not Five Separate Steps

↓

This Is Why Accepting Multiple Tokens "for the price of one"
Is Possible at All
```

This is the actual mechanism behind the speedup — it isn't that verification is inherently cheaper than generation, it's that checking several tokens in parallel is roughly as expensive as generating just one token sequentially. Without this insight, the whole technique would seem to just move the same amount of work around rather than save any.

---

# Speculative Decoding Doesn't Change the Output — It's Lossless

This is worth stating explicitly, because it's easy to assume Speculative Decoding is a quality-for-speed trade-off. It isn't.

```text
Standard Generation with Target Model Alone
→ Produces some output distribution

Speculative Decoding (Draft + Target Model)
→ Produces the EXACT SAME output distribution, mathematically

↓

The Draft Model Only SUGGESTS candidates.
The Target Model's Own Judgment ALWAYS Determines
What's Actually Accepted.
```

This is fundamentally different from simply "using a smaller model for speed" — that would change the output quality. Speculative Decoding is specifically designed so that, on average, the final output is statistically identical to what the Target Model alone would have produced — it's a pure speed optimization with a rigorous correctness guarantee, not an approximation.

The large model performs every generation step.

With Speculative Decoding:

```text
↓

↓

```

Multiple tokens may be accepted at once,

reducing total inference time.

# Where Does the Draft Model Come From?

The Draft Model isn't an arbitrary unrelated model — its usefulness depends heavily on how well its predictions tend to match the Target Model's.

```text
Common Approaches:
- A smaller model from the SAME model family
  (e.g. a distilled or smaller version trained similarly
   to the large Target Model — predictions tend to align well)
- An n-gram / lookup-based "model"
  (extremely cheap statistical prediction based on common patterns,
   works well for very predictable text like code completion)
- Self-Speculative Decoding
  (using an early-exit or skipped-layer version of the SAME
   Target Model as its own draft — no separate model needed at all)
```

The general principle: the more similar the Draft Model's predictions are to what the Target Model would actually choose, the higher the acceptance rate, and the bigger the speedup.

---

# Estimating the Speedup: Acceptance Rate Matters

The real-world speedup depends heavily on how often the Draft Model guesses correctly — this isn't a fixed number, it's measured per deployment.

```text
Acceptance Rate = % of Draft Tokens the Target Model Accepts

High Acceptance Rate (e.g. 80%)
→ Most draft tokens get through → Large speedup

Low Acceptance Rate (e.g. 20%)
→ Most draft tokens get rejected and regenerated
→ Speedup shrinks, and near-zero acceptance can even be SLOWER
  than normal generation (wasted draft computation)
```

```text
Deploying Speculative Decoding?

↓

Measure Acceptance Rate on REAL Production Traffic

↓

Low Acceptance Rate?

↓

Consider a Better-Matched Draft Model, or Skip Speculative
Decoding for This Workload Entirely
```

This is why "evaluate whether the additional complexity justifies the performance gains" (in Best Practices) is such an important step — the technique isn't a guaranteed win, its payoff is entirely conditional on the Draft Model's real acceptance rate for actual traffic.

# Interaction with Batching

Speculative Decoding and Batch Inference (previous chapters) both aim to improve throughput, but combining them adds real complexity.

```text
Batching Alone
→ Groups multiple DIFFERENT users' requests together

Speculative Decoding Alone
→ Speeds up ONE request's sequential generation

Combined
→ Each request in the batch may have a DIFFERENT number
  of accepted draft tokens per step, making the batch's
  "shape" uneven at every iteration
```

This is precisely the kind of variable-length complexity that continuous batching (from the previous chapter) is designed to handle — production serving engines that support both together need scheduling logic sophisticated enough to manage per-request acceptance counts inside an already-dynamic batch.

# Benefits

Speculative Decoding provides:

- Lower Latency
- Faster Token Generation
- Better GPU Utilization
- Reduced Inference Cost
- Improved User Experience

These benefits are especially valuable for large models.

---

# Limitations

Speculative Decoding is most effective when:

- The Draft Model frequently predicts correctly.

If the Draft Model makes many incorrect predictions,

the Target Model must regenerate more tokens,

reducing the performance benefit.

# Real-World Example

Imagine an AI Coding Assistant.

Instead of having a large reasoning model generate every character,

a lightweight coding model predicts several upcoming tokens.

The larger model verifies those predictions.

Developers receive suggestions much faster while maintaining high quality.

Code completion is a particularly good fit for this technique because code is highly predictable (repeated patterns, common syntax), giving the Draft Model a naturally high acceptance rate — which is exactly the condition under which Speculative Decoding delivers its biggest wins.

# Industry Insight

Speculative Decoding is becoming increasingly important for serving large foundation models efficiently.

It is especially useful for:

- Chat Assistants
- Coding Assistants
- Enterprise AI Platforms
- High-Traffic LLM Services

As model sizes continue to grow,

Speculative Decoding helps reduce latency without requiring significantly more hardware.

Because the technique is mathematically lossless, it has been adopted relatively quickly across major inference engines — it's a rare case in ML systems engineering where a speed optimization comes with a rigorous guarantee that output quality is completely unaffected.

# Best Practices

Choose a Draft Model that is fast and reasonably accurate.

Prefer a Draft Model from the same family, or a self-speculative approach, for higher acceptance rates.

Use Speculative Decoding for latency-sensitive applications.

Measure token acceptance rates on real production traffic before committing to the approach.

Monitor overall throughput improvements.

Account for the added scheduling complexity when combining with batching.

Evaluate whether the additional complexity justifies the performance gains.

# Common Beginner Mistakes

### Mistake 1

Thinking the Draft Model generates the final response.

The Target Model always determines the final output.

---

### Mistake 2

Using an extremely weak Draft Model.

Poor predictions reduce the effectiveness of Speculative Decoding.

---

### Mistake 3

Assuming every predicted token is accepted.

The Target Model verifies every prediction.

---

### Mistake 4

Confusing Speculative Decoding with Model Routing.

Model Routing chooses **which model** handles a request.

Speculative Decoding uses **two models together** to accelerate inference.

---

### Mistake 5

Assuming Speculative Decoding trades quality for speed.

It's specifically designed to be lossless — the output distribution matches the Target Model alone; only the computation pattern changes.

---

### Mistake 6

Deploying Speculative Decoding without measuring acceptance rate first.

A low acceptance rate can make the technique net-negative for a given workload — it isn't a guaranteed win in every scenario.

# Interview Tip

A common interview question is:

> **What is Speculative Decoding?**

A good answer is:

Speculative Decoding is an inference optimization technique in which a small, fast Draft Model predicts several future tokens, while a larger Target Model verifies those predictions. Correct predictions are accepted immediately, reducing latency and improving inference efficiency without sacrificing the quality of the final output.

A strong follow-up point: mention that verification is fast because the Target Model checks multiple draft tokens in a single **parallel** forward pass (roughly the cost of generating one token normally), that the technique is mathematically **lossless** (same output distribution as the Target Model alone), and that real-world speedup depends entirely on the Draft Model's measured **acceptance rate**.

# Key Takeaways

- Speculative Decoding accelerates LLM inference.
- It uses a Draft Model and a Target Model together.
- The Draft Model predicts; the Target Model verifies.
- Verification is fast because checking several draft tokens in parallel costs about the same as generating one token sequentially.
- The technique is lossless — output quality matches the Target Model alone, it's not a quality trade-off.
- Draft Models often come from the same model family, an n-gram predictor, or a self-speculative variant of the Target Model itself.
- Real-world speedup depends on the Draft Model's acceptance rate, which should be measured on actual traffic.
- Combining with batching adds real scheduling complexity, since acceptance counts vary per request.
- Correct predictions reduce the amount of work performed by the larger model.
- It is an important optimization for serving large LLMs efficiently in production.
