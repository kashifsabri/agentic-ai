# Introduction

Imagine an AI Agent asks an MCP Server to:

```text
Analyze 50,000 documents.
```

This operation may take several minutes.

Should the Client simply wait without any updates?

No.

The Server should inform the Client about its progress.

For example:

```text
10%

25%

50%

75%

Completed
```

Similarly,

the Server may need to notify the Client that:

- A task has started
- A task has completed
- A resource has changed
- An operation has been cancelled

These updates are handled through **Notifications** and **Progress Tracking**.

---

# What are MCP Notifications?

An MCP Notification is a one-way message sent between an MCP Client and an MCP Server that **does not require a response**.

Unlike a request,

a notification simply communicates information.

The receiver processes the notification,

but does not send a reply.

---

# The Concrete Format You've Already Seen

The MCP Messages & JSON-RPC chapter showed exactly what one of these looks like on the wire:

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/progress",
  "params": {
    "progressToken": "task-123",
    "progress": 45,
    "total": 100
  }
}
```

Worth noticing what's structurally different from a request: there's no `id` field. That's not an oversight — it's the defining structural feature of a notification. Without an `id`, there's nothing for a response to reference back to, which is exactly why no response is expected or possible in the first place.

---

# What Is the `progressToken` Actually For?

This is a detail easy to skim past, but it solves a real practical problem: what if the Client has **multiple long-running operations in flight at the same time**? A progress update needs to say which specific operation it belongs to.

```text
Client sends Request A (id: 1) — "Analyze 50,000 documents"
   → includes a progressToken, e.g. "task-A"

Client sends Request B (id: 2) — "Generate financial report"
   → includes a different progressToken, e.g. "task-B"

Server sends progress notifications tagged with "task-A" or "task-B"
   → the Client matches each incoming progress update to the
     correct original operation using this token, NOT the
     (nonexistent) notification id
```

So the `progressToken` plays a similar linking role to the `id` field in ordinary requests/responses, just specifically for connecting a stream of progress notifications back to the operation they describe — necessary because notifications themselves don't carry an `id`.

---

# Why Are Notifications Needed?

Some events happen asynchronously.

Examples include:

- Task Started
- Task Completed
- Resource Updated
- Progress Changed
- Connection Closed

Sending a full request-response pair for every event would be unnecessary.

Notifications provide a lightweight alternative.

---

# Notifications Flow in Both Directions

The examples so far mostly show Server → Client notifications (progress updates), which can make it seem like notifications are inherently server-initiated. They're not — either side can send one, whenever it has one-way information to communicate.

```text
Server → Client examples:
- Progress updates on a long-running tool call
- "This resource's content just changed" (if the Client subscribed)
- "My list of available tools just changed"

Client → Server examples:
- "My list of available roots (filesystem access boundaries)
  just changed"
- Cancellation of an in-progress request (see below)
```

The direction depends entirely on which side has information the other side needs to know about — it's not a Server-only mechanism.

---

# Cancellation Is a Notification Too

A concrete and important example worth calling out specifically: if a Client decides it no longer needs the result of a long-running request (the user closed the app, or a timeout was hit — tying back to the max-iteration and timeout safeguards discussed in the ReAct chapter), it can send a cancellation notification.

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/cancelled",
  "params": {
    "requestId": 1,
    "reason": "User cancelled the operation"
  }
}
```

Note that this references the original request's `id` (here, `requestId: 1`) inside its `params` — that's how the Server knows _which_ in-progress operation to actually stop, even though the cancellation notification itself has no `id` of its own. This connects directly to a point from the Connection Lifecycle chapter: since notifications (including cancellation) aren't guaranteed to arrive, a Server can't assume a cancelled operation is _definitely_ stopped the instant it sends this — well-designed Servers should still handle the case where some work continues briefly after cancellation was requested.

# Requests vs Notifications

Both are MCP messages,

but they behave differently.

|Request|Notification|
|---|---|
|Expects a response|Does not expect a response|
|Has a request ID|No request ID|
|Used to perform operations|Used to communicate events|

Think of it this way:

- **Request** → "Please do this."
- **Notification** → "Just letting you know."

---

# Notifications Are "Fire and Forget" — A Reliability Tradeoff

This is worth being explicit about, since it's a real limitation, not just a design detail.

```text
Request         → Sender KNOWS whether it succeeded, failed, or
                   timed out, because a response (or lack of one)
                   provides that confirmation

Notification     → Sender has NO built-in way to know whether the
                   notification was actually received — there's no
                   acknowledgment, no retry mechanism, no delivery
                   guarantee at the protocol level
```

Practical implication: notifications are appropriate for _informational_ updates (progress percentages, "hey, something changed") where an occasional missed message is a minor UX inconvenience, not a correctness problem. They're a poor fit for anything where the sender absolutely needs confirmation that the message landed — that's what requests (with their expected response) are for. This is also why cancellation, discussed above, can't be treated as a hard guarantee — it's a best-effort signal, not a confirmed transaction.

# What is Progress Tracking?

Progress Tracking allows an MCP Server to report the status of long-running operations.

Instead of remaining silent,

the Server periodically informs the Client about the current progress.

This improves the user experience.

---

# Example

Suppose the Agent requests:

```text
Generate Annual Financial Report
```

Instead of waiting several minutes,

the Client receives updates like:

```text
10% Complete

↓

35% Complete

↓

60% Complete

↓

90% Complete

↓

Finished
```

The user knows the system is still working.

---

# Why is Progress Tracking Important?

Without progress updates,

users may assume:

- The application crashed.
- The network failed.
- The request was lost.

Progress Tracking reassures users that work is continuing.

# Best Practices

Send notifications only for meaningful events.

Provide periodic progress updates for long-running tasks.

Avoid sending excessive notifications.

Use notifications only when no response is required.

Display progress clearly to users.

Always include a `progressToken` when multiple long-running operations could be in flight simultaneously.

Treat cancellation and other notifications as best-effort signals, not guaranteed-delivery confirmations.

# Common Beginner Mistakes

### Mistake 1

Using requests for simple status updates.

Notifications are more appropriate because no response is needed.

---

### Mistake 2

Never reporting progress.

Users may think the application has failed.

---

### Mistake 3

Sending notifications too frequently.

Excessive updates can waste resources and overwhelm the Client.

---

### Mistake 4

Treating notifications like requests.

Notifications are informational and do not expect replies.

---

### Mistake 5

Assuming notifications only flow from Server to Client.

Either side can send a notification — the Client can notify the Server too (e.g. cancellation, or a change in the Client's own available roots).

---

### Mistake 6

Assuming a sent notification (especially a cancellation) was definitely received and acted upon.

Notifications have no built-in delivery guarantee — they're fire-and-forget, unlike requests which confirm success or failure via a response.

# Interview Tip

A common interview question is:

> **What is the difference between an MCP Request and an MCP Notification?**

A good answer is:

An MCP Request asks the Server to perform an operation and expects a response. An MCP Notification communicates information, such as progress updates or status changes, and does not expect any response. Notifications are commonly used for asynchronous events and long-running operations.

---

# Interview Tip

A stronger follow-up worth preparing for:

> **If a Client has two long-running tool calls happening at the same time, how does it know which progress notification belongs to which call?**

Answer:

Through the `progressToken` included in the original request and echoed back in each progress notification's params. Since notifications have no `id` field of their own (unlike requests), the `progressToken` serves as the link connecting a stream of progress updates back to the specific operation they describe.

# Key Takeaways

- Notifications are one-way messages that do not expect responses, structurally identifiable by having no `id` field.
- A `progressToken` links a stream of progress notifications back to the specific request they belong to, especially important with multiple concurrent operations.
- Notifications can flow in either direction — Client to Server as well as Server to Client (e.g. cancellation, or a Client's roots changing).
- Cancellation is itself sent as a notification, referencing the original request's `id` inside its params — and like all notifications, it's a best-effort signal, not a guaranteed one.
- Notifications are "fire and forget" — there's no built-in delivery confirmation, unlike requests.
- Progress Tracking keeps Clients informed during long-running operations.
- Notifications improve responsiveness and user experience.
- Requests perform work; notifications communicate events.
- MCP uses notifications for asynchronous communication and progress reporting.
