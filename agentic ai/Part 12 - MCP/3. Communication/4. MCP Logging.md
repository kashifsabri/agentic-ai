# Two Different Things Both Called "Logging" — Worth Separating

Before going further, it's worth flagging something this chapter blends together, since it's a genuine source of confusion between the MCP spec specifically and general software practice.

```text
MCP protocol-level logging (a defined MCP capability)
→ The Server sends structured log messages AS NOTIFICATIONS,
  using the method "notifications/message"
→ These travel over the same MCP connection to the Client, which
  can display them, forward them, or ignore them
→ This is literally the notification mechanism from the previous
  chapter, applied specifically to log-style messages

Traditional server-side application logging
→ The Server (like any backend application) writes logs to files,
  a log aggregation service, or a monitoring platform
→ The Client never sees these directly — they're purely for the
  people operating the Server
```

The examples throughout the rest of this chapter (Python's `logging` module, timestamps in files, centralized logging systems) mostly describe the _second_ kind — general backend logging practice, not something unique to MCP. The genuinely MCP-specific piece is the _first_ kind: an actual protocol capability where the Server can push log-level messages to the Client over the connection itself, the same way it can push progress notifications. Both matter, but only one of them is actually part of the MCP specification — worth being precise about which one an interview question is really asking about.

# What is MCP Logging?

MCP Logging is the process of recording important events that occur during communication between an MCP Client and an MCP Server.

Logs help developers understand:

- What happened
- When it happened
- Why it happened
- Whether it succeeded or failed

Unlike Notifications,

logs are primarily intended for developers and operators,

not end users.

(Note, per the distinction above: MCP's protocol-level log messages are technically _sent as_ notifications — "unlike Notifications" here is best read as referring to typical _progress_ notifications specifically, not the entire notification mechanism, since log messages and progress updates are both delivered the same underlying way.)

---

Examples include:

If something goes wrong,

logs provide the information needed to investigate the issue.

# Correlation IDs: Tracing One Request Across Multiple Hops

Worth introducing a practical concept here, since a single user request in a real MCP-based system can pass through several components: Host → Agent → Client → Server → external API, and possibly back through several MCP hops if multiple Servers are involved.

```text
Without a correlation ID:
→ Logs from the Host, the Client, the Server, and the external
  API are separate, disconnected entries — reconstructing "what
  happened for this one user request" means manually piecing
  together timestamps and guessing

With a correlation ID:
→ A single unique ID is generated at the start of the request
  and passed along through every hop
→ Every log entry from every component includes that same ID
→ A developer can search logs for one ID and see the ENTIRE
  request's journey across all systems, in order
```

This is a standard practice in distributed systems generally (often called **distributed tracing**), and it becomes especially valuable in MCP-based architectures precisely because a single Agent action can legitimately span Host, multiple Clients, multiple Servers, and multiple external APIs — without a shared ID threading through all of it, debugging a failure means guessing which log lines across which systems actually belong together.

# Logging vs Notifications

Although both communicate information,

they serve different purposes.

|Notifications|Logging|
|---|---|
|Inform Clients about events|Record events for developers and operators|
|Temporary|Usually stored|
|Improve user experience|Support debugging, monitoring, and auditing|

A progress notification may tell the Client:

```text
50% Complete
```

A log may record:

```text
10:42:15

Progress Updated

50%
```

(As noted above, MCP's own protocol-level logging is technically delivered as a notification too — this table is best understood as contrasting typical _event/progress_ notifications with logging's _purpose and audience_, rather than implying they're delivered through entirely unrelated mechanisms.)

A simplified logging example:

```python

```

Production MCP Servers typically use structured logging frameworks rather than simple text logs.

A structured log entry, with a correlation ID included, might look like:

```json
{
  "timestamp": "2026-08-05T10:42:15Z",
  "level": "INFO",
  "correlationId": "req-a1b2c3",
  "event": "tool_executed",
  "tool": "github.search_repositories"
}
```

# Logging and User Privacy — Connecting Back to Memory Storage

This connects directly to the privacy and security discussion in the Memory Storage chapter. Logs often capture request parameters, user inputs, and tool arguments — which can easily include personal or sensitive information if not handled carefully.

```text
- The same data-minimization and retention principles from Memory
  Storage apply to logs: don't log more than needed, and don't
  keep logs indefinitely without a policy
- Logs are frequently overlooked in privacy reviews, precisely
  because they feel like "just debugging output" rather than
  "another place personal data is stored" — but they are exactly
  that
- Regulations like GDPR (and similar data protection laws
  elsewhere) can apply to log data containing personal information,
  the same as any other stored personal data
```

Treating logs as a genuine data-storage location, not just an operational afterthought, is a meaningful part of building a compliant, privacy-respecting MCP system.

---

# A Related Risk: Log Injection

Briefly worth knowing: if raw, unsanitized user input or tool output is written directly into logs, it can create its own small injection risk — for example, malicious input designed to include characters that break a log format, or content crafted to mislead someone reading logs in a dashboard (a lightweight cousin of the prompt injection concept discussed earlier, aimed at whoever reviews the logs rather than at the model itself). Structured logging (treating fields as data, not concatenating raw strings into a log line) largely avoids this class of problem.

# Best Practices

Log important events consistently.

Use appropriate log levels.

Include timestamps.

Avoid logging sensitive information.

Use structured logs whenever possible.

Monitor logs regularly.

Include a correlation ID in every log entry so a single request can be traced across every component it touches.

Apply the same data-minimization and retention discipline to logs as to any other stored personal data.

# Common Beginner Mistakes

### Mistake 1

Logging sensitive information.

Never log:

- Passwords
- API Keys
- OAuth Tokens
- Private User Data

---

### Mistake 2

Logging everything.

Excessive logging makes important information difficult to find.

---

### Mistake 3

Using only debug logs in production.

Production systems typically emphasize information, warning, and error logs.

---

### Mistake 4

Ignoring logs until something fails.

Regular log monitoring helps detect problems early.

---

### Mistake 5

Conflating MCP's protocol-level log notifications with general server-side application logging.

They're related but distinct: one is a defined MCP capability delivered as a notification to the Client; the other is standard backend logging practice, invisible to the Client.

---

### Mistake 6

Not including a correlation ID, making it difficult to trace a single request across Host, Client, Server, and external API logs.

# Interview Tip

A common interview question is:

> **Why is Logging important in MCP?**

A good answer is:

MCP Logging records important events such as client connections, tool execution, resource access, and errors. It helps developers monitor system behavior, troubleshoot failures, and maintain reliable MCP Servers. Unlike Notifications, logs are intended for debugging and operational visibility rather than user communication.

---

# Interview Tip

A stronger follow-up worth preparing for:

> **Is MCP's logging capability the same thing as normal application logging?**

Answer:

Not exactly — they're related but distinct. MCP defines a protocol-level logging capability where the Server sends structured log messages to the Client as notifications (using `notifications/message`), which the Client can display or forward. Traditional application logging is the Server writing logs to files or a monitoring platform for its own operators, invisible to the Client. Real systems typically use both: MCP-level log notifications for Client-visible operational transparency, and standard backend logging for the Server's own operational needs.

# Key Takeaways

- MCP Logging records important Server events.
- MCP defines a protocol-level logging capability (delivered as a notification) distinct from general server-side application logging — both matter, but only one is MCP-specific.
- Correlation IDs let a single request be traced across every component it touches (Host, Client, Server, external API) — important given how many hops a real MCP request can involve.
- Logs help developers debug, monitor, and maintain MCP systems.
- Common log levels include Information, Warning, Error, and Debug.
- Logs should never contain sensitive credentials or private data, and should follow the same privacy/retention discipline as any other stored personal data.
- Unsanitized data written into logs can itself create a minor injection risk — structured logging largely avoids this.
- Logging and Notifications serve different purposes and complement each other.
