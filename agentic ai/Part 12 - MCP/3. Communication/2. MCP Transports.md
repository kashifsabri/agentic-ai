# Introduction

In the previous chapter, we learned that MCP Clients and Servers communicate using JSON-RPC messages.

But this raises an important question.

How does a JSON-RPC message actually travel from the Client to the Server?

Consider this request:

```json
{
  "method": "tools/call"
}
```

Does it travel:

- Through HTTP?
- Through a WebSocket?
- Through standard input/output?
- Through another communication channel?

JSON-RPC defines **what** the message looks like.

A **Transport** defines **how the message travels**.

---

# What is an MCP Transport?

An MCP Transport is the communication channel used to exchange JSON-RPC messages between an MCP Client and an MCP Server.

Think of the transport as the road,

while JSON-RPC is the vehicle traveling on that road.

Without a transport,

messages cannot move between the Client and the Server.

---

# Why Does MCP Need Transports?

JSON-RPC only defines the message format.

It does **not** specify:

- How to establish a connection
- How data is transmitted
- How messages are delivered

Those responsibilities belong to the transport layer.

# Common MCP Transports

The MCP specification supports multiple transport mechanisms.

The most common are:

- Standard Input / Output (stdio)
- Streamable HTTP

Each serves different use cases.

---

# 1. Standard Input / Output (stdio)

The Client starts the MCP Server as a local process.

Communication happens using:

- Standard Input (stdin)
- Standard Output (stdout)

Workflow

```text
Host

↓

Client

↓

stdin/stdout

↓

Local MCP Server
```

This transport is commonly used for local development and desktop applications.

---

## Advantages

- Simple
- Fast
- No network required
- Easy to develop locally

---

## Limitations

- Works only on the same machine
- Cannot easily support remote services

---

# 2. Streamable HTTP

The Client communicates with a remote MCP Server over HTTP.

Workflow

```text
Client

↓

HTTP

↓

Remote MCP Server
```

This transport is commonly used for cloud-hosted MCP Servers.

---

## Advantages

- Works across networks
- Supports cloud deployment
- Easy to scale
- Suitable for enterprise systems

---

## Limitations

- Requires network connectivity
- Slightly higher latency than local communication

# A Brief Note on How "Streamable HTTP" Got Here

Worth knowing if you go deeper into MCP documentation or older material: "Streamable HTTP" isn't the only HTTP-based approach that's existed. An earlier version of the spec used a two-endpoint design with **HTTP + Server-Sent Events (SSE)** — one endpoint for the Client to send requests, and a separate persistent SSE connection for the Server to stream responses back.

```text
Older approach: HTTP POST (requests) + separate SSE connection (responses)
Current approach: Streamable HTTP — a single, simpler connection model
                  that still supports streaming when needed
```

The newer Streamable HTTP transport consolidated this into something simpler to implement correctly. If you see references to "HTTP+SSE" as a distinct MCP transport in older tutorials or docs, know that it's effectively the predecessor to what's now just called Streamable HTTP — not a third option you need to separately choose between today.

# Security Implications Differ by Transport — Not Just Performance

This connects directly to the security chapters covered earlier (Agent Permissions, Least-Privilege, and the "tool poisoning" risk from the MCP Servers chapter) — the choice of transport isn't just a performance/convenience decision, it changes the trust boundary entirely.

```text
stdio
→ The Server runs as a local process, typically inheriting the SAME
  operating system permissions as the Host application itself
→ There's no network exposure by default — the "boundary" is
  effectively the local machine and whatever that process is
  allowed to do on it
→ Risk shifts to: what can this local process do if it's malicious
  or compromised, given it runs with real OS-level privileges?

Streamable HTTP
→ The Server is a separate, remote system — communication crosses
  a real network boundary
→ Requires its own authentication (API keys, OAuth tokens) and
  should use encrypted connections (HTTPS/TLS), not plain HTTP
→ Risk shifts to: is this remote Server who it claims to be, and
  is the connection itself secure from interception?
```

Practical implication: a stdio-based local tool should still only be given the OS permissions it actually needs (tying back to Least-Privilege), while a remote HTTP-based Server connection needs its own layer of authentication and authorization — you're not just trusting "the tool," you're trusting a network endpoint you don't control the same way you control a local process.

# Comparing MCP Transports

|Transport|Best For|
|---|---|
|stdio|Local desktop applications and development|
|Streamable HTTP|Remote servers and cloud deployments|

Choose the transport based on where the Server is running.

---

# A Session Generally Sticks to One Transport

Worth stating explicitly, since it connects back to the 1:1 Client-Server session concept from the MCP Clients chapter: once a Client establishes a session with a Server over a particular transport (say, stdio), that session doesn't switch to a different transport (say, HTTP) partway through. The transport is chosen and fixed at connection time, as part of how that specific session is set up — if you needed the same Server reachable over both a local process and a remote endpoint, that would typically mean running (and connecting to) two separately configured instances, not one session that changes transport mid-conversation.

---

# Mapping This to Tools You May Have Already Seen

Connecting this to something concrete: in the MCP Hosts chapter, connectors like Figma or Gmail were mentioned as examples of MCP Servers accessible through this environment. Since these are cloud services you don't run locally, they're reached over **Streamable HTTP** with their own authentication — not stdio, since there's no local process to launch for a service like Gmail. A hypothetical local tool (say, one that reads files directly off your own computer) would be a stdio candidate instead, since it needs to run as a process on your machine rather than being reached over a network.

# Industry Insight

Modern MCP deployments typically use:

- **stdio** for local tools and desktop applications.
- **Streamable HTTP** for cloud-hosted and enterprise MCP Servers.

Because MCP separates the communication protocol from the transport,

the same Client and Server logic can often work with different transport mechanisms.

---

# Best Practices

Choose stdio for local development.

Use Streamable HTTP for remote deployments.

Keep transport logic separate from business logic.

Use secure connections (HTTPS/TLS) and proper authentication for remote Servers.

Apply Least-Privilege to local stdio processes too — inherited OS permissions should still be scoped to what the tool actually needs.

Let the MCP SDK manage transport details whenever possible.

# Common Beginner Mistakes

### Mistake 1

Confusing JSON-RPC with the transport.

JSON-RPC defines the message.

The transport delivers the message.

---

### Mistake 2

Thinking transport changes the MCP protocol.

The protocol remains the same.

Only the communication channel changes.

---

### Mistake 3

Using HTTP for everything.

Local desktop applications are often simpler with stdio.

---

### Mistake 4

Implementing transport logic manually.

The official MCP SDK already provides transport implementations.

---

### Mistake 5

Assuming stdio is inherently "safer" just because there's no network exposure.

A local process still inherits real OS-level permissions — it should still follow Least-Privilege, not be assumed automatically safe.

---

### Mistake 6

Treating an unencrypted HTTP connection to a remote MCP Server the same as a secured one.

Remote transport requires proper authentication and encrypted connections (HTTPS/TLS), not just "it's HTTP so it works."

# Interview Tip

A common interview question is:

> **What is the difference between JSON-RPC and an MCP Transport?**

A good answer is:

JSON-RPC defines the structure of requests and responses exchanged between an MCP Client and an MCP Server. The transport defines how those messages are physically transmitted, such as through stdio for local communication or Streamable HTTP for remote communication.

---

# Interview Tip

A stronger follow-up worth preparing for:

> **Does the choice of transport affect security, or just performance?**

Answer:

Both. stdio-based Servers run as local processes inheriting the Host's OS-level permissions, so the trust boundary is the local machine and what that process is allowed to do — Least-Privilege still applies to it. Streamable HTTP-based Servers cross an actual network boundary, so they need their own authentication (API keys, OAuth) and encrypted connections (TLS), since you're trusting a remote endpoint you don't directly control the way you control a local process. The right transport depends on where the Server runs, but each one shifts what you specifically need to secure.

# Key Takeaways

- MCP Transports carry JSON-RPC messages between Clients and Servers.
- JSON-RPC defines the message format; the transport defines the communication channel.
- The two most common transports are stdio and Streamable HTTP — Streamable HTTP is the evolution of an older, more complex HTTP+SSE two-endpoint design.
- Each transport implies a different security trust boundary: stdio inherits local OS permissions, HTTP crosses a network boundary and needs its own auth and encryption.
- A session is generally locked to the transport it was established with — it doesn't switch mid-conversation.
- stdio is ideal for local applications, while Streamable HTTP is designed for remote deployments.
- The MCP SDK abstracts most transport implementation details.
