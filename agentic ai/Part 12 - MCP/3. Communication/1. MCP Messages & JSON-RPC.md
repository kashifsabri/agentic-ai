# Introduction

Imagine an AI Agent wants to search GitHub.

The Agent cannot simply say:

```text
Hey GitHub, find my repositories.
```

Computers require structured communication.

Instead, the Agent sends a message like:

```json
{
  "method": "tools/call",
  "params": {
    "name": "github.search_repositories",
    "arguments": {
      "query": "langgraph"
    }
  }
}
```

The MCP Server understands this message,

executes the request,

and returns another structured message.

This standardized communication is possible because MCP uses **JSON-RPC**.

---

# What are MCP Messages?

MCP Messages are standardized requests and responses exchanged between an MCP Client and an MCP Server.

They allow both sides to communicate using a common structure,

regardless of the programming language or platform.

Every interaction in MCP is represented as a message.

---

# What is JSON-RPC?

JSON-RPC is a lightweight protocol for remote procedure calls using JSON.

It defines a standard way to:

- Send requests
- Return responses
- Report errors
- Identify requests

MCP builds on JSON-RPC rather than inventing a completely new messaging format.

---

# Message Format vs Transport — Two Different Layers

This is worth clarifying now, since it directly sets up the next chapter and is a common point of confusion.

```text
JSON-RPC (this chapter)
→ The MESSAGE FORMAT: what the actual request/response text looks
  like — the structure of the JSON itself

Transport (next chapter)
→ The DELIVERY MECHANISM: how those JSON-RPC messages physically
  travel between Client and Server — e.g. stdio for local processes,
  HTTP/SSE for remote ones (briefly previewed in the MCP Clients chapter)
```

A useful analogy: JSON-RPC is like the _language_ two people are speaking (say, English), while the transport is the _medium_ carrying that language (a phone call vs a letter vs speaking face-to-face). The same JSON-RPC message could travel over stdio or over HTTP — the message format stays identical regardless of which transport delivers it. This separation is intentional: it lets MCP support very different environments (a local file-system tool vs a cloud-hosted API) without needing a different message format for each.

JSON-RPC is:

- Widely supported

This makes it an excellent foundation for communication between AI Agents and external systems.

# Why JSON-RPC Instead of REST?

Since most developers are more familiar with REST APIs than JSON-RPC, this comparison is worth having ready for an interview.

```text
REST
→ Organized around RESOURCES and HTTP verbs
  e.g. GET /repositories, POST /issues, DELETE /issues/42
→ The URL and HTTP method together describe the operation

JSON-RPC
→ Organized around METHODS being called directly, with parameters
  e.g. {"method": "tools/call", "params": {"name": "search_repositories", ...}}
→ Everything about the call (what to do, with what arguments) lives
  inside the message body itself, not the URL/verb
```

Why this fits MCP better than REST: MCP needs to expose a flexible, growing set of arbitrary operations (tools, resources, prompts — potentially dozens of different named methods per Server), transported over multiple possible mechanisms (not just HTTP, but also stdio for local processes). REST's resource-and-verb model maps awkwardly onto "call this arbitrary named tool with these arguments," and REST is fundamentally tied to HTTP semantics — which doesn't fit a local stdio connection at all. JSON-RPC's "call a named method with parameters" model matches MCP's actual use case (invoking named tools/operations) far more directly, and it's transport-agnostic by design.

# Anatomy of a JSON-RPC Request

A typical request contains:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    ...
  }
}
```

Let's understand each field.

---

## jsonrpc

Specifies the protocol version.

Example

```json
"jsonrpc": "2.0"
```

---

## id

Identifies the request.

Example

```json
"id": 1
```

The same ID appears in the response,

allowing the Client to match responses with requests.

---

## method

Specifies the operation being requested.

Example

```json
"method": "tools/call"
```

Other methods include:

- resources/read
- prompts/get
- initialize

We'll study these later.

---

## params

Contains the information required to execute the request.

Example

```json
"params": {
  "name": "github.search"
}
```

# A Concrete Look at `initialize`

The MCP Clients chapter mentioned that a session begins with a capability negotiation handshake before any tool calls happen. Here's what that actually looks like as a JSON-RPC exchange, tying the two chapters together directly:

```json
Client sends:
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2024-11-05",
    "capabilities": { ... }
  }
}
```

```json
Server responds:
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2024-11-05",
    "capabilities": {
      "tools": {},
      "resources": {}
    },
    "serverInfo": { "name": "github-mcp-server", "version": "1.0.0" }
  }
}
```

This is a normal JSON-RPC request/response pair, using the `initialize` method specifically — it's not a special message type outside the JSON-RPC format, just a particular method name the protocol reserves for establishing the session. Once this handshake completes, the Client knows exactly what capabilities (tools, resources, prompts) the Server actually offers, and can start making real requests like `tools/call`.

# Anatomy of a JSON-RPC Response

A successful response looks like:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    ...
  }
}
```

The Server returns:

- Protocol version
- Matching request ID
- Result

---

# Error Responses

If something goes wrong,

the Server returns an error instead.

Example

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32601,
    "message": "Method not found"
  }
}
```

Instead of crashing,

the Client receives structured error information.

# A Practical Example of When Notifications Matter

It's worth grounding "notifications don't expect a response" in a concrete scenario, since otherwise it's easy to wonder why they're needed at all.

Imagine a tool call that takes a long time — say, an MCP Server searching through a large codebase, or generating a large report. Without notifications, the Client would simply wait silently until the final response arrives, with no visibility into progress. This connects back to a concern raised in the ReAct chapter: long-running operations benefit from some signal that things are still working, rather than looking indistinguishable from a hung connection.

```json
Server sends (notification, no id, no response expected):
{
  "jsonrpc": "2.0",
  "method": "notifications/progress",
  "params": {
    "progressToken": "task-123",
    "progress": 45,
    "total": 100
  }
}
```

The Server can send several of these as work proceeds, and the Client (and by extension, the Host's UI) can show a progress indicator to the user — all before the final `result` response for the original request eventually arrives. The key structural difference from a request: notifications have no `id` field, because there's nothing to match a response back to — they're one-directional, fire-and-forget updates.

# Batch Requests (A JSON-RPC Feature Worth Knowing)

One more JSON-RPC capability worth mentioning: the protocol supports sending multiple requests in a single batch, as a JSON array, rather than one request per round-trip.

```json
[
  { "jsonrpc": "2.0", "id": 1, "method": "tools/call", "params": {...} },
  { "jsonrpc": "2.0", "id": 2, "method": "resources/read", "params": {...} }
]
```

This connects back to the parallel function calling concept from the Function Calling chapter — batching reduces round-trips when multiple independent operations are needed at once, similar in spirit to requesting multiple function calls in one turn, just expressed at the JSON-RPC transport level instead of at the model's tool-calling level.

# Best Practices

Always follow the JSON-RPC specification.

Use unique request IDs.

Validate incoming messages.

Return structured error responses.

Keep message formats consistent.

Use notifications for progress updates on long-running operations rather than leaving the Client with no feedback.

# Common Beginner Mistakes

### Mistake 1

Thinking JSON-RPC is unique to MCP.

JSON-RPC is an independent protocol that MCP builds upon.

---

### Mistake 2

Ignoring request IDs.

The Client uses IDs to match responses with requests.

---

### Mistake 3

Returning plain text instead of structured responses.

MCP communication should always follow the JSON-RPC format.

---

### Mistake 4

Treating notifications like requests.

Notifications do not expect responses.

---

### Mistake 5

Confusing the message format (JSON-RPC) with the transport mechanism (stdio, HTTP/SSE).

They're separate layers — the same JSON-RPC message can travel over different transports.

# Interview Tip

A common interview question is:

> **Why does MCP use JSON-RPC?**

A good answer is:

MCP uses JSON-RPC because it provides a simple, lightweight, language-independent protocol for structured communication between Clients and Servers. It standardizes requests, responses, and error handling, making MCP interoperable across different programming languages and AI frameworks.

---

# Interview Tip

A stronger follow-up worth preparing for:

> **Why did MCP choose JSON-RPC over a REST-style API?**

Answer:

REST is organized around resources and HTTP verbs, which fits CRUD-style operations well but maps awkwardly onto calling an arbitrary, growing set of named tools with arbitrary parameters — MCP's actual use case. JSON-RPC's "call this method with these parameters" model fits that directly. REST is also inherently tied to HTTP, while MCP needs to work over multiple transports, including local stdio connections that have no HTTP semantics at all — JSON-RPC is transport-agnostic, which REST isn't.

# Key Takeaways

- MCP communication is based on JSON-RPC.
- JSON-RPC is the message format; transport (covered next) is the separate delivery mechanism — the same message can travel over stdio or HTTP.
- JSON-RPC's method-call style fits MCP's use case (calling named tools/operations) better than REST's resource-and-verb style, and it isn't tied to HTTP.
- Every interaction is represented as a structured message.
- Requests contain a method, parameters, and a unique ID; the `initialize` method is a normal JSON-RPC call used specifically for the session handshake.
- Responses return either a result or an error.
- Notifications (no `id`, no expected response) are useful for progress updates during long-running operations.
- JSON-RPC supports batching multiple requests into one call, reducing round-trips.
- JSON-RPC enables consistent communication across all MCP-compatible systems.
