# Introduction

Imagine an MCP Client connects to an MCP Server.

The Client wants to:

- Call Tools
- Read Resources
- Request Prompts

But how does the Client know whether the Server actually supports these capabilities?

Should it simply assume?

No.

Before normal communication begins,

the Client and Server exchange information about the capabilities they support.

This process is called **Capability Negotiation**.

---

# What is Capability Negotiation?

Capability Negotiation is the process by which an MCP Client and an MCP Server exchange information about the features they support during initialization.

This allows both sides to understand:

- What operations are available
- Which features can be used
- Which features are unavailable

Only supported capabilities are used during the session.

---

# This Is the Same `initialize` Exchange You've Already Seen

Worth connecting the dots directly rather than treating this as a separate mechanism: the MCP Messages & JSON-RPC chapter showed a concrete `initialize` request/response pair. Look again at what the Server's response actually contained:

```json
"result": {
  "protocolVersion": "2024-11-05",
  "capabilities": {
    "tools": {},
    "resources": {}
  },
  "serverInfo": { "name": "github-mcp-server", "version": "1.0.0" }
}
```

That `"capabilities": { "tools": {}, "resources": {} }` field **is** capability negotiation, in literal JSON-RPC form — it's not a separate protocol step happening somewhere else, it's specifically the payload carried inside the `initialize` response you already looked at. This chapter is explaining the _meaning and purpose_ of a field you've already seen the _exact syntax_ of.

# Why is Capability Negotiation Needed?

Imagine a Client sends:

```text
Call Tool
```

But the Server only supports:

- Resources
- Prompts

The request would fail.

Instead,

the Client first discovers the Server's capabilities.

It then uses only the features that are supported.

---

# Negotiation Is Bidirectional, Not Just Server → Client

The examples so far frame this as "the Server advertises, the Client adapts" — which is true, but only half the picture. In practice, **the Client also advertises its own capabilities** to the Server, as part of the same `initialize` request.

```text
Client → Server:  "Here's what I (the Client/Host) support:
                   e.g. I can provide 'roots' (file system access
                   boundaries), I support 'sampling' (letting the
                   Server ask ME to make an LLM call on its behalf)"

Server → Client:   "Here's what I (the Server) support:
                   e.g. tools, resources, prompts"
```

Why this matters: some MCP capabilities require the Client's cooperation to work at all. For example, **sampling** is a capability where the _Server_ can ask the _Client_ to run an LLM completion on its behalf (useful when a Server needs some AI reasoning as part of fulfilling a request, without needing its own separate LLM access). This only works if the Client declares upfront that it supports handling sampling requests. So negotiation isn't the Server unilaterally telling the Client what's available — both sides are declaring what they're each capable of participating in, and the actual usable feature set for the session is the overlap between what both sides support.

# What is a Capability?

A capability is a feature that an MCP component supports.

Examples include:

- Tools
- Resources
- Prompts
- Sampling
- Logging
- Notifications

Not every MCP Server supports every capability.

---

# Capabilities Can Have Finer-Grained Sub-Flags

The examples so far show whole categories (Tools: yes/no, Resources: yes/no), but real capability objects can include more specific sub-flags within a category, not just an on/off switch for the whole thing.

```json
"capabilities": {
  "tools": {
    "listChanged": true
  },
  "resources": {
    "subscribe": true,
    "listChanged": true
  }
}
```

Here, `"listChanged": true` under `tools` means the Server can notify the Client whenever its available tool list changes dynamically (not just "tools exist," but "and I'll tell you if that list is updated later"). `"subscribe": true` under `resources` means the Client can subscribe to be notified when a specific resource's content changes. This level of granularity is why negotiation matters even between two Servers that both nominally "support tools" — the exact sub-features available can still differ.

# How Capability Negotiation Works

The process is straightforward.

### Step 1

The Client connects.

↓

### Step 2

Initialization begins.

↓

### Step 3

The Server advertises its supported capabilities.

↓

### Step 4

The Client records them.

↓

### Step 5

The Client uses only supported capabilities.

(And, per the bidirectional point above: the Client also advertised its own capabilities in Step 2, as part of the same `initialize` request — the Server records those too.)

# What Happens With a Protocol Version Mismatch?

Capability Negotiation assumes both sides are at least speaking a compatible protocol version in the first place — worth knowing what happens when they aren't, since it's a natural edge case to ask about.

```text
Client sends: "protocolVersion": "2024-11-05"
Server only supports: "protocolVersion": "2024-06-01" (older)
```

Typically, the Server responds during `initialize` with the protocol version it actually supports, and the Client is responsible for deciding whether it can work with that version or not — some implementations support graceful degradation to an older mutually-supported version, while a completely incompatible mismatch should result in the Client declining to proceed rather than attempting communication that's likely to fail unpredictably. This is another reason initialization has to happen before any real work: version compatibility, not just capability lists, needs to be confirmed first.

# Benefits of Capability Negotiation

Capability Negotiation provides several advantages.

- Prevents unsupported requests
- Improves interoperability
- Allows different Servers to expose different features
- Makes Clients more flexible
- Supports future MCP extensions

It enables Clients and Servers to evolve independently.

# Industry Insight

Capability Negotiation is a common design pattern in distributed systems.

Rather than assuming every system supports identical features,

components advertise their capabilities during initialization.

This makes systems:

- Backward compatible
- Forward compatible
- Easier to extend

MCP uses this same approach to support evolving capabilities without breaking existing implementations.

---

# Best Practices

Always negotiate capabilities during initialization.

Never assume a capability is supported.

Design Clients to adapt dynamically.

Handle unsupported capabilities gracefully.

Allow new capabilities to be added without breaking existing Clients.

Remember negotiation is bidirectional — a Host/Client should accurately declare what it can support too, especially for Client-side capabilities like sampling.

# Common Beginner Mistakes

### Mistake 1

Assuming every Server supports every capability.

Different Servers expose different features.

---

### Mistake 2

Skipping Capability Negotiation.

This may lead to unsupported requests and communication failures.

---

### Mistake 3

Treating missing capabilities as errors.

Many Servers intentionally expose only a subset of MCP capabilities.

---

### Mistake 4

Hardcoding supported capabilities.

Clients should discover capabilities dynamically during initialization.

---

### Mistake 5

Assuming capability negotiation is one-directional (Server → Client only).

The Client also advertises its own supported capabilities in the same `initialize` exchange — some features (like sampling) require the Client's declared support to function at all.

---

### Mistake 6

Assuming "both sides support tools" means identical tool-related behavior.

Sub-capabilities (like `listChanged` or `subscribe`) mean the same top-level category can still differ in finer-grained supported features.

# Interview Tip

A stronger follow-up worth preparing for:

> **Is capability negotiation something only the Server does, advertising to the Client?**

Answer:

No — it's bidirectional. Within the same `initialize` exchange, the Client also declares its own supported capabilities to the Server, not just the other way around. This matters because some MCP features, like sampling (where a Server can ask the Client to perform an LLM call on its behalf), depend on the Client having declared support for handling that kind of request. The capabilities actually usable in a session are the overlap of what both sides declared, not just what the Server offers.

# Key Takeaways

- Capability Negotiation occurs during MCP initialization, as part of the same `initialize` exchange covered in the JSON-RPC chapter.
- Negotiation is bidirectional — the Client declares its own capabilities too, not just the Server.
- Some capabilities (like sampling) require the Client's declared cooperation to function at all.
- Capabilities can include finer-grained sub-flags (e.g. `listChanged`, `subscribe`) beyond a simple supported/not-supported flag.
- Protocol version compatibility is confirmed alongside capabilities, and mismatches need to be handled explicitly.
- Servers may expose different sets of capabilities.
- Clients should adapt dynamically rather than making assumptions.
- Capability Negotiation makes MCP flexible, extensible, and interoperable.
