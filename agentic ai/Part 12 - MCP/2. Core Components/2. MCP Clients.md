# Introduction

Imagine you're using an AI Assistant.

You ask:

```text
Search my GitHub repositories.
```

The AI Agent decides that GitHub information is needed.

However,

the Agent does **not** communicate directly with GitHub.

Instead,

it asks the **MCP Client** to contact the GitHub MCP Server.

The MCP Client:

- Opens the connection
- Sends the request
- Waits for the response
- Returns the result to the Agent

Think of the MCP Client as the **messenger** between the Agent and the MCP Server.

---

# What is an MCP Client?

An MCP Client is the component responsible for communicating with one or more MCP Servers.

It sends requests,

receives responses,

and manages communication between the AI Agent and external capabilities.

The Client does **not** execute tools.

It simply manages communication.

# A Needed Correction: Client-to-Server Cardinality

Before going further, it's worth clarifying something the diagrams later in this chapter get slightly wrong, since it's the kind of detail that gets tested directly in interviews and matters for getting the architecture right.

Later in this chapter, a diagram shows "One Client, Multiple Servers" (one Client fanning out to GitHub, Slack, and PostgreSQL Servers). In the actual MCP specification, the relationship is the opposite: **each Client instance maintains a dedicated, stateful, one-to-one session with exactly one Server.**

```text
Correct model:

MCP Host
   │
   ├── MCP Client 1 ──── (1:1 session) ──── GitHub MCP Server
   ├── MCP Client 2 ──── (1:1 session) ──── Slack MCP Server
   └── MCP Client 3 ──── (1:1 session) ──── PostgreSQL MCP Server
```

So when an application (Host) needs to talk to three different Servers, it creates **three separate Client instances** — not one Client juggling three server connections. This matches what the Host chapter described: a Host manages _multiple_ Clients, with each Client dedicated to _one_ Server connection.

Why this design choice matters: a 1:1 Client-Server relationship lets each session maintain its own independent state, capabilities negotiated specifically for that connection, and error handling — without one Server's connection issues affecting another. Think of each Client as a single phone line to a single Server, not a switchboard operator juggling multiple calls on one line.

The rest of this chapter's _concepts_ (what a Client does, how it manages a connection, error handling) are all still accurate — just mentally correct the "one Client, many Servers" framing to "the Host creates one Client per Server it needs to reach."

# How Communication Actually Happens: Transport Mechanisms

It's worth knowing, at least at a high level, what "the Client connects to the Server" means technically — this is called the **transport layer** in MCP.

```text
stdio (standard input/output)
→ Used when the Server runs as a local process on the same machine
  as the Host (e.g. a local tool running alongside Claude Desktop)
→ Client and Server communicate by writing to and reading from
  each other's input/output streams

HTTP with Server-Sent Events (SSE) / Streamable HTTP
→ Used when the Server is remote (running on a different machine,
  accessed over a network — like a cloud-hosted GitHub or Slack
  integration)
→ Standard web protocols carry the messages back and forth
```

This distinction matters practically: a locally-running tool (like a file system or local database integration) typically uses stdio for low-latency, no-network-hop communication, while a cloud service integration (like the Figma or Gmail connectors seen in this environment) uses HTTP-based transport since the Server lives elsewhere entirely.

# Sessions and the Handshake

Since each Client-Server pair maintains a dedicated 1:1 connection (per the correction above), that connection is called a **session**, and it begins with a **capability negotiation handshake** before any actual tool calls happen.

```text
1. Client connects to Server

2. Client and Server exchange information about what they each
   support (protocol version, available capabilities)

3. Server responds with what it offers: available tools,
   resources, and prompts

4. Session is now established — the Client can start making
   actual requests (like calling a specific tool)
```

This means a Client isn't just a dumb pipe forwarding messages — it holds session state: which Server it's connected to, what that Server's negotiated capabilities are, and the ongoing connection status. This is part of why "one Client, many unrelated Servers" doesn't fit the actual model — each session's negotiated state is specific to one particular Server.

# Client vs Host vs Server

Each component has a different responsibility.

|Component|Responsibility|
|---|---|
|Host|Runs the application|
|Client|Manages communication (one dedicated session per Server)|
|Server|Provides capabilities|

Think of them as:

```text

↓

↓

↓
```

# Best Practices

Create a dedicated Client instance per Server connection, rather than trying to share one Client across unrelated Servers.

Handle connection failures gracefully.

Validate server responses.

Monitor communication errors.

Keep business logic outside the Client.

# Common Beginner Mistakes

### Mistake 1

Thinking the Client executes tools.

The Server executes tools.

The Client only communicates.

---

### Mistake 2

Confusing the Client with the Agent.

The Agent performs reasoning.

The Client handles communication.

---

### Mistake 3

Believing a single Client instance connects to multiple unrelated Servers.

In the actual MCP model, each Client maintains a dedicated 1:1 session with one Server; a Host creates a separate Client for each Server it needs to reach.

---

### Mistake 4

Putting business logic inside the Client.

The Client should focus only on communication.

---

### Mistake 5

Assuming all Client-Server communication happens the same way.

Local Servers typically use stdio transport; remote/cloud Servers typically use HTTP-based transport (like SSE) — the mechanism differs based on where the Server runs.

# Interview Tip

A common interview question is:

> **What is the role of an MCP Client?**

A good answer is:

An MCP Client manages communication between an AI Agent and MCP Servers. It establishes connections, sends requests, receives responses, handles communication errors, and returns results to the Agent. It does not execute tools or perform reasoning.

---

# Interview Tip

A stronger follow-up worth preparing for, given the correction above:

> **How many Servers can a single MCP Client connect to?**

Answer:

Exactly one. Each MCP Client maintains a dedicated, stateful, one-to-one session with a single Server, including a capability negotiation handshake specific to that connection. If a Host application needs to reach multiple Servers (say, GitHub, Slack, and a database), it creates a separate Client instance for each one — it's the Host that manages multiple Clients, not a single Client managing multiple Server connections.

# Key Takeaways

- The MCP Client is responsible for communication with MCP Servers.
- Each Client maintains a dedicated 1:1 session with exactly one Server — a Host creates multiple Clients to reach multiple Servers, not one Client fanning out to many.
- A session begins with a capability negotiation handshake before any tool calls happen.
- Communication happens over a transport mechanism — commonly stdio for local Servers, HTTP/SSE for remote ones.
- It sends requests and receives responses on behalf of the Agent.
- The Client manages connections, errors, and communication for its one Server.
- The Client does not execute tools or perform reasoning.
