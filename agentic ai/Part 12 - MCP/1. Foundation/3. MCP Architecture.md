# Introduction

Imagine a user asks an AI Assistant:

```text
Find all open GitHub issues assigned to me.
```

The AI model cannot directly access GitHub.

Instead, the request passes through several components before reaching GitHub.

```text
User

↓

AI Agent

↓

MCP Client

↓

MCP Server

↓

GitHub API

↓

GitHub
```

Each component has a specific responsibility.

Together, they form the **MCP Architecture**.

---

# What is MCP Architecture?

MCP Architecture defines how different components communicate to allow AI Agents to access external tools, resources, and services.

Rather than connecting directly to every external system,

the Agent communicates through standardized MCP components.

This separation makes the system easier to build,

maintain,

and extend.

> **Note:** This is an example of the classic software engineering principle of **separation of concerns** — each layer (Host, Client, Server) has exactly one job, and none of them needs to understand the internal details of the others. The Host doesn't need to know how GitHub's API works; the Client doesn't need to know what the user's question was; the Server doesn't need to know which AI application is calling it. This is what makes the architecture reusable rather than a single monolithic integration.

# Core Components

The MCP Architecture consists of three primary components.

- Host
- Client
- Server

We'll study each one in detail in the upcoming chapters.

For now, understand their responsibilities.

---

## Host

The Host is the application that the user interacts with.

Examples include:

- ChatGPT
- Claude Desktop
- VS Code
- Cursor
- Enterprise AI Applications

The Host provides the user interface and starts MCP communication.

The Host is also typically the component responsible for **security decisions** — deciding which MCP servers a user is allowed to connect to, requesting user consent before a tool with side effects (like sending an email or deleting a file) is actually invoked, and enforcing any permission scopes. This matters because it means MCP's specification treats trust and consent as part of the architecture itself, not as something bolted on separately by each application.

---

## Client

The MCP Client communicates with MCP Servers.

Its responsibilities include:

- Connecting to Servers
- Sending Requests
- Receiving Responses
- Managing Communication

Think of the Client as the communication manager.

An important detail: **a Host typically maintains one Client instance per connected Server**, not one Client shared across all servers. If an AI application is connected to a GitHub server, a Slack server, and a Notion server simultaneously, it manages three separate Client-Server sessions, each with its own connection state, capabilities, and lifecycle. This 1:1 pairing is part of why adding a new server doesn't disturb the existing connections to other servers.

---

## Server

The MCP Server exposes capabilities to the Client.

These capabilities may include:

- Tools
- Resources
- Prompts

The Server performs the requested operations and returns results.

Servers are typically built and run independently of any particular AI application — a GitHub MCP Server, for instance, doesn't know or care whether it's being called by Claude Desktop, Cursor, or a custom enterprise Agent. This independence is what allows a single server implementation to be published once and reused broadly, rather than rebuilt for each Host.

# Request Flow

A typical request follows this sequence.

```text
User

↓

Host

↓

MCP Client

↓

MCP Server

↓

External Tool

↓

MCP Server

↓

MCP Client

↓

Host

↓

User
```

Every request follows this standardized workflow.

Before any tool calls happen, there's actually an earlier step not shown above: **initialization**. When a Client first connects to a Server, they perform a handshake exchanging protocol versions and declaring their respective **capabilities** — for example, the Server states whether it supports tools, resources, prompts, or notifications, and the Client states what it's able to handle in return. Only after this handshake completes does the normal request/response flow (like calling a tool) begin. This is also the point at which errors like version mismatches are caught early, rather than surfacing later as a confusing failure mid-task.

# Why Separate Client and Server?

Instead of combining everything into one application,

MCP separates responsibilities.

Benefits include:

- Better modularity
- Easier maintenance
- Independent development
- Reusable Servers
- Standard communication

A single MCP Server can serve many different Clients.

There's also a security benefit worth noting: because the Server runs as a separate process (or even on a separate machine, depending on transport), it can be sandboxed, given its own restricted credentials, and monitored independently of the Host application. A compromised or buggy tool inside a Server is less likely to directly compromise the Host application than it would be if everything ran together as one process with shared memory and permissions.

# Visual Architecture

```text
                Host

                  │

                  ▼

             MCP Client

                  │

          JSON-RPC Messages

                  │

                  ▼

             MCP Server

        ┌────────┼────────┐

        ▼        ▼        ▼

     Tools   Resources  Prompts

                  │

                  ▼

        External Services
```

Notice that the Client never talks directly to the external services.

Everything passes through the MCP Server.

It's worth being precise about what **Tools**, **Resources**, and **Prompts** each mean, since they're often used loosely:

- **Tools** are actions the model can invoke that typically have side effects or perform computation — e.g., `send_email`, `create_issue`.
- **Resources** are read-only data the Host can attach to context — e.g., a file's contents, a database record — conceptually closer to "things a user or model can read" than "things a model can do."
- **Prompts** are reusable, server-defined prompt templates that a Host can surface to the user (e.g., a "summarize this PR" template exposed by a GitHub server) rather than something the model decides to invoke on its own.

# Python Example

A simplified example:

```python
client.connect(server)

response = client.call_tool(
    "github.search_issues"
)

print(response)
```

The Client does not need to know how GitHub works internally.

It only communicates using MCP.

A slightly fuller example, showing the initialization handshake mentioned above before any tool call happens:

```python
# 1. Connect and perform the capability handshake
client.connect(server)
capabilities = client.initialize()  # negotiates protocol version + capabilities

# 2. Discover what this server actually offers before calling anything
available_tools = client.list_tools()

# 3. Call a tool using the standardized request/response shape
response = client.call_tool(
    name="github.search_issues",
    arguments={"assignee": "me", "state": "open"}
)

print(response)
```

Note that `list_tools()` is what makes MCP servers self-describing — the Client (and by extension, the model) doesn't need the tool names hardcoded in advance; it learns them dynamically from the Server at connection time.

# Industry Insight

The modular architecture of MCP allows organizations to build reusable Servers that can be shared across multiple AI applications.

Instead of maintaining separate integrations for every Agent,

organizations maintain a single MCP Server for each service.

This greatly reduces engineering effort and improves interoperability.

This modularity is also why MCP servers can be distributed in different ways depending on need: run locally via stdio for tools that need direct filesystem or local-machine access, or hosted remotely and reached over HTTP for cloud services shared across an organization — the three-layer architecture (Host/Client/Server) stays the same either way, only the transport between Client and Server changes.

# Best Practices

Separate communication from business logic.

Keep MCP Servers focused on a single responsibility.

Reuse Servers across multiple applications.

Follow the MCP specification consistently.

Design Servers to be modular and independent.

A couple of additional points:

- **Design each Server around a single service or domain**, rather than building one large "do everything" server — this mirrors the microservices principle of single responsibility and keeps permission scopes narrow (a Slack server should only need Slack credentials, not also database credentials).
- **Treat the initialization handshake and capability negotiation seriously when building a Host.** Skipping proper version/capability checks can lead to a Client assuming a Server supports something it doesn't, producing confusing runtime failures instead of a clean, early error.

# Common Beginner Mistakes

### Mistake 1

Confusing the Host with the Client.

The Host provides the user interface.

The Client manages MCP communication.

---

### Mistake 2

Thinking the Client executes tools.

The Server executes tools.

The Client only sends requests and receives responses.

---

### Mistake 3

Assuming one Server can expose only one tool.

An MCP Server can expose many tools, resources, and prompts.

---

### Mistake 4

Connecting directly to external APIs from the Host.

Communication should flow through the MCP Client and MCP Server.

---

### Mistake 5

Assuming a single Client instance handles every connected Server.

In practice, a Host manages one Client per Server connection. Treating this as a single shared client can lead to confused state management — for example, mixing up which capabilities belong to which server once more than one is connected.

# Interview Tip

A common interview question is:

> **Explain the architecture of MCP.**

A good answer is:

MCP follows a client-server architecture. The Host provides the user interface, the MCP Client manages communication, and the MCP Server exposes tools, resources, and prompts. Communication occurs through standardized JSON-RPC messages, allowing AI Agents to interact with external systems in a consistent and reusable way.

A stronger follow-up, if asked for more depth, is to mention the **initialization handshake** (protocol version and capability negotiation before any tool calls happen) and the **1:1 Client-to-Server pairing** — a Host manages a separate Client instance for each Server it's connected to, which is part of why adding or removing a server doesn't disturb existing connections.

# Key Takeaways

- MCP follows a modular client-server architecture built on separation of concerns.
- The three core components are the Host, Client, and Server.
- A Host typically manages one Client per connected Server.
- Every session begins with an initialization handshake negotiating protocol version and capabilities.
- MCP Clients communicate with MCP Servers using standardized JSON-RPC messages.
- MCP Servers expose tools (actions), resources (readable data), and prompts (reusable templates) — each with a distinct purpose.
- The modular architecture enables reusable integrations, independent security boundaries, and simplifies AI application development.
