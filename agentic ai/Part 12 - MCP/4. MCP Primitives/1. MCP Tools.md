# Introduction

Imagine an AI Assistant receives the following request:

```text
What's the weather in Mumbai today?
```

The AI model itself doesn't know the current weather.

Instead, it decides to use an external capability.

It calls:

```text
Weather Tool
```

The Tool contacts a weather service,

retrieves the latest forecast,

and returns the result to the AI Agent.

This external capability is called an **MCP Tool**.

---

# What is an MCP Tool?

An MCP Tool is a callable function exposed by an MCP Server that allows an AI Agent to perform an action or retrieve dynamic information.

Unlike the AI model,

a Tool can interact with the outside world.

Examples include:

- Search the web
- Send an email
- Query a database
- Read GitHub issues
- Create a Jira ticket
- Check today's weather

---

# Why Do We Need Tools?

LLMs have limitations.

They cannot:

- Access live information
- Modify external systems
- Execute business logic
- Perform real-world actions

Tools extend the capabilities of an AI Agent.

Instead of relying only on its internal knowledge,

the Agent can interact with external systems.

# Tool Annotations (Safety Hints)

Not all Tools carry the same level of risk. MCP lets a Server attach **annotations** to a Tool that describe its behavior, so Clients and Agents can treat it appropriately.

```python
@server.tool(
    read_only_hint=True,     # Does not modify anything
    destructive_hint=False,  # Cannot cause irreversible damage
    idempotent_hint=True     # Calling it twice has the same effect as once
)
def get_weather(city: str):
    return f"The weather in {city} is sunny."
```

|Annotation|Meaning|
|---|---|
|`read_only_hint`|Tool only reads data, never modifies anything|
|`destructive_hint`|Tool can cause irreversible changes (e.g., delete data)|
|`idempotent_hint`|Calling it multiple times has the same effect as calling it once|

Clients can use these hints to decide things like: skip confirmation for read-only tools, but require explicit user approval before running a destructive one.

# Structured Error Responses

When a Tool fails, it shouldn't just crash — it should return a structured error the Agent can reason about.

```python
@server.tool()
def send_email(to: str, subject: str, body: str):
    if "@" not in to:
        return {
            "isError": True,
            "content": [{"type": "text", "text": "Invalid email address."}]
        }
    ...
```

Returning a consistent `isError` field (rather than throwing an unhandled exception) lets the Agent distinguish between "the tool ran and found a problem" versus "the tool itself is broken" — and decide whether to retry, ask the user, or try a different approach.

# Human-in-the-Loop for Risky Tools

For Tools marked as destructive or high-impact (e.g., `delete_database`, `send_payment`), it's common practice to require explicit human confirmation before execution, rather than letting the Agent call them autonomously.

```text
Agent wants to call: delete_customer_record
↓
destructive_hint = True
↓
Pause → Ask user: "Confirm deletion of customer #4521?"
↓
User approves → Tool executes
```

This pattern connects directly to Human-in-the-Loop practices used more broadly in Agent safety — the more irreversible an action, the more important it is to keep a human in the approval path.

# Tools vs Resources vs Prompts

These MCP primitives serve different purposes.

|Primitive|Purpose|
|---|---|
|Tool|Performs an action or computation|
|Resource|Provides data or content|
|Prompt|Provides reusable instructions for the AI model|

Think of them this way:

- **Tool** → _Do something._
- **Resource** → _Read something._
- **Prompt** → _Guide the model._

We'll study Resources and Prompts in the next chapters.

# Tool Naming Conventions

Clear, consistent naming helps both developers and the LLM choose the right Tool.

```text
Good:  get_weather, search_repository, create_issue, delete_user
Avoid: doStuff, tool1, handleRequest
```

A common convention is `verb_noun` (e.g., `search_flights`, `send_email`) — the verb signals the action, and the noun signals what it acts on. This also makes destructive operations easier to spot at a glance (`delete_...`, `remove_...`).

---

# Least-Privilege Tool Design

Every Tool a Server exposes is a capability the connected Agent can use — so each one should only grant the minimum access needed for its purpose.

```text
Bad:  execute_sql(query: str)          → Agent can run ANY SQL, including DROP TABLE
Better: get_customer_by_id(id: str)    → Agent can only read one specific record type
```

Exposing a narrow, purpose-built Tool instead of a broad, general-purpose one significantly reduces the damage a misbehaving or manipulated Agent could cause — this is the same least-privilege principle used in traditional software security.

# Best Practices

Design each Tool for a single responsibility.

Use clear and descriptive Tool names, following a consistent verb_noun convention.

Validate all input parameters.

Return structured and predictable outputs, including structured errors.

Handle errors gracefully.

Annotate Tools with read-only/destructive/idempotent hints where supported.

Require human confirmation for destructive or high-impact Tools.

Apply least-privilege design — expose narrow, purpose-built Tools rather than broad ones.

Avoid exposing unsafe or unnecessary operations.

---

# Common Beginner Mistakes

### Mistake 1

Creating one Tool that performs many unrelated tasks.

Prefer small, focused Tools.

---

### Mistake 2

Returning unstructured responses.

Tools should return data that the Agent can interpret reliably.

---

### Mistake 3

Skipping input validation.

Always validate arguments before executing the Tool.

---

### Mistake 4

Confusing Tools with Resources.

Tools perform actions.

Resources provide data.

---

### Mistake 5

Exposing an overly broad Tool (like raw SQL execution) instead of narrow, specific ones.

This gives the Agent far more power than the task actually requires.

---

### Mistake 6

Letting destructive Tools execute without any human confirmation step.

Irreversible actions deserve a checkpoint, not full autonomy by default.

# Interview Tip

A common interview question is:

> **What is an MCP Tool?**

A good answer is:

An MCP Tool is a callable capability exposed by an MCP Server that allows an AI Agent to perform actions or retrieve dynamic information. The Agent invokes the Tool through the MCP protocol, the Tool executes the requested operation and returns a structured result (or structured error), and the Agent uses that outcome for further reasoning. Tools can be annotated as read-only, destructive, or idempotent so Clients know when extra caution — like human confirmation — is warranted.

# Key Takeaways

- MCP Tools allow AI Agents to perform actions and access external systems.
- Tools are callable functions exposed by an MCP Server.
- The AI model decides when to use a Tool; the Tool performs the actual work.
- Tool annotations (read-only, destructive, idempotent) communicate risk level to the Client.
- Structured error responses let the Agent distinguish tool failures from tool-detected problems.
- Destructive or high-impact Tools should require human confirmation before executing.
- Clear naming conventions and least-privilege design make Tools safer and easier to use correctly.
- Tools extend the capabilities of AI Agents beyond the model's built-in knowledge.
- Well-designed Tools are focused, reusable, and secure.
