# Introduction

Imagine an MCP Server is helping an AI Agent analyze a software project.

The Server needs a summary of a large source file before it can continue.

Can the Server generate the summary itself?

No.

The MCP Server is **not** an AI model.

Instead,

it asks the **Client** to have the AI model generate the summary.

The Client sends the request to the LLM,

receives the generated text,

and returns it to the Server.

This process is called **MCP Sampling**.

---

# What is MCP Sampling?

MCP Sampling is a capability that allows an MCP Server to request an AI-generated completion from the Client's language model.

Instead of containing its own AI model,

the Server delegates text generation to the Client.

The Client performs the LLM call and returns the result.

---

# Why Do We Need Sampling?

An MCP Server may occasionally require AI reasoning while executing a task.

Examples include:

- Summarizing a document
- Explaining source code
- Translating text
- Classifying content
- Generating structured output

Rather than embedding its own LLM,

the Server asks the Client to use the model that is already available.

# Why Doesn't the Server Call the LLM Directly?

Keeping the LLM inside the Client provides several benefits.

- One AI model can serve many Servers.
- Authentication remains centralized.
- The Server remains lightweight.
- Different Clients can use different AI models.

This keeps responsibilities clearly separated.

# The Sampling Request Structure

A Sampling request isn't just a raw string — it's a structured message that gives the Client (and its LLM) everything needed to generate a good response.

```json
{
  "messages": [
    { "role": "user", "content": "Summarize this Python file: ..." }
  ],
  "systemPrompt": "You are a concise technical writer.",
  "maxTokens": 300,
  "modelPreferences": {
    "hints": [{ "name": "claude-3-sonnet" }],
    "intelligencePriority": 0.8,
    "speedPriority": 0.3
  },
  "includeContext": "thisServer"
}
```

Key fields:

- **messages** — the conversation content to send to the LLM
- **systemPrompt** — optional instructions shaping the model's behavior
- **maxTokens** — limits response length (connects to Chapter 39's latency/cost trade-offs)
- **modelPreferences** — hints about what kind of model to use
- **includeContext** — how much surrounding context to include

---

# Model Preferences

Since the Server doesn't control which model the Client uses, it can only express **preferences**, not a hard requirement — leaving the final choice to the Client.

|Field|Meaning|
|---|---|
|`hints`|Suggested model names, treated as soft hints, not guarantees|
|`costPriority`|How much to prioritize a cheaper model (0–1)|
|`speedPriority`|How much to prioritize a faster model (0–1)|
|`intelligencePriority`|How much to prioritize a more capable model (0–1)|

```text
Server: "I'd like a fast, cheap model — this is a simple classification task."
↓
Client: Honors preference where possible, but may substitute based on what's available
```

This mirrors the cost vs accuracy trade-off from Chapter 38 — the Server can signal what matters for this particular request, while the Client retains control.

---

# Context Inclusion Options

The `includeContext` field controls how much of the surrounding conversation or session the Client shares with the LLM for this Sampling request.

|Value|Meaning|
|---|---|
|`none`|Only the explicit messages in the request are sent|
|`thisServer`|Include context relevant to the requesting Server|
|`allServers`|Include context from all connected Servers|

```text
includeContext: "none"       → Minimal, isolated request
includeContext: "thisServer" → Server's own conversation context included
includeContext: "allServers" → Broader context, higher risk of leaking unrelated data
```

Choosing the narrowest scope that still gets the job done keeps requests efficient and reduces the chance of unrelated or sensitive context leaking into a response.

# Human-in-the-Loop Review of Sampling Requests

Because a Server is asking the Client's LLM (running on the user's behalf, often with the user's credentials and context) to generate content, most Clients are designed to let a human review the request — and sometimes the response — before it's sent or returned.

```text
Server sends Sampling Request
↓
Client shows user: "This Server wants to generate: [prompt preview]"
↓
User approves or denies
↓
If approved → LLM generates response
↓
Client may show the response to the user before returning it to the Server
```

This human-in-the-loop step (the same pattern discussed for destructive Tools in Chapter 74) prevents a Server from silently using the user's LLM access for unexpected or unwanted purposes.

# Sampling vs Tools

Although both involve communication,

their purposes are different.

|Tool|Sampling|
|---|---|
|Executes an external operation|Requests AI-generated text|
|May call APIs or databases|Uses the Client's language model|
|Returns external data|Returns generated content|

Think of them this way:

- **Tool** → _Interact with the outside world._
- **Sampling** → _Ask the LLM to reason or generate text._

---

# Security Considerations for Sampling

Because Sampling lets a Server effectively "borrow" the user's LLM access, it introduces some risks worth guarding against:

- **Prompt injection toward the user's model** — a malicious or compromised Server could try to craft a Sampling request that manipulates the LLM into producing harmful or misleading content
- **Context leakage** — requesting `includeContext: "allServers"` unnecessarily could expose data from unrelated Servers into a single generation request
- **Unbounded cost** — a Server could request very large or very frequent completions, running up cost on the user's account

Mitigations:

- Always route Sampling requests through human approval for anything non-trivial
- Default to the narrowest `includeContext` that satisfies the task
- Apply rate limits and `maxTokens` caps on Sampling requests, just as you would for any LLM call (Chapter 38)

# Best Practices

Request Sampling only when AI reasoning is required.

Keep Sampling prompts focused and concise.

Do not use Sampling when a simple Tool or Resource is sufficient.

Design Servers to remain independent of any specific LLM — treat model preferences as hints, not requirements.

Use the narrowest `includeContext` scope needed for the task.

Expect and support human review before a Sampling request is fulfilled.

Handle failed or denied Sampling requests gracefully.

# Common Beginner Mistakes

### Mistake 1

Thinking the MCP Server contains an LLM.

The Client owns the language model.

---

### Mistake 2

Using Sampling for simple calculations or data retrieval.

Use Tools or Resources when AI reasoning is unnecessary.

---

### Mistake 3

Assuming every Client supports Sampling.

Clients advertise supported capabilities during capability negotiation.

---

### Mistake 4

Tightly coupling the Server to a specific model.

Servers should remain model-agnostic.

---

### Mistake 5

Requesting broad context (`allServers`) by default.

This unnecessarily increases the risk of leaking unrelated data into a single generation.

---

### Mistake 6

Assuming Sampling requests always execute without oversight.

Well-behaved Clients route non-trivial Sampling requests through human approval before calling the LLM.

# Interview Tip

A common interview question is:

> **What is MCP Sampling?**

A good answer is:

MCP Sampling allows an MCP Server to request AI-generated output from the Client's language model. The request includes structured fields like messages, model preferences, and context scope, and the Client — often after human approval — performs the LLM call and returns the generated result. This keeps the Server independent of any specific AI model while giving the Client control over cost, scope, and oversight.

# Key Takeaways

- MCP Sampling allows a Server to request AI-generated output from the Client.
- The Client owns the language model and performs the LLM call.
- A Sampling request is structured: messages, system prompt, token limits, model preferences, and context scope.
- Model preferences are hints (cost/speed/intelligence priority), not guarantees — the Client decides.
- `includeContext` controls how much surrounding context is shared, with narrower scopes being safer.
- Human-in-the-loop review protects users from unexpected or unwanted LLM usage by a Server.
- Sampling introduces security considerations: prompt injection, context leakage, and cost risk.
- Servers remain lightweight and model-independent.
- Sampling complements Tools, Resources, and Prompts within the MCP ecosystem.
