# Introduction

Imagine an AI Assistant receives the request:

```text
Summarize the company's Leave Policy.
```

The Agent doesn't need to perform an action.

It simply needs to **read a document**.

The document might be stored in:

- A file
- A database
- A knowledge base
- A company wiki

Instead of calling a Tool,

the Agent reads an **MCP Resource**.

Resources provide information.

They do not perform actions.

---

# What is an MCP Resource?

An MCP Resource is a piece of data or content exposed by an MCP Server that an AI Agent can read.

Resources are designed to provide information,

not perform operations.

Examples include:

- Documents
- Files
- Database records
- Configuration files
- Knowledge Base articles
- API documentation

---

# Why Do We Need Resources?

Not every AI task requires executing a Tool.

Sometimes,

the Agent simply needs information.

Examples:

```text

```

Using a Tool for these tasks would be unnecessary.

Resources provide a simpler and more efficient way to access information.

# Resources vs Tools

Although both are MCP primitives,

they serve different purposes.

| Tool | Resource |
|------|----------|
| Performs an action | Provides information |
| May change external systems | Read-only content |
| Executes logic | Returns data |

Think of them this way:

- **Tool** → *Do something.*
- **Resource** → *Read something.*

# Resource Identifiers

Each Resource typically has a unique identifier.

Example

```text
company://policies/leave

docs://api/authentication

file://README.md
```

The Client requests a Resource using its identifier,

and the Server returns the associated content.

---

# Listing and Discovering Resources

Before reading a specific Resource, a Client typically asks the Server what's available.

```text
Client → resources/list → Server
Server → [
    { "uri": "company://policies/leave", "name": "Leave Policy" },
    { "uri": "company://policies/conduct", "name": "Code of Conduct" }
  ]
```

```python
resources = await session.list_resources()
for r in resources.resources:
    print(r.uri, r.name)
```

This discovery step lets a Client (or the LLM behind it) know what information is available before deciding what to read — similar to how `list_tools()` works for Tools.

# Resource Templates (Dynamic/Parameterized Resources)

Some Resources aren't fixed documents — they represent a *pattern* of resources, parameterized by an identifier supplied at read-time.

```python
@server.resource("company://employee/{employee_id}/profile")
def employee_profile(employee_id: str):
    return get_profile_from_db(employee_id)
```

```text
Template: company://employee/{employee_id}/profile
↓
Client requests: company://employee/4521/profile
↓
Server returns: profile data for employee 4521
```

This lets a single Resource definition serve many concrete instances (one per employee, one per document, one per record) instead of manually registering a separate Resource for every item.

---

# Resource Subscriptions (Change Notifications)

Some Resources change over time — a policy gets updated, a report gets regenerated. Rather than the Client repeatedly re-reading a Resource to check for changes, MCP supports **subscriptions**.

```text
Client subscribes to: company://policies/leave
↓
Policy document is updated on the Server
↓
Server sends notification: resources/updated
↓
Client re-reads the Resource to get the latest content
```

```python
await session.subscribe_resource("company://policies/leave")
```

This is useful for long-running Agents that should stay aware of changing information without constantly polling for updates.

# MIME Types and Binary Resources

Resources aren't limited to plain text — a Resource has a MIME type that tells the Client how to interpret its content.

```python
@server.resource("company://logo.png")
def company_logo():
    return {
        "mimeType": "image/png",
        "blob": read_file_as_base64("logo.png")
    }
```

| MIME Type | Example Content |
|-----------|------------------|
| `text/plain` | Plain documents, policies |
| `text/markdown` | README files, formatted docs |
| `application/json` | Structured data records |
| `image/png`, `application/pdf` | Binary content (images, PDFs) |

Text-based Resources are returned as plain content; binary Resources are typically base64-encoded so they can travel safely over JSON-RPC.

# Read-Only Nature

Resources are generally read-only.

For example,

an Agent can:

- Read a policy
- Read a document
- Read a configuration

But modifying those items usually requires a Tool.

This separation improves security and clarity.

---

# Caching Resources

Since Resources are read-only and sometimes expensive to generate (e.g., querying a large report), Clients or Servers can cache their content to avoid redundant work.

```text
First Read:  Fetch from database → Cache result → Return to Client
Second Read: Return cached result directly (fast)
```

When combined with subscriptions, a cache can safely stay valid until a `resources/updated` notification arrives, invalidating it only when the underlying content actually changes.

# Best Practices

Keep Resources read-only whenever possible.

Use meaningful and consistent identifiers.

Organize Resources logically.

Return structured content when appropriate, with the correct MIME type.

Use Resource Templates instead of registering many near-identical Resources manually.

Subscribe to Resources that change, rather than polling repeatedly.

Cache expensive Resources, invalidating on update notifications.

Avoid exposing sensitive information without proper authorization.

---

# Common Beginner Mistakes

### Mistake 1

Using a Tool when a Resource is sufficient.

If the Agent only needs to read information,

use a Resource.

---

### Mistake 2

Allowing Resources to modify data.

Resources should provide information,

not perform actions.

---

### Mistake 3

Using unclear Resource identifiers.

Choose identifiers that are descriptive and easy to understand.

---

### Mistake 4

Exposing confidential documents without access control.

Protect sensitive Resources using proper authentication and authorization.

---

### Mistake 5

Registering a separate Resource for every record instead of using a Resource Template.

This doesn't scale — a parameterized template handles all instances with one definition.

---

### Mistake 6

Polling a Resource repeatedly to check for changes instead of subscribing.

This wastes requests when the Server can simply notify the Client when content changes.

# Interview Tip

A common interview question is:

> **What is the difference between an MCP Tool and an MCP Resource?**

A good answer is:

An MCP Tool performs an action or computation, such as sending an email or querying a database. An MCP Resource provides read-only information, such as documents, files, or knowledge base articles, and can be discovered via listing, parameterized via templates for dynamic content, and kept fresh via subscriptions instead of polling. Tools execute operations, while Resources expose content.

# Key Takeaways

- MCP Resources provide read-only information to AI Agents.
- Resources expose documents, files, records, and other content.
- Clients discover Resources via listing and can read them by URI.
- Resource Templates let one definition serve many parameterized instances.
- Subscriptions let Clients stay updated on changes without polling.
- MIME types let Resources carry both text and binary content (images, PDFs, JSON).
- Caching reduces redundant work for expensive-to-generate Resources.
- Resources do not perform actions or modify systems.
- They complement Tools by supplying information for reasoning.
- Well-designed Resources are organized, secure, and easy to discover.
