# Introduction

Imagine an AI Assistant receives the request:

```text

```

Instead of writing this prompt every time,

This ensures every code review follows the same high-quality instructions.

---

# What is an MCP Prompt?

An MCP Prompt is a reusable prompt template exposed by an MCP Server that provides structured instructions to an AI model.

Unlike a Tool,

a Prompt does not perform an action.

Unlike a Resource,

a Prompt is not simply data.

Its purpose is to guide the model's behavior.

---

# Why Do We Need Prompts?

Many AI tasks require carefully engineered instructions.

Examples include:

- Code Review
- Email Writing
- Document Summarization
- SQL Generation
- Translation
- Customer Support

Instead of embedding these instructions inside every application,

they can be stored as reusable MCP Prompts.

# Prompt vs Tool vs Resource

These three MCP primitives serve different purposes.

|Primitive|Purpose|
|---|---|
|Tool|Performs an action|
|Resource|Provides information|
|Prompt|Provides reusable instructions|

Think of them as:

- **Tool** → _Do something._
- **Resource** → _Read something._
- **Prompt** → _Think this way._

# Listing Prompts

Just like Tools and Resources, Clients can ask a Server what Prompts are available before using one.

```python
prompts = await session.list_prompts()
for p in prompts.prompts:
    print(p.name, p.description)
```

```text
Client → prompts/list → Server
Server → [
    { "name": "code_review", "description": "Reviews code for bugs and security issues" },
    { "name": "summarize_document", "description": "Summarizes a document with adjustable length" }
  ]
```

This lets a Client (or a human user, in tools like Claude Desktop) browse what reusable instructions are available before picking one.

# Prompt Arguments and Schemas

Like Tool inputs, a Prompt's arguments are typically declared with a schema, so the Client knows exactly what to supply and can validate it before sending.

```python
@server.prompt()
def summarize_document(document: str, max_words: int = 200):
    """
    Summarize the given document.
    Arguments:
        document: The full text to summarize.
        max_words: Maximum length of the summary.
    """
    return f"Summarize the following document in under {max_words} words:\n\n{document}"
```

```text
Prompt: summarize_document
Arguments:
  - document (required, string)
  - max_words (optional, integer, default 200)
```

Declaring arguments explicitly (rather than expecting free-form text) keeps Prompts predictable and easy to validate, the same way Chapter 41's template variables did for application-level prompt templates.

# Multi-Message Prompts

A Prompt doesn't have to return a single block of text — it can return a structured sequence of messages with roles, similar to a chat conversation.

```python
@server.prompt()
def code_review(code: str):
    return [
        {"role": "system", "content": "You are a senior software engineer performing a code review."},
        {"role": "user", "content": f"Review this code for bugs, security issues, and performance:\n\n{code}"}
    ]
```

```text
Rendered Prompt:
System: You are a senior software engineer performing a code review.
User:   Review this code for bugs, security issues, and performance: ...
```

This mirrors the system/user role structure covered in Chapter 41 — MCP Prompts can define not just _what_ to say, but _how_ the conversation should be framed for the model.

# Embedding Resources in Prompts

A Prompt can reference or embed a Resource directly, so the Client doesn't need to separately fetch and stitch together content.

```python
@server.prompt()
def review_against_policy(code: str):
    policy = read_resource("company://policies/secure-coding")
    return [
        {"role": "system", "content": f"Company Secure Coding Policy:\n{policy}"},
        {"role": "user", "content": f"Review this code against the policy:\n\n{code}"}
    ]
```

This combines two MCP primitives — a Prompt pulling in a Resource — to produce a single, ready-to-use instruction set grounded in the organization's actual documentation.

# Prompts as Slash Commands

In Client applications like Claude Desktop, MCP Prompts are often surfaced directly to the user as slash commands.

```text

↓

↓

```

This turns a curated, well-engineered Prompt into something a non-technical user can trigger with a simple command, without needing to know how the underlying instructions are written.

# Why Not Hardcode Prompts?

Without MCP,

developers often write prompts directly inside application code.

```python
prompt = "Review this code..."
```

This creates problems:

- Difficult to update
- Hard to reuse
- Duplicate prompts across projects

MCP Prompts solve this by centralizing prompt templates.

# Governance and Versioning in Practice

Because centralized Prompts are used across many teams and applications, changing one has a wide blast radius. Mature organizations apply the same discipline from Chapter 40 (Prompt Versioning) at the MCP Server level:

```text
code_review v1.0 → in production across 5 apps
↓
Propose code_review v1.1 (adds security checklist)
↓
Evaluate against golden dataset
↓
Roll out gradually, monitor for regressions
↓
Promote to default
```

Treating server-hosted Prompts as versioned, tested assets — not just editable text — prevents an update meant for one team from silently breaking another team's workflow.

# Best Practices

Create Prompts for reusable tasks.

Keep instructions clear and specific.

Use parameters instead of hardcoding values, with a declared argument schema.

Use multi-message structure (system/user roles) for more precise control over model behavior.

Embed Resources into Prompts when grounding instructions in live documentation.

Version important Prompts and evaluate changes before rollout.

Review Prompt quality regularly.

# Common Beginner Mistakes

### Mistake 1

Using a Prompt when a Tool is needed.

Prompts guide the model.

They do not perform external actions.

---

### Mistake 2

Embedding every Prompt directly in application code.

Reusable prompts belong in MCP Servers.

---

### Mistake 3

Creating overly broad Prompts.

Each Prompt should solve one well-defined task.

---

### Mistake 4

Duplicating the same Prompt across multiple projects.

Centralized Prompts improve consistency and maintainability.

---

### Mistake 5

Leaving Prompt arguments undeclared or unvalidated.

This makes Prompts error-prone and harder for Clients to use correctly.

---

### Mistake 6

Editing a shared Prompt in place without versioning or testing.

A change meant to help one team can silently break another team's workflow that depends on the same Prompt.

# Interview Tip

A common interview question is:

> **What is an MCP Prompt?**

A good answer is:

An MCP Prompt is a reusable prompt template exposed by an MCP Server. It provides structured instructions — often as a multi-message, role-based sequence with declared arguments — that guide an AI model's behavior for common tasks such as summarization, code review, or document generation. Prompts can also embed Resources for grounding. Unlike Tools, Prompts do not perform actions, and unlike Resources, they provide instructions rather than raw information.
