# Introduction

Imagine an AI Agent connects to a Company HR MCP Server.

The Agent requests:

```text
Read Employee Salaries
```

Should the Server immediately return the data?

No.

Before granting access, the Server must answer two questions:

1. **Who is requesting access?**
2. **What are they allowed to access?**

The first question is answered through **Authentication**.

The second is answered through **Authorization**.

Together, they protect MCP Servers from unauthorized access.

---

# What is Authentication?

Authentication is the process of verifying the identity of a Client before allowing it to access an MCP Server.

Authentication answers the question:

> **Who are you?**

Examples include:

- Username and Password
- API Key
- OAuth Token
- JWT Token
- Client Certificate

Only authenticated Clients can establish trusted communication.

---

# This Is Where the "Enforced Permission" Idea Becomes Concrete

This chapter is a direct, concrete realization of a point made back in the Agent Permissions chapter — worth connecting explicitly.

Recall: a prompted restriction ("don't do X" in a system prompt) is not real security, because it relies on the model choosing to comply. Real security is a permission check enforced in application code, before execution, regardless of what the model requests.

Authentication and Authorization, as covered in this chapter, **are** that enforcement layer, specifically for MCP:

```text
"The model shouldn't request this action" → a prompted preference
"The Server verifies who's asking, and blocks it if unauthorized"
                                            → an ENFORCED boundary,
                                              exactly the kind the
                                              Agent Permissions
                                              chapter argued for
```

So when this chapter describes checking identity and permissions "before executing a sensitive operation," that's not a new idea — it's the actual implementation of the enforced-permission principle introduced earlier, specifically at the MCP protocol/Server level.

---

# What is Authorization?

Authorization determines what an authenticated Client is allowed to do.

Authorization answers the question:

> **What are you allowed to access?**

Examples include:

- Call Tools
- Read Resources
- Write Resources
- Access Sensitive Data
- Execute Administrative Operations

A Client may be authenticated but still not have permission to perform every action.

---

# Authentication vs Authorization

Although closely related,

they solve different problems.

|Authentication|Authorization|
|---|---|
|Verifies identity|Determines permissions|
|Answers "Who are you?"|Answers "What can you do?"|
|Happens first|Happens after authentication|

Think of entering an office building.

Authentication checks your identity card.

Authorization determines which rooms you may enter.

# Does Authentication Matter Equally for Every Transport?

This connects back to the MCP Transports chapter's point that each transport implies a different trust boundary — worth applying that specifically to authentication here.

```text
stdio (local process)
→ The Server runs as a local process, typically launched directly
  by the Host, already running under the same user's OS-level
  permissions
→ Formal authentication (API keys, OAuth) is often unnecessary
  here, since the operating system itself is already the trust
  boundary — if you can launch the process, you're implicitly
  "authenticated" by virtue of having access to the machine

Streamable HTTP (remote)
→ The Server is reachable over a network, potentially by anyone
  who can reach that network endpoint
→ Formal authentication becomes essential — without it, there's
  no way to distinguish a legitimate Client from anyone else
  who discovers the URL
```

This is why authentication discussions in MCP overwhelmingly focus on the remote/HTTP case — it's not that local stdio Servers have no security considerations at all (Least-Privilege on OS permissions still matters, per the Transports chapter), it's that _authentication specifically_ (verifying "who is this Client") is a much smaller concern when the trust boundary is already "whoever has access to this machine."

# Common Authentication Methods

## 1. API Keys

The Client sends a secret API key.

Simple to implement,

but suitable only for trusted environments.

---

## 2. OAuth

The Client authenticates using an OAuth provider.

Common for services such as:

- Google
- GitHub
- Microsoft

OAuth allows secure delegated access without sharing passwords.

---

## 3. JWT (JSON Web Tokens)

The Client sends a signed token containing identity information.

The Server validates the token before accepting requests.

JWT is widely used in enterprise applications.

---

## 4. Mutual TLS (mTLS)

Both the Client and the Server verify each other's certificates.

This provides strong authentication,

especially in enterprise environments.

# Token Passthrough: A Real, Documented MCP Anti-Pattern

This is a specific, concrete security failure worth knowing by name, since it directly connects the OAuth/token concepts above to the confused-deputy problem raised in the Least-Privilege chapter.

**Token passthrough** happens when an MCP Server, instead of validating a Client's token and using its own credentials to call an upstream service, simply forwards the Client's token directly to that upstream API without proper validation.

```text
Risky pattern (token passthrough):

Client's OAuth token (scoped for THIS MCP Server)
     ↓ forwarded as-is, unchecked
Upstream API — which may accept the token even though it
               wasn't actually intended for this use, if the
               token's audience/scope isn't properly verified
```

Why this is dangerous: OAuth tokens are typically issued for a specific intended recipient (the "audience"). If an MCP Server blindly passes a Client's token through to another service without confirming that token was actually meant to be used that way, it can enable exactly the confused-deputy scenario described earlier — a token intended for one narrow purpose ends up granting broader access than intended, because a component in the middle didn't enforce its own validation and just forwarded trust it didn't verify.

The safer pattern:

```text
Client authenticates to the MCP Server directly
     ↓
MCP Server validates the token IS actually meant for it
  (checks the token's audience/scope)
     ↓
MCP Server uses ITS OWN separate, properly-scoped credentials
  to call any upstream service, rather than forwarding the
  Client's token onward unchanged
```

This is a specific enough issue that it's called out directly in MCP security guidance — worth knowing by name if you're asked about MCP-specific (rather than generic) security concerns in an interview.

# Authorization Models

After authentication,

the Server decides which operations are permitted.

Common models include:

### Role-Based Access Control (RBAC)

Permissions are assigned based on roles.

Example

```text
Administrator

↓

Read

Write

Delete

--------------------

Viewer

↓

Read Only
```

---

### Attribute-Based Access Control (ABAC)

Permissions depend on attributes such as:

- Department
- Project
- Location
- Time
- Device

This allows more fine-grained control.

---

### Least-Privilege Access

Clients receive only the permissions required for their current task.

For example,

a documentation Agent may need:

- Read Repository

but not:

- Delete Repository

This minimizes security risks.

---

# Authentication & Authorization Workflow

```text
Client Connects

↓

Authenticate Client

↓

Verify Identity

↓

↓

```

Requests that fail authentication or authorization are rejected.

# Python Example

A simplified authorization check:

```python
user_role = "viewer"

    print("Delete allowed.")
else:
    print("Permission denied.")
```

Production MCP Servers use identity providers,

tokens,

and policy engines rather than simple role checks.

# Best Practices

Authenticate every Client.

Authorize every request.

Apply the Principle of Least Privilege.

Never trust unauthenticated connections.

Use secure token-based authentication.

Audit authentication failures and permission changes.

Validate a token's intended audience before using it — never blindly forward a Client's token to an upstream service (avoid the token passthrough anti-pattern).

Match authentication rigor to the transport's actual trust boundary — remote HTTP Servers need it far more critically than local stdio Servers.

# Common Beginner Mistakes

### Mistake 1

Thinking authentication automatically grants full access.

Authentication verifies identity.

Authorization determines permissions.

---

### Mistake 2

Using hardcoded credentials.

Use secure identity providers or secret management systems.

---

### Mistake 3

Granting excessive permissions.

Follow the Principle of Least Privilege.

---

### Mistake 4

Checking authorization only once.

Permission checks should occur whenever a sensitive operation is requested.

---

### Mistake 5

Blindly forwarding a Client's token to an upstream API without validating its intended audience or scope.

This is the token passthrough anti-pattern, and it can lead to a confused-deputy-style privilege escalation.

---

### Mistake 6

Treating authentication requirements identically across every transport, without considering that a local stdio Server's trust boundary is fundamentally different from a remote HTTP Server's.

# Interview Tip

A common interview question is:

> **What is the difference between Authentication and Authorization in MCP?**

A good answer is:

Authentication verifies the identity of an MCP Client, answering "Who are you?" Authorization determines what that authenticated Client is allowed to do, answering "What are you allowed to access?" Production MCP Servers require both before allowing access to tools, resources, or other capabilities.

---

# Interview Tip

A stronger follow-up worth preparing for:

> **What is "token passthrough" in MCP, and why is it a security risk?**

Answer:

Token passthrough is when an MCP Server forwards a Client's authentication token directly to an upstream service without validating that the token was actually intended for that use — instead of validating the token itself and using its own properly-scoped credentials for upstream calls. This can allow a token scoped for one narrow purpose to grant broader, unintended access further downstream, which is a specific instance of the confused-deputy problem: a component in the middle passes along trust it never actually verified.

# Key Takeaways

- Authentication verifies a Client's identity.
- Authorization determines the Client's permissions — and is the concrete, MCP-level implementation of the "enforced, not prompted" permission principle from the Agent Permissions chapter.
- Authentication always occurs before Authorization.
- Authentication matters most for remote/HTTP Servers; local stdio Servers rely more on the OS itself as the trust boundary.
- Token passthrough — forwarding a Client's token to an upstream service without validating it — is a real, documented MCP anti-pattern connected to the confused-deputy problem.
- Common authentication methods include API Keys, OAuth, JWT, and mTLS.
- Secure MCP Servers enforce both Authentication and Authorization for every sensitive operation.
