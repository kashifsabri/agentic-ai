# Introduction

Imagine you're using an AI Coding Assistant on your laptop.

The Agent needs to:

- Read local files
- Search your Git repository
- Execute local commands

Since everything is already on your computer,

it makes sense for the MCP Server to run locally.

Now imagine an Enterprise AI Assistant.

Thousands of employees use it simultaneously.

The Agent needs access to:

- Company databases
- CRM systems
- Cloud storage
- Internal APIs

Running an MCP Server on every employee's computer would be impractical.

Instead,

the MCP Server runs centrally in the cloud.

This introduces two deployment models:

- Local MCP Servers
- Remote MCP Servers

---

# What is a Local MCP Server?

A Local MCP Server runs on the same machine as the MCP Host or Client.

Communication typically occurs through:

- stdio
- Local IPC
- Local network interfaces

No internet connection is required for communication.

---

# Deployment Decision vs Transport Decision — Two Layers, Not One

This chapter maps almost directly onto the earlier MCP Transports chapter (Local ≈ stdio, Remote ≈ Streamable HTTP), which makes sense — but it's worth being precise that these are technically **two separate decisions** that happen to usually go together, not one and the same choice.

```text
Deployment decision (this chapter)
→ WHERE does the Server's process actually run — on this machine,
  or somewhere else entirely?

Transport decision (earlier chapter)
→ HOW do messages physically travel between Client and Server,
  given where the Server runs
```

In the overwhelming majority of real setups, these correlate tightly: a Server running locally uses stdio, and a Server running remotely uses HTTP-based transport — which is exactly why this chapter and the Transports chapter feel so similar. But it's worth knowing they're not strictly the same axis: you could, in principle, run a Server on a remote machine and still expose it over something other than the "typical" mapping, or run multiple local Servers that communicate over local network interfaces rather than stdio (as the chapter itself briefly notes). The practical guidance ("local → stdio, remote → HTTP") holds almost all the time, but understanding _why_ it holds — because deployment location constrains which transports even make sense — is the more transferable interview-level insight than just memorizing the pairing.

# The Operational Cost Tradeoff That's Easy to Miss

The comparison so far focuses on latency, scalability, and access — worth adding the dimension of ongoing operational cost and responsibility, since it's often what actually decides this in a real organization.

```text
Local MCP Server
→ Zero hosting cost — it runs on hardware the user already owns
→ But: no operator to monitor it, patch it, or ensure uptime;
  reliability is whatever the individual user's machine provides
→ Updates require the user to update their own installation

Remote MCP Server
→ Real ongoing cost: compute, storage, monitoring, on-call/SRE
  time, scaling infrastructure
→ In exchange: centralized control — one update reaches every
  user immediately, uptime can be actively monitored and improved,
  and someone is actually responsible for it staying available
```

This is why Remote deployment isn't purely a technical upgrade — it trades "free but unmanaged" for "costs money but is actually operated." For a single developer's personal tool, that tradeoff usually favors Local. For anything serving many users where reliability and consistency matter, it usually favors Remote, cost notwithstanding.

# Local vs Remote Comparison

|Local MCP Server|Remote MCP Server|
|---|---|
|Runs on the user's machine|Runs on another machine or in the cloud|
|Very low latency|Network latency|
|Direct access to local resources|Access to centralized enterprise resources|
|Limited to one device|Shared across many users|
|Easier for development|Better for production deployment|

Neither approach is universally better.

The choice depends on the application.

# The Gateway Pattern: Combining Both in One System

Worth introducing a common enterprise pattern that goes a step beyond simple "hybrid" (using some Local, some Remote Servers side by side): a **gateway** or **proxy** MCP Server.

```text
Host/Client
     │
     ▼
Gateway MCP Server (Remote)
     │
     ├── proxies to → HR MCP Server
     ├── proxies to → CRM MCP Server
     └── proxies to → Database MCP Server
```

Instead of a Host managing many separate Client connections to many separate Servers directly, a single "gateway" Remote Server sits in front, itself acting as a Client to several other Servers, and exposing a unified interface outward. Benefits include centralizing authentication/authorization in one place (connecting back to the previous chapter), applying consistent logging and rate-limiting across all underlying Servers, and giving the Host a simpler, single connection point instead of managing many. This is a common pattern in larger enterprise MCP deployments specifically because it concentrates the security enforcement (auth, permissions, logging) in one well-audited place rather than spreading it across many independently-configured Servers.

# Best Practices

Use Local Servers for personal and development workflows.

Use Remote Servers for shared enterprise services.

Secure all Remote Servers with strong authentication.

Monitor Remote Server availability.

Choose the deployment model based on scalability and security requirements.

Consider a gateway pattern when many Remote Servers need consistent auth, logging, and access control.

Factor in ongoing operational cost and responsibility, not just latency and access, when choosing Remote deployment.

# Common Beginner Mistakes

### Mistake 1

Thinking Remote Servers are always better.

Local Servers are often faster and simpler for desktop applications.

---

### Mistake 2

Running enterprise services as Local Servers.

Shared services are usually better deployed remotely.

---

### Mistake 3

Ignoring security for Remote Servers.

Remote deployments should always enforce authentication and authorization.

---

### Mistake 4

Creating separate implementations for Local and Remote Servers.

The MCP protocol remains the same.

Only the transport and deployment change.

---

### Mistake 5

Treating "Local vs Remote" and "stdio vs HTTP" as if they were literally the same decision, rather than two correlated but conceptually distinct layers (where it runs vs how messages travel).

---

### Mistake 6

Comparing Local and Remote purely on latency/scalability while ignoring the real operational cost and responsibility difference (unmanaged but free, vs managed but costly).

# Interview Tip

A common interview question is:

> **What is the difference between a Local MCP Server and a Remote MCP Server?**

A good answer is:

A Local MCP Server runs on the same machine as the Client and is commonly used for desktop applications and development. A Remote MCP Server runs on another machine or in the cloud, allowing multiple Clients to access shared tools and resources. Both use the same MCP protocol but differ in deployment, scalability, latency, and resource access.

---

# Interview Tip

A stronger follow-up worth preparing for:

> **In a large enterprise with many internal MCP Servers, how would you avoid configuring authentication and logging separately for each one?**

Answer:

A gateway (or proxy) MCP Server pattern — a single Remote Server that itself connects to and aggregates several underlying Servers, exposing one unified interface to Hosts. This centralizes authentication, authorization, and logging in one place, rather than requiring each individual underlying Server to implement and maintain its own security layer consistently.

# Key Takeaways

- Local MCP Servers run on the same machine as the Client.
- Remote MCP Servers run on another machine, typically in the cloud.
- "Local vs Remote" (deployment) and "stdio vs HTTP" (transport) are correlated but conceptually separate decisions.
- Local deployment offers speed and privacy, at zero hosting cost but with no dedicated operator; Remote deployment offers scalability and centralized management, at real ongoing operational cost.
- A gateway/proxy MCP Server pattern centralizes auth, logging, and access control across many underlying Servers in larger deployments.
- The MCP protocol remains the same regardless of where the Server is deployed.
