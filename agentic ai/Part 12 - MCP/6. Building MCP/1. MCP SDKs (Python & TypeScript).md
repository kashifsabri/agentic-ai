# What is an MCP SDK?

An MCP SDK (Software Development Kit) is a library that helps developers build MCP Clients and MCP Servers without implementing the MCP protocol from scratch.

Instead of worrying about:

- JSON-RPC
- Message parsing
- Transport management
- Connection lifecycle
- Capability negotiation

the SDK provides these features automatically.

Developers can focus on the business logic.

---

# Why Do We Need SDKs?

Imagine implementing an MCP Server manually.

You would need to write code for:

- JSON parsing
- Request routing
- Error handling
- Connection management
- Tool registration
- Resource registration
- Notifications
- Logging

This would require thousands of lines of code.

The SDK reduces this complexity dramatically.

# Official MCP SDKs

The official MCP project provides SDKs for multiple programming languages.

- Python SDK

# The Decorator Pattern: How Tools Actually Get Registered

The chapter's later code examples show creating a `Server` object, but skip the part that developers spend the most time on: actually defining a tool. Both major SDKs use a **decorator pattern**, letting you turn an ordinary function into an MCP tool with minimal extra code.

```python
from mcp.server import Server

server = Server("weather-server")

@server.tool()
def get_weather(city: str) -> str:
    """Get the current weather for a given city."""
    return weather_api.fetch(city)
```

That `@server.tool()` decorator is doing the heavy lifting: it registers `get_weather` as a callable MCP tool, handles receiving `tools/call` requests for it, and passes along the incoming arguments as actual Python function parameters — you never manually write JSON-RPC handling code for this. This is the concrete mechanism behind the abstract "you write tools, the SDK handles the protocol" framing given earlier in the chapter.

---

# Tool Schemas Are Often Auto-Generated From Your Code

This connects directly back to the Function Calling chapter, which described tool schemas as JSON descriptions of name, parameters, and types sent to the model. Here's the part that chapter didn't cover: in most SDKs, you don't hand-write that schema yourself.

```text
Your function's type hints (city: str)
      ↓
Your function's docstring ("Get the current weather...")
      ↓
SDK automatically generates the JSON Schema description
      ↓
That generated schema is what actually gets sent to the model
  as part of tool/capability information
```

This is why writing clear type hints and a clear docstring isn't just good Python style — it's functionally equivalent to writing the tool description that the Function Calling chapter emphasized mattering for the model's decision-making. A vague docstring produces a vague tool description, which can make the model less reliable about when and how to call that tool, even though the underlying function works perfectly.

# Testing a Server Without Building a Full Host First

A practical development question worth answering here: how do you actually try out a Server you're building, before wiring up a complete Host application around it?

The official tooling includes an **Inspector** — a standalone testing tool that acts as a lightweight, generic Host/Client specifically for development. It lets you connect to your in-progress Server, see its negotiated capabilities, manually invoke tools with test arguments, and inspect the raw JSON-RPC messages going back and forth — all without needing Claude Desktop, Cursor, or a custom Host application running yet.

```text
Your MCP Server (in development)
        ↑
        │ connect and test manually
        │
    MCP Inspector
```

This is the practical answer to "how do I debug my Server before it's plugged into a real AI application" — you don't need a full Agent and LLM in the loop just to verify your tools work and return the shape of data you expect.

# SDK Version vs Protocol Version: They Can Drift

Worth a brief but important caution: the version number of the SDK package you install (e.g. `pip install mcp==1.4.0`) is not automatically identical to the MCP _protocol_ version that Server negotiates during `initialize` (as covered in the Capability Negotiation chapter).

```text
SDK version    → tracks the library's own release history
                  (bug fixes, new convenience features, etc.)

Protocol version → tracks the MCP specification itself
                  (e.g. "2024-11-05") — this is what actually
                  gets negotiated between Client and Server
```

In practice, a newer SDK version usually supports a newer protocol version, but they're still two different numbers tracking two different things. If you ever see compatibility issues between a Client and Server built with different SDK versions, this is the first place to look — not just "are both SDKs up to date," but "do they actually agree on protocol version during negotiation."

# Best Practices

Use the official SDK whenever possible.

Keep business logic separate from protocol logic.

Organize tools, resources, and prompts into separate modules.

Write clear type hints and docstrings — they often become the actual tool schema sent to the model.

Use the Inspector (or equivalent) to test tools during development, before integrating with a full Host.

Update the SDK regularly, and confirm protocol version compatibility, not just SDK version, when debugging Client-Server issues.

Read the official SDK documentation before building production systems.

# Common Beginner Mistakes

### Mistake 1

Trying to implement MCP manually.

The official SDK already handles most protocol details.

---

### Mistake 2

Mixing business logic with communication logic.

The SDK should handle communication,

while your code implements application behavior.

---

### Mistake 3

Thinking Python and TypeScript SDKs work differently.

They expose different language APIs,

but follow the same MCP specification.

---

### Mistake 4

Ignoring SDK updates.

New MCP features are often added through SDK releases.

---

### Mistake 5

Writing vague type hints or skipping docstrings on tool functions.

Since these often auto-generate the schema sent to the model, vague documentation directly translates into a less reliable tool description.

---

### Mistake 6

Assuming SDK version and protocol version are the same number, or always move in lockstep.

They track different things — always confirm negotiated protocol version specifically when debugging compatibility issues.

# Interview Tip

A common interview question is:

> **Why should developers use the official MCP SDK instead of implementing the protocol manually?**

A good answer is:

The official MCP SDK abstracts protocol details such as JSON-RPC, transports, connection management, capability negotiation, and error handling. This allows developers to focus on implementing tools, resources, and business logic while ensuring compliance with the MCP specification.

---

# Interview Tip

A stronger follow-up worth preparing for:

> **How does the SDK generate the tool schema that gets sent to the model?**

Answer:

Most SDKs auto-generate the JSON Schema description from the tool function's type hints and docstring, rather than requiring the developer to hand-write it. This means writing clear, specific type hints and documentation isn't just good practice — it directly determines the quality of the tool description the model uses to decide when and how to call that tool, connecting directly to the importance of clear function descriptions covered in the Function Calling chapter.
