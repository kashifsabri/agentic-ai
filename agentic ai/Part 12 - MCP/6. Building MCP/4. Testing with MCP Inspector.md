# What is MCP Inspector?

MCP Inspector is an official developer tool used to connect to an MCP Server and inspect its capabilities.

It allows developers to:

- Connect to an MCP Server
- View available Tools
- View Resources
- View Prompts
- Execute Tool Calls
- Inspect Responses
- Debug Communication

Think of it as **Postman for MCP Servers**.

---

# Launching MCP Inspector

MCP Inspector is run directly with `npx`, no separate installation required.

```bash
npx @modelcontextprotocol/inspector python server.py
```

This starts your Server as a subprocess (via stdio) and opens a local web UI, typically at:

```text
http://localhost:5173
```

For a Server that uses HTTP/SSE instead of stdio, point Inspector at the running Server's URL:

```bash
npx @modelcontextprotocol/inspector --url http://localhost:8000
```

---

# Navigating the Inspector Interface

Once connected, the Inspector UI is organized into a few key panels:

```text
Server Info Panel  → Name, version, negotiated capabilities
Tools Tab          → List of tools, their input schemas, and a form to call them
Resources Tab      → Browsable list of exposed resources and their content
Prompts Tab        → List of prompt templates with variable inputs
Logs / Messages    → Raw JSON-RPC requests and responses as they happen
```

The **Logs** panel is particularly useful — it shows the exact JSON-RPC messages exchanged, which is the ground truth when debugging a protocol-level issue rather than a business-logic bug.

# Testing Different Transports and Configurations

Since a Server may need to run over stdio locally but HTTP/SSE remotely, it's worth testing both paths before release.

```bash
# Test the local/stdio path
npx @modelcontextprotocol/inspector python server.py

# Test the deployed/remote path
npx @modelcontextprotocol/inspector --url https://my-server.example.com
```

If your Server reads configuration from environment variables (e.g., API keys, feature flags), pass them explicitly when launching so you're testing the same configuration that production will use:

```bash
API_KEY=test-key npx @modelcontextprotocol/inspector python server.py
```

This helps catch configuration-related bugs — like a missing environment variable — before they surface in a real deployment.

# Inspector CLI Mode for Scripted Checks

Beyond the interactive UI, Inspector also supports a CLI mode that can call a tool directly from the command line and print the result — useful for quick scripted checks or including in a shell-based smoke test.

```bash
npx @modelcontextprotocol/inspector --cli python server.py \
  --method tools/call \
  --tool-name get_weather \
  --tool-arg city=Mumbai
```

This is handy for a fast sanity check (e.g., in a pre-commit hook or a manual release checklist) without opening the full UI — though it's still a manual/ad hoc tool, not a substitute for real automated tests (see below).

# Limitations of MCP Inspector (and When to Add Automated Tests)

MCP Inspector is excellent for interactive, exploratory testing during development — but it has limits:

- It's a manual tool: someone has to open it and click through scenarios
- It doesn't run automatically in CI/CD pipelines
- It doesn't track regressions over time the way a test suite does

For production reliability, Inspector should be paired with actual automated tests:

```python
import pytest

@pytest.mark.asyncio
async def test_get_weather_returns_valid_response():
    async with stdio_client(server_params) as (read, write):
        async with ClientSession(read, write) as session:
            await session.initialize()
            result = await session.call_tool("get_weather", {"city": "Mumbai"})
            assert "weather" in result.content[0].text.lower()
```

A good workflow: use Inspector while building and debugging a tool interactively, then codify the key scenarios as automated tests that run on every code change.

# Best Practices

Test every Tool before deployment.

Verify Resources and Prompts.

Check error handling.

Validate input parameters.

Test authentication if implemented.

Test both stdio and HTTP/SSE transports if the Server supports both.

Codify key scenarios as automated tests, not just manual Inspector sessions.

Retest after every major change.

# Common Beginner Mistakes

### Mistake 1

Testing only through an AI Agent.

Use MCP Inspector first to isolate Server issues.

---

### Mistake 2

Ignoring error scenarios.

Test both successful and failed requests.

---

### Mistake 3

Deploying without testing.

Always verify Server behavior before production deployment.

---

### Mistake 4

Assuming the Server works because it starts successfully.

A running Server is not necessarily a correct Server.

---

### Mistake 5

Relying only on manual Inspector sessions for ongoing quality.

Without automated tests, regressions can slip in silently between releases.

---

### Mistake 6

Never testing with the actual environment variables or transport used in production.

A Server that works with test defaults in Inspector can still fail once real configuration is applied.
