This interaction is called **MCP Elicitation**.

---

# What is MCP Elicitation?

MCP Elicitation is a capability that allows an MCP Server to request additional information from the user through the MCP Client.

Instead of making assumptions,

the Server pauses execution until the required information is provided.

---

# Why Do We Need Elicitation?

AI Agents often receive incomplete requests.

Examples include:


Each request may be missing important details.

Elicitation allows the Server to collect the required information before continuing.

# The Elicitation Request Schema

Elicitation isn't a free-form chat message — a request declares a structured schema describing exactly what fields are needed, similar to a Tool's input schema (Chapter 74).

```json
{
  "message": "Please provide your flight details.",
  "requestedSchema": {
    "type": "object",
    "properties": {
      "destination": { "type": "string", "description": "City you're flying to" },
      "departure_city": { "type": "string", "description": "City you're flying from" },
      "travel_date": { "type": "string", "format": "date" },
      "passengers": { "type": "integer", "minimum": 1, "default": 1 }
    },
    "required": ["destination", "departure_city", "travel_date"]
  }
}
```

```python
result = await session.elicit(
    message="Please provide your flight details.",
    schema=FlightDetailsSchema
)
```

Using a schema (instead of open-ended text) lets the Client render an appropriate form, validate the answer's shape before returning it, and lets the Server safely assume the response matches what it asked for.

# User Response Actions: Accept, Decline, Cancel

An Elicitation request doesn't always get a clean answer — the protocol explicitly supports three outcomes, and the Server must handle all of them.

|Action|Meaning|
|---|---|
|Accept|User provides the requested information|
|Decline|User explicitly refuses to provide it|
|Cancel|User dismisses the request without answering|

```python
response = await session.elicit(message="...", schema=FlightDetailsSchema)

if response.action == "accept":
    proceed_with_booking(response.data)
elif response.action == "decline":
    return "No problem — let me know if you'd like to try again."
else:  # cancel
    return "Booking cancelled."
```

Treating "decline" and "cancel" as first-class outcomes (not just as errors) is what makes Elicitation feel like a natural conversation instead of a rigid form the user is forced to complete.

# Elicitation vs Prompts

Although both involve user interaction,

they have different purposes.

|Prompt|Elicitation|
|---|---|
|Guides the AI model|Collects missing user input|
|Used before or during reasoning|Used when required information is missing|
|Reusable instruction template|Interactive question to the user|

Think of them this way:

- **Prompt** → _Guide the AI._
- **Elicitation** → _Ask the user._

# What Elicitation Should NOT Be Used For

Because Elicitation directly prompts the user for input, it's tempting to use it for anything — but some categories of information should never be requested this way.

```text
Avoid eliciting:
- Passwords or authentication credentials
- Full payment card numbers
- Government ID numbers
- Any secret that should go through a dedicated, secure auth flow
```

Elicitation is designed for ordinary task data (dates, names, preferences) — not as a substitute for proper authentication (Chapter 82) or secure credential handling. A Server requesting a password through Elicitation is a red flag a Client should be built to recognize and block, similar to how a legitimate bank never asks for your full PIN over chat.

# Handling Timeouts

Elicitation pauses the Server's execution while waiting on the user — but a user may never respond. Servers need a defined timeout behavior rather than waiting indefinitely.

```text
Elicitation sent → waiting...
↓
No response after N minutes
↓
Server treats it as a soft cancel: cleans up, logs the incomplete request,
and returns a clear message instead of hanging forever
```

```python
try:
    response = await asyncio.wait_for(session.elicit(...), timeout=300)
except asyncio.TimeoutError:
    return "Still waiting on flight details — feel free to try again when ready."
```

This connects to the checkpointing ideas from Chapter 56: an Elicitation-blocked workflow is a natural point to checkpoint state, so the user can resume later without losing prior progress.

# Batch vs Sequential Elicitation

When several fields are missing, a Server can either ask for everything at once (batch) or one question at a time (sequential).

|Batch|Sequential|
|---|---|
|One form with all fields|One question per turn|
|Faster for the user if all fields are simple|More conversational, easier for follow-up context|
|Best for structured, form-like data|Best for a natural back-and-forth chat interface|

```text
Batch:      "Please provide destination, departure city, and travel date." (one form)
Sequential: "What's your destination?" → "And your departure city?" → "When are you traveling?"
```

Choosing the right style depends on the Client's interface — a form-based UI favors batch, while a chat-based UI often feels more natural with sequential questions.

# Best Practices

Ask only for missing information.

Keep questions short and specific.

Avoid requesting unnecessary details.

Use a structured schema so responses can be validated automatically.

Handle accept, decline, and cancel as distinct, expected outcomes.

Never request passwords, payment details, or other credentials via Elicitation.

Define a timeout and a graceful fallback if the user never responds.

Choose batch or sequential elicitation based on the Client's interface style.

Resume execution automatically once the required information is available.

# Common Beginner Mistakes

### Mistake 1

Guessing missing values.

Always ask the user when required information is unavailable.

---

### Mistake 2

Asking for information that is already available.

Collect only what is missing.

---

### Mistake 3

Asking multiple unrelated questions at once.

Guide the user through the workflow clearly.

---

### Mistake 4

Continuing execution with incomplete information.

Validate required inputs before proceeding.

---

### Mistake 5

Using Elicitation to request sensitive credentials.

Passwords and payment details belong in a dedicated, secure authentication flow, not a general-purpose Elicitation request.

---

### Mistake 6

Waiting indefinitely for a user response with no timeout.

Without a timeout and fallback, a stalled Elicitation can block the workflow forever.

# Interview Tip

A common interview question is:

A good answer is:

MCP Elicitation allows an MCP Server to request additional information from the user through the MCP Client when required inputs are missing, using a structured schema so responses can be validated automatically. The user can accept, decline, or cancel the request, and the Server should handle all three outcomes along with a timeout for no response. It enables interactive workflows where the Server pauses execution, collects the necessary information, and then resumes processing — but it should never be used to collect sensitive credentials.
