# What are MCP Roots?

MCP Roots define the locations or workspaces that a Client makes available to an MCP Server.

They tell the Server:

> **"You may work within these locations."**

Roots establish the scope of accessible content without exposing the user's entire system.

---

# Why Do We Need Roots?

AI Agents often work with:

- Source code
- Documents
- Projects
- Workspaces

Without Roots,

a Server would not know:

- Which files belong to the current task
- Which folders it may access
- Which locations are off-limits

Roots provide this context while improving security.

# How Roots Are Communicated (Protocol-Level)

Roots aren't just a conceptual idea — they're exchanged through explicit MCP messages, similar to how Tools and Resources are listed.

```text
Server → roots/list → Client
Client → [
    { "uri": "file:///workspace/ecommerce-app", "name": "EcommerceApp" }
  ]
```

```python
roots = await session.list_roots()
for r in roots.roots:
    print(r.uri, r.name)
```

A Server requests the current Roots when it needs to know its working scope, rather than assuming a fixed location.

---

# URI Format for Roots

Roots are expressed as URIs, most commonly using the `file://` scheme for local file system paths.

```text
file:///workspace/ecommerce-app
file:///C:/Projects/EcommerceApp
```

Using a URI format (rather than a raw OS-specific path string) keeps Roots consistent across operating systems and makes them easy to compare, validate, and combine with Resource URIs from Chapter 75.

# Dynamic Roots and Change Notifications

A user's workspace isn't always static — they might open a second project folder, or close one, mid-session. MCP supports this through a **listChanged** notification.

```text
User opens a second project folder in their editor
↓
Client sends notification: roots/list_changed
↓
Server calls roots/list again to get the updated set
```

```python
@session.on_roots_list_changed
async def handle_roots_changed():
    updated_roots = await session.list_roots()
    # Re-scope the Server's understanding of what's accessible
```

This lets a Server stay in sync with the user's actual working context throughout a long session, rather than only knowing what was shared at connection time.

# Roots Are Advisory, Not Enforcement

It's important to understand what Roots actually guarantee: they communicate _intended_ scope, but the MCP protocol itself doesn't force a Server to respect that boundary.

```text
Client shares Root: /workspace/ecommerce-app
↓
A well-behaved Server only reads within this path
↓
A misbehaving Server could still attempt to read outside it,
if the underlying OS/process permissions allow it
```

Real security comes from combining Roots with actual enforcement mechanisms:

- Running the Server in a sandboxed process with restricted file system access
- OS-level permission scoping (the process literally cannot read outside the Root)
- Code review / vetting of Servers before connecting them, especially third-party ones

This connects directly to the upcoming discussion of Agent Permissions — Roots express _intended_ scope; permissions and sandboxing are what actually _enforce_ it.

# Roots vs Resources

Although related,

they are different concepts.

|Root|Resource|
|---|---|
|Defines where the Server may look|Defines what content is available|
|Scope or boundary|Individual piece of data|

Think of them this way:

- **Root** → _Where can I access?_
- **Resource** → _What can I read?_

# Best Practices

Share only the Roots needed for the current task.

Keep Roots as narrow as practical.

Do not expose sensitive directories unnecessarily.

Allow users to control which Roots are shared.

Treat Roots as security boundaries, but back them with actual sandboxing or OS-level enforcement.

Handle `roots/list_changed` so long-running Servers stay in sync with the user's workspace.

# Common Beginner Mistakes

### Mistake 1

Thinking a Root is a file.

A Root defines a location or workspace,

not an individual document.

---

### Mistake 2

Sharing the entire file system.

Only expose directories relevant to the task.

---

### Mistake 3

Confusing Roots with Resources.

Roots define scope.

Resources provide content.

---

### Mistake 4

Assuming the Server can access any folder.

The Server can only access Roots explicitly shared by the Client.

---

### Mistake 5

Assuming Roots alone provide real security.

Roots communicate intent — actual enforcement requires sandboxing or OS-level permission scoping.

---

### Mistake 6

Ignoring `roots/list_changed` notifications.

A Server that never re-checks Roots can act on stale assumptions about what's still in scope.

# Interview Tip

A common interview question is:

> **What are MCP Roots?**

A good answer is:

MCP Roots define the locations or workspaces that a Client makes available to an MCP Server, communicated via `roots/list` as `file://` URIs and updated dynamically through `list_changed` notifications. They establish the scope within which the Server can access files or resources, improving security by limiting access to only the areas required for the current task — though real enforcement still depends on sandboxing or OS-level permissions, since Roots themselves are advisory.

# Key Takeaways

- MCP Roots define the workspace or locations shared with an MCP Server.
- Roots are communicated via `roots/list` and expressed as `file://` URIs.
- `roots/list_changed` notifications keep Servers in sync as the user's workspace changes.
- Roots limit the Server's _intended_ access to only approved areas — they are advisory, not enforced by the protocol itself.
- Real security requires pairing Roots with sandboxing or OS-level permission enforcement.
- They improve privacy and security.
- A Root defines **where** the Server may access information.
- Roots work together with Resources to provide safe access to data.
