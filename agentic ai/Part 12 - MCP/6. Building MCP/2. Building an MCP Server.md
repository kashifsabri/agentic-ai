# Step 3 — Create the Server

Create a new Server instance.

```python
from mcp.server import Server

server = Server("weather-server")
```

The SDK handles:

- Protocol implementation
- Connection management
- JSON-RPC
- Message handling

You only define your application's capabilities.

---

# Step 4 — Register a Tool

Define a tool that Clients can call.

Example:

```python
@server.tool()
def get_weather(city: str):
    return f"The weather in {city} is sunny."
```

The SDK automatically exposes this function as an MCP Tool.

Clients can now discover and invoke it.

---

# Defining Input Schemas

The type hints on a tool's parameters aren't just documentation — the SDK uses them to generate a schema that tells the Client (and the LLM behind it) exactly what input is valid.

```python
from pydantic import BaseModel, Field

class WeatherInput(BaseModel):
    city: str = Field(description="City name, e.g. 'Tokyo'")
    units: str = Field(default="celsius", description="celsius or fahrenheit")

@server.tool()
def get_weather(input: WeatherInput):
    return f"The weather in {input.city} is sunny ({input.units})."
```

Using a structured schema instead of loose parameters:

- Rejects invalid input before your function body even runs
- Gives the LLM clear guidance on what values are expected
- Makes the tool self-documenting for anyone integrating with it

---

# Writing Good Tool Descriptions

An MCP Tool is only useful if the LLM calling it understands _when_ and _how_ to use it. The function's docstring and parameter descriptions directly shape this.

Weak

```python
@server.tool()
def get_weather(city: str):
    """Gets weather."""
    ...
```

Better

```python
@server.tool()
def get_weather(city: str):
    """
    Get the current weather conditions for a specific city.
    Use this when the user asks about temperature, rain, or
    general weather conditions for a named location.
    """
    ...
```

Just like a well-written prompt (Chapter 33), a well-written tool description directly affects how reliably the LLM chooses and uses the tool correctly.

# Choosing a Transport

MCP Servers can communicate over different transports depending on where the Client and Server run.

|Transport|Description|Best For|
|---|---|---|
|stdio|Server runs as a local subprocess, communicates via standard input/output|Local tools, CLI integrations, desktop apps|
|HTTP / SSE|Server runs remotely, Client connects over the network|Remote/shared servers, web-based Clients, multi-user access|

```python
# stdio (local process)
server.run(transport="stdio")

# HTTP/SSE (remote server)
server.run(transport="sse", port=8000)
```

Choose stdio for tools that only need to run on the same machine as the Client; choose HTTP/SSE when multiple Clients need to reach the same Server over a network.

# Async Tools

Many real tools call external APIs or databases, which involves waiting on I/O. Tools can be defined as async functions so the Server doesn't block while waiting.

```python
@server.tool()
async def get_weather(city: str):
    response = await weather_api_client.fetch(city)
    return response.summary
```

This allows the Server to handle other requests while a slow network call is in progress.

# Exposing Resources and Prompts

Tools aren't the only capability a Server can expose. MCP also supports **Resources** (readable data) and **Prompts** (reusable prompt templates).

```python
@server.resource("weather://forecast/{city}")
def get_forecast_resource(city: str):
    return f"5-day forecast data for {city}..."

@server.prompt()
def weather_report_prompt(city: str):
    return f"Write a friendly weather report for {city} based on the forecast data."
```

Resources let Clients read data without triggering an action; Prompts let Clients reuse a well-crafted template instead of writing one from scratch each time.

# Handling Errors

Tools should fail gracefully with a clear message rather than crashing the Server or returning a confusing raw exception.

```python
@server.tool()
def get_weather(city: str):
    if not city.strip():
        raise ValueError("City name cannot be empty.")
    try:
        return weather_api_client.fetch(city)
    except ConnectionError:
        return {"error": "Weather service is currently unavailable. Please try again later."}
```

A structured, descriptive error lets the calling Agent (or LLM) understand what went wrong and decide how to respond, instead of the interaction simply failing silently.

# Testing with MCP Inspector

Before connecting a real Client, the official **MCP Inspector** tool lets you test a Server directly — listing its tools, sending sample calls, and inspecting responses.

```bash
npx @modelcontextprotocol/inspector python server.py
```

This is useful for verifying that:

- Tools are registered correctly
- Input schemas behave as expected
- Error handling returns sensible messages

Testing this way catches integration issues early, before a real Agent ever calls the Server.

# Packaging and Deployment

Once a Server is ready to share, it needs to be packaged so Clients can install and run it.

```text
requirements.txt / pyproject.toml → Dependencies
README.md                          → Setup instructions
Dockerfile (optional)              → Containerized deployment
```

For local tools distributed via stdio, publishing to a package registry (like PyPI or npm) lets users install and run the Server with a single command. For remote HTTP/SSE Servers, standard deployment practices (containers, cloud hosting) apply, same as any web service.

# Best Practices

Keep each Server focused on a single domain.

Design tools with clear responsibilities.

Validate all tool inputs using structured schemas.

Write clear, specific tool descriptions to guide LLM tool selection.

Return structured responses.

Handle errors gracefully with descriptive messages.

Organize tools into separate modules as the project grows.

Test with a tool like MCP Inspector before connecting real Clients.

---

# Common Beginner Mistakes

### Mistake 1

Putting all application logic into one file.

As the Server grows,

split tools into separate modules.

---

### Mistake 2

Exposing internal helper functions as tools.

Only register functions intended for Client use.

---

### Mistake 3

Skipping input validation.

Always validate Client-provided arguments.

---

### Mistake 4

Ignoring error handling.

Servers should return meaningful errors instead of crashing.

---

### Mistake 5

Writing vague tool descriptions.

A poorly described tool leads the LLM to call it at the wrong time or with wrong arguments.

---

### Mistake 6

Choosing the wrong transport for the use case.

Using stdio for a Server that needs to serve multiple remote Clients (or HTTP for a purely local tool) adds unnecessary complexity.
