# Connecting via stdio (A Full Example)

In practice, connecting to a local Server means spawning it as a subprocess and communicating over stdio. Here's what that looks like end to end:

```python
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

server_params = StdioServerParameters(
    command="python",
    args=["server.py"]
)

async def main():
    async with stdio_client(server_params) as (read, write):
        async with ClientSession(read, write) as session:
            await session.initialize()
            tools = await session.list_tools()
            print(tools)

            result = await session.call_tool("get_weather", {"city": "Mumbai"})
            print(result)
```

Using `async with` here matters: it guarantees the connection and session are properly closed even if an error occurs midway, instead of leaking an open subprocess or socket.

# Connecting an LLM Agent to MCP Tools

In a real Agentic AI application, the Client's discovered tools need to be converted into a format the LLM's function-calling API understands, so the LLM can decide when to call them.

```python
mcp_tools = await session.list_tools()

llm_tools = [
    {
        "name": tool.name,
        "description": tool.description,
        "input_schema": tool.inputSchema
    }
    for tool in mcp_tools.tools
]

response = llm.invoke(messages, tools=llm_tools)

if response.tool_call:
    result = await session.call_tool(
        response.tool_call.name,
        response.tool_call.arguments
    )
```

This is the bridge between MCP (how tools are exposed) and the Agent loop from earlier chapters (how the LLM decides to call a tool) — the Client is what connects the two.

# Connecting to Multiple Servers

A single Agent often needs capabilities from more than one Server — for example, weather, GitHub, and a database Server all at once.

```python
sessions = {}

for name, params in {
    "weather": weather_server_params,
    "github": github_server_params,
}.items():
    read, write = await stdio_client(params).__aenter__()
    session = ClientSession(read, write)
    await session.initialize()
    sessions[name] = session

# Route a tool call to the right server
result = await sessions["github"].call_tool("search_repository", {"query": "mcp"})
```

Production Agents typically maintain a registry mapping each tool name to the Server session that owns it, so a tool call can be routed correctly regardless of how many Servers are connected.

# Retry and Timeout Handling

Network calls and subprocess communication can fail transiently. Clients should handle this rather than letting a single failure break the whole Agent run.

```python
import asyncio

async def call_tool_with_retry(session, tool_name, args, retries=3, timeout=10):
    for attempt in range(retries):
        try:
            return await asyncio.wait_for(
                session.call_tool(tool_name, args),
                timeout=timeout
            )
        except asyncio.TimeoutError:
            if attempt == retries - 1:
                raise
            await asyncio.sleep(2 ** attempt)  # exponential backoff
```

This pattern — timeout, retry with backoff, and eventually surface the error — mirrors standard practice for any unreliable network call, and applies directly to MCP tool invocations.

# Best Practices

Reuse Client connections when possible.

Initialize every session properly.

Validate responses before using them.

Handle network failures gracefully with retries and timeouts.

Close connections when they are no longer needed — use context managers to guarantee this.

Maintain a tool-to-server registry when connected to multiple Servers.

---

# Common Beginner Mistakes

### Mistake 1

Calling tools before initialization.

The session must be initialized first.

---

### Mistake 2

Assuming every Server exposes the same capabilities.

Always discover capabilities dynamically.

---

### Mistake 3

Ignoring communication errors.

Clients should handle connection failures and retries.

---

### Mistake 4

Keeping unused connections open.

Always disconnect when communication is complete.

---

### Mistake 5

Manually managing connection open/close instead of using context managers.

This risks leaking subprocesses or sockets if an error occurs mid-session.

---

### Mistake 6

Hardcoding a single Server connection when the Agent may need several.

Without a tool-to-server registry, routing calls to the correct Server becomes fragile as more Servers are added.

# Interview Tip

A common interview question is:

> **How does an MCP Client communicate with an MCP Server?**

A good answer is:

An MCP Client connects to an MCP Server, initializes the session, negotiates capabilities, discovers available tools and resources, sends JSON-RPC requests, receives responses, and returns the results to the AI Agent. In practice, the Client also converts discovered tools into the LLM's function-calling format, handles retries and timeouts, and may manage connections to multiple Servers at once. The Client manages communication but does not execute tools itself.

# Key Takeaways

- The MCP Client manages communication with MCP Servers.
- It connects, initializes, discovers capabilities, and invokes tools.
- Context managers (`async with`) ensure connections are always properly closed.
- Discovered MCP tools must be converted into the LLM's function-calling format to be usable by an Agent.
- A Client can connect to multiple Servers, routed through a tool-to-server registry.
- Retry logic with timeouts and backoff makes tool calls resilient to transient failures.
- The Client does not execute business logic.
- The SDK handles protocol details such as JSON-RPC and transports.
- Production Clients include authentication, retries, logging, and error handling.
