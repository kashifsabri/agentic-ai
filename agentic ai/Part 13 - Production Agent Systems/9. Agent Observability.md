# What is Agent Observability?

Agent Observability is the ability to understand **what happened inside an AI Agent during execution**.

Instead of only seeing the final response,

developers can inspect the Agent's complete execution process.

This includes:

- Reasoning steps
- Model calls
- Tool execution
- Memory retrieval
- State updates
- Errors
- Performance metrics

# Monitoring vs Observability

Although the terms are often used together,

they are different.

|Monitoring|Observability|
|---|---|
|Detects problems|Explains problems|
|Shows system health|Shows execution details|
|Uses dashboards and alerts|Uses logs, metrics, and traces|
|Answers **"Something is wrong."**|Answers **"Why did it go wrong?"**|

Monitoring tells you **that** a problem exists.

Observability helps you understand **why** it exists.

# Correlation IDs in Practice

Every piece of observability data for a single user request should be tied together with a shared **correlation ID** (also called a request ID or trace ID) — without it, logs from thousands of concurrent requests become impossible to untangle.

```python
import uuid
import logging
import contextvars

request_id_var = contextvars.ContextVar("request_id", default=None)

def start_request():
    request_id = str(uuid.uuid4())
    request_id_var.set(request_id)
    return request_id

class RequestIdFilter(logging.Filter):
    def filter(self, record):
        record.request_id = request_id_var.get() or "unknown"
        return True

logging.basicConfig(
    format="%(asctime)s [%(request_id)s] %(message)s"
)
logging.getLogger().addFilter(RequestIdFilter())
```

```text
Without correlation ID:
  "Calling weather tool"       ← which request is this from??
  "Tool timeout"
  "Calling weather tool"       ← is this a retry, or a different user?

With correlation ID:
  [req-4521] Calling weather tool
  [req-4521] Tool timeout
  [req-4521] Retrying weather tool
  [req-8832] Calling weather tool   ← clearly a different request
```

This ID should be generated once at the start of a request and threaded through every log line, metric tag, and trace span for that request — including across services if the Agent calls other internal APIs.

# OpenTelemetry for AI Agents

Rather than building custom tracing from scratch, most production systems use **OpenTelemetry (OTel)** — an open, vendor-neutral standard for logs, metrics, and traces that works across almost any observability backend.

```python
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter

trace.set_tracer_provider(TracerProvider())
tracer = trace.get_tracer(__name__)
trace.get_tracer_provider().add_span_processor(
    BatchSpanProcessor(OTLPSpanExporter(endpoint="http://localhost:4317"))
)

async def run_agent(user_input: str):
    with tracer.start_as_current_span("agent_execution") as span:
        span.set_attribute("user_input_length", len(user_input))

        with tracer.start_as_current_span("llm_call"):
            response = await call_llm(user_input)

        with tracer.start_as_current_span("tool_call") as tool_span:
            tool_span.set_attribute("tool_name", response.tool_call.name)
            result = await call_tool(response.tool_call)

        return result
```

Because OTel is a standard, switching observability backends (Datadog, Honeycomb, Grafana, etc.) later doesn't require rewriting instrumentation — just changing the exporter configuration.

# Protecting Sensitive Data in Observability Pipelines

Logs and traces often capture raw user input and model output — which can include names, emails, medical details, or other PII. This data needs to be redacted before it's stored or shipped to a third-party observability platform.

```python
import re

def redact_pii(text: str) -> str:
    text = re.sub(r'[\w.+-]+@[\w-]+\.[\w.-]+', '[EMAIL_REDACTED]', text)
    text = re.sub(r'\b\d{3}-\d{2}-\d{4}\b', '[SSN_REDACTED]', text)
    text = re.sub(r'\b\d{16}\b', '[CARD_REDACTED]', text)
    return text

logging.info(f"User request: {redact_pii(user_input)}")
```

```text
Before: "My email is john.doe@example.com and my card is 4111111111111111"
After:  "My email is [EMAIL_REDACTED] and my card is [CARD_REDACTED]"
```

Beyond simple pattern-based redaction, some teams route observability data through a dedicated PII-scrubbing service before it reaches logs — since regex alone can miss less structured sensitive information (like a name embedded naturally in a sentence).

# Trace Sampling Strategies

At high volume, capturing a full, detailed trace for every single request can be expensive and produce more data than anyone can realistically use. **Sampling** captures a representative subset instead.

|Strategy|How it Works|Best For|
|---|---|---|
|Head-based sampling|Decide to sample at the start of a request (e.g., 10% of all requests)|Simple, low-overhead, general use|
|Tail-based sampling|Decide after the request completes, biased toward errors/slow requests|Catching interesting cases (failures, high latency) without keeping everything|
|Always-sample errors|100% of failed/erroring requests are traced, successes sampled at a lower rate|Balancing cost with never missing a failure|

```python
import random

def should_sample(is_error: bool, base_rate: float = 0.1) -> bool:
    if is_error:
        return True  # always trace errors
    return random.random() < base_rate  # sample 10% of successful requests
```

This ensures the system captures full detail on every failure (where debugging matters most) while keeping storage and processing costs manageable on the much larger volume of successful requests.

# Observability Tooling Landscape

Rather than building everything from scratch, most teams adopt existing observability platforms — some general-purpose, some purpose-built for LLM applications.

|Tool|Focus|
|---|---|
|**Langfuse**|LLM/Agent-specific tracing, prompt versions, evaluation|
|**LangSmith**|LangChain-native tracing and evaluation|
|**Datadog / New Relic**|General-purpose APM, infrastructure + application monitoring|
|**Grafana + Prometheus**|Open-source metrics dashboards and alerting|
|**Honeycomb**|High-cardinality distributed tracing|

LLM-specific tools (Langfuse, LangSmith) typically understand concepts like "prompt version" and "token cost" natively, while general-purpose APM tools are better suited for infrastructure-level metrics (CPU, memory, network) — many production stacks use both together.

# Best Practices

Capture every important execution step.

Record model and tool interactions.

Correlate events using request identifiers threaded through logs, metrics, and traces.

Standardize instrumentation using OpenTelemetry where possible.

Redact PII before storing or exporting observability data.

Sample intelligently — always capture errors, sample successes at a lower rate.

Store observability data securely.

Use observability throughout development and production.

# Common Beginner Mistakes

### Mistake 1

Logging only the final response.

The complete execution path should be observable.

---

### Mistake 2

Assuming monitoring is enough.

Monitoring detects problems.

Observability explains them.

---

### Mistake 3

Ignoring tool execution details.

Tool failures are a common source of production issues.

---

### Mistake 4

Collecting observability data without analyzing it.

Observability is valuable only when it helps improve the system.

---

### Mistake 5

Logging raw user input and model output without redacting PII.

This can turn an observability pipeline into a compliance and privacy liability.

---

### Mistake 6

Capturing 100% detailed traces at high volume with no sampling strategy.

This drives up storage and processing cost without proportionally more debugging value — sample successes, always keep errors.

# Key Takeaways

- Agent Observability provides visibility into the internal execution of AI Agents.
- It helps explain why failures occur.
- Correlation IDs tie together all logs, metrics, and traces for a single request.
- OpenTelemetry provides a vendor-neutral standard for instrumenting Agent execution.
- PII must be redacted from observability data before storage or export.
- Sampling (especially always-sample-errors) keeps high-volume tracing affordable.
- Purpose-built tools (Langfuse, LangSmith) and general APM tools (Datadog, Grafana) often work together.
- Observability is broader than monitoring.
- Modern observability is built on logs, metrics, and traces.
- Observability is essential for debugging and operating production AI systems.
