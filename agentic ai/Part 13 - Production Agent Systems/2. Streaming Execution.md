# What is Streaming Execution?

Streaming Execution is the process of returning partial results to the user while the Agent is still executing the task.

Instead of waiting for the entire workflow to finish,

the Agent continuously sends updates as work progresses.

---

# Why Do We Need Streaming?

Many Agent tasks take time.

Examples include:

- Reading large documents
- Searching multiple databases
- Calling several APIs
- Running multiple tools
- Multi-Agent collaboration
- Report generation

Waiting until everything finishes makes the application feel slow.

Streaming keeps users informed.

# Types of Streaming

Streaming can occur at different levels.

### 1. Token Streaming

The LLM streams generated tokens as they are produced.

Example:

```text
The

↓

weather

↓

today

↓

is

↓

sunny...
```

This is the most common form of streaming.

---

### 2. Progress Streaming

The Agent reports execution progress.

Example:

```text
Searching files...

↓

Analyzing data...

↓

Generating answer...
```

The user understands what the Agent is currently doing.

---

### 3. Tool Streaming

Individual tools stream their progress.

Example:

```text
Downloading File...

35%

↓

70%

↓

Completed
```

This is useful for long-running tool executions.

---

### 4. Multi-Step Streaming

The Agent streams the result of each reasoning step.

Example:

```text
Planning...

↓

Searching...

↓

Summarizing...

↓

Answer Complete
```

This provides transparency into the Agent's workflow.

# Python Example: Basic Token Streaming

Most LLM SDKs support streaming natively — the response arrives as an iterator instead of one final string.

```python
from anthropic import Anthropic

client = Anthropic()

with client.messages.stream(
    model="claude-sonnet-4-6",
    max_tokens=500,
    messages=[{"role": "user", "content": "Summarize this document..."}]
) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)
```

Each `text` chunk is a small piece of the final response — printing (or sending) it immediately, instead of collecting everything first, is what creates the streaming effect for the user.

# Python Example: Structured Streaming Events

Real Agent applications stream more than just text — they stream _typed events_ so the Client can distinguish progress updates from actual content.

```python
import json

def stream_agent_response(user_query: str):
    yield json.dumps({"type": "status", "message": "Thinking..."})

    yield json.dumps({"type": "tool_call", "tool": "search_flights"})
    flight_results = search_flights(user_query)
    yield json.dumps({"type": "tool_result", "tool": "search_flights", "data": flight_results})

    yield json.dumps({"type": "status", "message": "Generating response..."})
    for token in generate_response_stream(flight_results):
        yield json.dumps({"type": "token", "content": token})

    yield json.dumps({"type": "done"})
```

|Event Type|Purpose|
|---|---|
|`status`|High-level progress update ("Thinking...", "Searching...")|
|`tool_call`|A tool is about to run|
|`tool_result`|A tool finished, with its output|
|`token`|A piece of the generated text response|
|`error`|Something went wrong mid-stream|
|`done`|Signals the stream is complete|

This structured approach lets a UI show a "Searching flights..." indicator, then smoothly transition to displaying streamed text — rather than just printing raw, undifferentiated chunks.

# Python Example: Serving a Stream over HTTP (SSE)

To deliver a stream to a web Client, the server typically uses **Server-Sent Events (SSE)**.

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()

@app.get("/agent/stream")
async def stream_endpoint(query: str):
    def event_generator():
        for event in stream_agent_response(query):
            yield f"data: {event}\n\n"

    return StreamingResponse(event_generator(), media_type="text/event-stream")
```

On the browser/Client side, this is consumed with the `EventSource` API (JavaScript) or an SSE-aware HTTP client, processing each `data:` line as it arrives instead of waiting for the connection to close.

# Handling Interruptions and Reconnection

A streaming connection can drop mid-response — a user closes a tab, or the network blips. Production systems need a plan for this rather than silently losing the response.

```python
async def stream_with_buffer(query: str):
    buffer = []
    try:
        for event in stream_agent_response(query):
            buffer.append(event)
            yield event
    except ConnectionResetError:
        # Persist what was generated so far (ties into Chapter 56 checkpointing)
        save_partial_response(query, buffer)
```

```text
Client reconnects
↓
Request: "resume stream for request_id=abc123"
↓
Server: replays buffered events, then continues live streaming
```

Keeping a buffer of emitted events (or checkpointing progress, as in Chapter 56) allows a dropped connection to resume cleanly instead of forcing the user to restart the entire task.

# Backpressure

If the Client consumes events slower than the Agent produces them (e.g., a slow network connection), events can pile up in memory. This is called **backpressure**, and streaming systems need to handle it deliberately.

```python
import asyncio

async def stream_with_backpressure(query: str, max_queue_size=50):
    queue = asyncio.Queue(maxsize=max_queue_size)

    async def producer():
        for event in stream_agent_response(query):
            await queue.put(event)  # blocks if queue is full, naturally slowing production

    asyncio.create_task(producer())

    while True:
        event = await queue.get()
        yield event
        if json.loads(event).get("type") == "done":
            break
```

Using a bounded queue (rather than an unbounded list) means a slow Client naturally throttles how fast the Agent generates further output, instead of the server's memory growing unbounded.

# Best Practices

Stream meaningful updates.

Avoid flooding users with unnecessary messages.

Clearly distinguish between progress updates and final results using typed events.

Handle interruptions gracefully, buffering or checkpointing so a dropped connection can resume.

Apply backpressure handling so a slow Client doesn't cause unbounded memory growth.

Keep streamed information consistent with the final response.

---

# Common Beginner Mistakes

### Mistake 1

Waiting for the entire workflow before sending anything.

Users prefer immediate feedback.

---

### Mistake 2

Streaming every internal reasoning step.

Only expose information that improves the user experience and is appropriate for the application.

---

### Mistake 3

Sending updates too frequently.

Excessive streaming can overwhelm both users and the system.

---

### Mistake 4

Ignoring failure scenarios.

If execution fails,

the user should receive a clear status rather than an incomplete stream.

---

### Mistake 5

Streaming raw, untyped text chunks instead of structured events.

Without event types (status, tool_call, token, error, done), the Client can't distinguish progress updates from actual content.

---

### Mistake 6

Not handling backpressure or dropped connections.

Without a bounded queue or a resume mechanism, a slow or interrupted Client can cause memory growth or a permanently lost response.
