# What is Agent Monitoring?

Agent Monitoring is the continuous observation of an AI Agent's health, performance, and behavior while it is running in production.

Monitoring answers questions such as:

- Is the Agent healthy?
- Is it responding normally?
- Are tools working correctly?
- Are response times increasing?
- Is token usage unusually high?

Monitoring continuously checks the system.

---

# What is Alerting?

Alerting is the process of notifying engineers when monitored values exceed predefined thresholds.

Instead of waiting for users to report problems,

the system detects issues automatically.

Example:

```text
Tool Failure Rate

↓

25%

↓

Threshold Exceeded

↓

Alert Sent
```

---

# Why Do We Need Monitoring?

With monitoring,

# Monitoring vs Observability

These concepts are closely related but different.

|Monitoring|Observability|
|---|---|
|Detects ongoing health|Explains internal behavior|
|Uses dashboards and alerts|Uses logs, metrics, and traces|
|Answers "Is the system healthy?"|Answers "Why did it fail?"|

Monitoring tells you **when** something is wrong.

Observability helps explain **why**.

# Alert Severity Levels

Not every alert deserves the same response. Assigning a severity level determines how (and how urgently) the team is notified.

|Severity|Meaning|Response|
|---|---|---|
|**P1 / Critical**|System down or unusable for most users|Page on-call immediately, 24/7|
|**P2 / High**|Significant degradation, not full outage|Page during business hours, notify off-hours|
|**P3 / Medium**|Minor issue, doesn't need immediate action|Slack/email notification, review next business day|
|**P4 / Low**|Informational, worth tracking|Logged/dashboarded only, no notification|

```python
def determine_severity(error_rate: float, affected_users_pct: float) -> str:
    if error_rate > 0.5 or affected_users_pct > 0.5:
        return "P1"
    elif error_rate > 0.1:
        return "P2"
    elif error_rate > 0.02:
        return "P3"
    return "P4"
```

Mapping severity to a specific notification channel (page vs Slack vs dashboard-only) is what prevents both under-reaction to real emergencies and alert fatigue from over-notifying on minor issues.

# Static Thresholds vs Anomaly Detection

Simple alerts compare a metric to a fixed number — but fixed thresholds don't always reflect what's actually "normal" for a system with variable traffic patterns.

```text
Static threshold: "Alert if error rate > 5%"
  Problem: 5% might be totally normal during a known traffic spike,
           or already too high during a quiet period.

Anomaly detection: "Alert if error rate deviates significantly
                     from this time-of-day/day-of-week's typical baseline"
  Better reflects what's actually unusual for THIS system, THIS time.
```

```python
def is_anomalous(current_value: float, historical_values: list[float], std_devs: float = 3) -> bool:
    import statistics
    mean = statistics.mean(historical_values)
    stdev = statistics.stdev(historical_values)
    return abs(current_value - mean) > std_devs * stdev
```

Static thresholds are simpler to reason about and a fine starting point; anomaly detection becomes valuable once a system has enough historical data and traffic is too variable for one fixed number to make sense at all times.

# SLO Burn-Rate Alerting

Rather than alerting on a raw metric threshold, mature systems alert based on how fast they're consuming their **error budget** relative to their SLO (Chapter: Production Readiness).

```text
SLO: 99.9% success rate over 30 days → error budget = 0.1% of requests can fail

Burn rate = (actual error rate) / (error rate allowed by SLO)

Burn rate = 1x   → consuming budget at the expected, sustainable rate
Burn rate = 10x  → will exhaust the entire month's error budget in ~3 days
Burn rate = 50x  → will exhaust it in hours — page immediately
```

```python
def calculate_burn_rate(current_error_rate: float, slo_error_budget: float) -> float:
    return current_error_rate / slo_error_budget

burn_rate = calculate_burn_rate(current_error_rate=0.02, slo_error_budget=0.001)
if burn_rate > 10:
    trigger_page(severity="P1")
elif burn_rate > 2:
    trigger_page(severity="P2")
```

This approach directly ties alerting to what actually matters to the business (staying within the promised SLA) rather than an arbitrary static number, and naturally scales the urgency of the alert to how quickly the problem will actually violate the SLA.

# Runbooks

An alert that fires with no guidance forces every on-call engineer to rediscover the fix from scratch. A **runbook** — a short, linked document describing how to investigate and resolve a specific alert — turns a 2 AM page into a fast, guided response.

```text
Alert: "Tool Failure Rate > 20% — search_flights"

Runbook:
1. Check the Flight API status page: https://status.flightapi.example.com
2. If API is down: enable fallback cached results (see feature flag: flight_fallback_cache)
3. If API is up but slow: check timeout config — may need temporary increase
4. If neither: check recent deploys — may be a code regression, consider rollback
5. Escalate to @flights-team if unresolved after 15 minutes
```

```python
ALERT_RUNBOOKS = {
    "tool_failure_rate_high": "https://wiki.internal/runbooks/tool-failures",
    "llm_provider_down": "https://wiki.internal/runbooks/llm-provider-outage",
}

def send_alert(alert_name: str, details: dict):
    runbook_url = ALERT_RUNBOOKS.get(alert_name, "No runbook available")
    notify_oncall(f"{alert_name}\nDetails: {details}\nRunbook: {runbook_url}")
```

Attaching the runbook link directly in the alert notification (not buried in a separate wiki search) is what actually makes it get used during a stressful incident.

# Alert Grouping and Deduplication

A single root cause (e.g., the LLM provider going down) can trigger dozens of individual metric breaches at once — without grouping, this floods the on-call engineer with what looks like dozens of unrelated problems.

```python
# Alertmanager configuration (Prometheus ecosystem)
```

```yaml
route:
  group_by: ["alertname", "service"]
  group_wait: 30s        # wait briefly to bundle related alerts together
  group_interval: 5m      # how often to send updates for an ongoing group
  repeat_interval: 4h     # don't re-notify the same unresolved alert too often
  receiver: "oncall-pagerduty"

  routes:
    - match:
        severity: P1
      receiver: "oncall-pagerduty"
      repeat_interval: 30m
    - match:
        severity: P3
      receiver: "team-slack-channel"
```

Grouping related alerts into a single notification ("LLM provider outage — 12 related alerts") instead of 12 separate pages is one of the most effective fixes for alert fatigue, alongside appropriate `repeat_interval` settings so unresolved issues aren't silently forgotten but also aren't re-paging every minute.

# Best Practices

Monitor both infrastructure and Agent behavior.

Alert only on actionable problems.

Assign severity levels so notification urgency matches actual impact.

Prefer SLO/burn-rate-based alerting over arbitrary static thresholds where possible.

Attach a runbook link to every alert.

Group and deduplicate related alerts to avoid flooding on-call engineers.

Avoid excessive alerts.

Review alert thresholds regularly.

Continuously monitor external dependencies such as LLM providers and third-party APIs.

---

# Common Beginner Mistakes

### Mistake 1

Monitoring only the server.

Production AI systems must also monitor models, tools, memory, and external services.

---

### Mistake 2

Creating too many alerts.

Excessive alerts lead to alert fatigue, causing important alerts to be ignored.

---

### Mistake 3

Using unrealistic thresholds.

Alert thresholds should be based on normal production behavior.

---

### Mistake 4

Monitoring without observability.

Monitoring detects problems, but observability is needed to diagnose them.

---

### Mistake 5

Treating every alert as equally urgent.

Without severity levels, a minor issue can page someone at 3 AM just as loudly as a full outage.

---

### Mistake 6

Sending alerts with no runbook or guidance.

This forces every on-call engineer to rediscover the fix from scratch, slowing incident response.

# Interview Tip

A common interview question is:

> **Why are Monitoring and Alerting important for AI Agents?**

A good answer is:

Monitoring continuously tracks the health and performance of an AI Agent by collecting metrics such as latency, error rates, token usage, and tool success. Alerting automatically notifies engineers when predefined thresholds — or, more robustly, SLO burn rates — are exceeded, with severity levels, grouping, and linked runbooks ensuring the right people are notified appropriately and can resolve issues quickly, before they significantly impact users.
