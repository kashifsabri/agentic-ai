# What are Logs?

Logs are timestamped records of important events.

They describe **what happened** during execution.

Example:

```text
10:15:02

Agent Started

--------------------

10:15:03

Calling Weather Tool

--------------------

10:15:05

Weather Tool Completed

--------------------

10:15:06

Response Returned
```

Logs create a timeline of events.

---

# Log Levels

Not every log message is equally important. Log levels let you filter noise from signal, and control verbosity per environment.

|Level|When to Use|
|---|---|
|`DEBUG`|Fine-grained detail, useful only during active debugging|
|`INFO`|Normal operational events (e.g., "Agent started", "Tool called")|
|`WARNING`|Something unexpected but recoverable (e.g., a retry)|
|`ERROR`|An operation failed and needs attention|
|`CRITICAL`|The system itself is at risk (e.g., can't reach the database at all)|

```python
import logging

logger = logging.getLogger("agent")
logger.setLevel(logging.INFO)  # DEBUG logs are suppressed in production

logger.debug("Full prompt sent to LLM: %s", full_prompt)      # dev-only detail
logger.info("Tool called: %s", tool_name)                      # normal operation
logger.warning("Tool timed out, retrying (%d/%d)", 1, 3)       # recoverable
logger.error("Tool failed after all retries: %s", tool_name)   # needs attention
```

Setting the log level differently per environment (e.g., `DEBUG` in development, `INFO` in production) keeps production logs readable while still allowing verbose output when actively debugging locally.

# Structured (JSON) Logging

Plain text logs are easy for humans to read one at a time, but hard for machines to search, filter, and aggregate at scale. Production systems typically use **structured logging** — emitting each log entry as JSON with consistent fields.

```python
import logging
import json
from datetime import datetime, timezone

class JSONFormatter(logging.Formatter):
    def format(self, record):
        log_entry = {
            "timestamp": datetime.now(timezone.utc).isoformat(),
            "level": record.levelname,
            "message": record.getMessage(),
            "request_id": getattr(record, "request_id", None),
            "component": record.name,
        }
        return json.dumps(log_entry)

handler = logging.StreamHandler()
handler.setFormatter(JSONFormatter())
logging.getLogger().addHandler(handler)

logging.info("Tool called", extra={"request_id": "req-4521"})
```

```json
{"timestamp": "2026-08-08T10:15:03Z", "level": "INFO", "message": "Tool called", "request_id": "req-4521", "component": "root"}
```

With structured logs, a query like "show me all ERROR logs for request_id=req-4521" becomes trivial in a log aggregation platform — with plain text, you'd be grepping through unstructured strings.

# What are Metrics?

Metrics are numerical measurements collected over time.

Instead of recording individual events,

they summarize system performance.

Examples include:

- Requests per Second
- Average Response Time
- Token Usage
- Error Rate
- Tool Success Rate
- CPU Usage
- Memory Usage

Metrics help answer:

> **How is the system performing overall?**

---

# Types of Metrics

Different metrics need different underlying data structures — using the right type matters for how the data can later be queried and visualized.

|Type|Behavior|Example|
|---|---|---|
|**Counter**|Only increases, resets on restart|Total requests served, total errors|
|**Gauge**|Goes up or down freely|Current queue depth, active connections|
|**Histogram**|Buckets values to show distribution|Response time percentiles (p50, p95, p99)|

```python
from prometheus_client import Counter, Gauge, Histogram

requests_total = Counter("agent_requests_total", "Total requests handled")
active_jobs = Gauge("agent_active_jobs", "Number of jobs currently running")
response_time = Histogram("agent_response_time_seconds", "Response time distribution")

requests_total.inc()                 # increment counter
active_jobs.set(12)                  # set gauge to current value
with response_time.time():           # automatically records duration
    handle_request()
```

Using a Counter for something that can decrease (like active connections) or a Gauge for something that should only ever grow (like total requests) makes the resulting dashboards misleading — matching metric type to behavior is what keeps the data meaningful.

# Metric Cardinality Pitfalls

**Cardinality** refers to how many unique combinations of label values a metric can have. High cardinality can silently overwhelm a metrics system.

```python
# Risky: user_id has potentially millions of unique values
requests_total.labels(user_id=user_id, endpoint="/chat").inc()

# Safer: bucket or omit high-cardinality labels
requests_total.labels(endpoint="/chat").inc()
```

```text
Low cardinality (safe):   endpoint = "/chat" | "/search" | "/summarize"  (a handful of values)
High cardinality (risky): user_id = "user_48291"                          (millions of values)
```

Adding a label like `user_id` or a raw request ID to a metric can create millions of unique time series, which most metrics backends handle very poorly — that kind of per-request detail belongs in logs or traces, not metric labels.

# What are Traces?

A Trace records the complete journey of a single request through the system.

It shows every component involved.

Example:

```text
User Request

↓

Planner

↓

LLM

↓

Memory

↓

Tool

↓

Database

↓

Final Response
```

Traces answer:

> **Where did the request spend its time?**

---

# Trace Spans and Parent-Child Relationships

A trace is made up of **spans** — each span represents one unit of work, and spans can be nested to show which operation triggered which.

```python
from opentelemetry import trace

tracer = trace.get_tracer(__name__)

async def handle_request(user_input: str):
    with tracer.start_as_current_span("handle_request") as parent_span:  # root span

        with tracer.start_as_current_span("plan") as plan_span:          # child span
            plan = await create_plan(user_input)

        with tracer.start_as_current_span("execute_tools") as tools_span:  # child span
            for step in plan.steps:
                with tracer.start_as_current_span(f"tool:{step.tool_name}"):  # grandchild span
                    await run_tool(step)

        return build_response(plan)
```

```text
handle_request (total: 3.2s)
├── plan (0.4s)
└── execute_tools (2.8s)
    ├── tool:search_flights (1.5s)
    └── tool:search_hotels (1.3s)
```

This parent-child structure is exactly what makes a trace visualization useful — you can see at a glance which specific step consumed the most time, down to an individual tool call within a larger workflow.

# Best Practices

Log meaningful events.

Use log levels consistently, and adjust verbosity per environment.

Prefer structured (JSON) logs so they're easy to query and aggregate.

Collect metrics continuously, choosing the right type (counter, gauge, histogram).

Watch for high-cardinality labels that can overwhelm a metrics backend.

Trace every important request, using nested spans to show the full call structure.

Use request IDs to correlate logs and traces.

Avoid logging sensitive information.

Monitor trends instead of isolated events.

---

# Common Beginner Mistakes

### Mistake 1

Relying only on logs.

Logs alone cannot show system-wide performance trends.

---

### Mistake 2

Collecting metrics without traces.

Metrics indicate that a problem exists,

but traces explain where it occurs.

---

### Mistake 3

Logging sensitive user information.

Always sanitize logs before storing them.

---

### Mistake 4

Ignoring correlation IDs.

Without request identifiers,

linking logs, metrics, and traces becomes difficult.

---

### Mistake 5

Using plain text logs at scale instead of structured JSON.

This makes searching and aggregating logs across thousands of requests far harder than it needs to be.

---

### Mistake 6

Adding high-cardinality labels (like user_id or raw request IDs) to metrics.

This can explode the number of unique time series and overwhelm the metrics backend — that level of detail belongs in logs or traces.

# Interview Tip

A common interview question is:

> **What is the difference between Logs, Metrics, and Traces?**

A good answer is:

Logs record individual events during execution (ideally structured and leveled), Metrics provide numerical summaries of system performance over time using counters, gauges, and histograms, and Traces capture the complete execution path of a single request as a tree of nested spans across multiple components. Together, they provide comprehensive observability for production AI systems.

---

# Key Takeaways

- Logs record individual execution events — use log levels and structured JSON format at scale.
- Metrics measure system performance over time using counters, gauges, and histograms.
- High-cardinality labels (like user IDs) can overwhelm a metrics backend — keep that detail in logs/traces instead.
- Traces capture the complete lifecycle of a request as a tree of nested, parent-child spans.
- All three are essential for debugging and operating production AI systems.
- Modern observability platforms combine Logs, Metrics, and Traces into a unified view.
