# Why Do We Need Performance Testing?

Functional testing verifies:

> **Does the Agent work?**

Performance testing verifies:

> **Does the Agent still work under heavy usage?**

Production systems must remain stable,

even during peak traffic.

---

# What is Load Testing?

Load Testing measures how well an AI Agent performs under its expected workload.

Example:

```text
Expected Users

↓

500 Concurrent Requests

↓

Measure Performance
```

The goal is to verify that the system meets its performance requirements.

---

# What is Stress Testing?

Stress Testing pushes the system beyond its expected capacity.

Example:

```text
Expected Capacity

↓

500 Users

↓

Stress Test

↓

2,000 Users

↓

Observe Failure Point
```

The objective is to understand how the system behaves under extreme conditions.

---

# Load Testing vs Stress Testing

|Load Testing|Stress Testing|
|---|---|
|Expected workload|Beyond expected workload|
|Measures normal performance|Measures breaking point|
|Validates stability|Identifies failure limits|
|Used before deployment|Used to improve resilience|

Both are essential for production systems.

# Load Testing with Locust

Rather than writing custom concurrency code, most teams use a dedicated load-testing tool. **Locust** is a popular Python-based option that lets you define user behavior and simulate thousands of concurrent users.

```python
# locustfile.py
from locust import HttpUser, task, between

class AgentUser(HttpUser):
    wait_time = between(1, 3)  # simulate realistic pauses between requests

    @task
    def ask_support_question(self):
        self.client.post("/agent/chat", json={
            "message": "Where is my order #4521?"
        })

    @task(2)  # weight: this task runs twice as often
    def ask_faq_question(self):
        self.client.post("/agent/chat", json={
            "message": "What's your return policy?"
        })
```

```bash
# Run with a web UI to control user count and ramp-up live
locust -f locustfile.py --host https://staging.myapp.com

# Or run headless for CI: 500 users, ramping up 10/sec, for 5 minutes
locust -f locustfile.py --host https://staging.myapp.com \
  --users 500 --spawn-rate 10 --run-time 5m --headless
```

Locust reports requests/second, response time percentiles (p50, p95, p99), and failure rates live as the test runs — exactly the metrics needed to answer "can this handle expected load?"

# Controlling Cost with Mocked LLM Endpoints

Running a load test with 500 simulated users, each triggering a real LLM call, can be extremely expensive — and can burn through provider rate limits meant for real users. Most load tests should run against a mocked LLM layer instead.

```python
from fastapi import FastAPI

app = FastAPI()

@app.post("/mock-llm/generate")
async def mock_llm(request: dict):
    import asyncio, random
    await asyncio.sleep(random.uniform(0.5, 2.0))  # simulate realistic latency
    return {"text": "This is a simulated response.", "tokens": 150}
```

```text
Load test target: staging environment configured to call the mock LLM endpoint
↓
Simulates realistic latency and payload size, without real API cost
```

A smaller, separate test — with a handful of real requests, not thousands — should still be run periodically against the _actual_ LLM provider to confirm real-world latency assumptions used in the mock are still accurate.

# Soak (Endurance) Testing

Load and stress tests are typically short bursts. **Soak testing** runs a sustained, moderate load for an extended period (hours, not minutes) to catch problems that only appear over time.

```bash
locust -f locustfile.py --host https://staging.myapp.com \
  --users 200 --spawn-rate 5 --run-time 6h --headless
```

```text
What soak testing catches that short tests miss:
- Memory leaks (memory usage climbing steadily over hours)
- Connection pool exhaustion
- Log files or temp files filling up disk space
- Gradual performance degradation from unbounded caches or growing state
```

A system that handles a 10-minute burst of load perfectly can still fail after 8 hours of sustained traffic if it's slowly leaking memory — soak testing is the only way to catch this before a real overnight production incident does.

# Spike Testing

**Spike testing** checks how the system handles a sudden, sharp increase in traffic — not a gradual ramp-up, but an abrupt jump.

```python
from locust import LoadTestShape

class SpikeShape(LoadTestShape):
    stages = [
        {"duration": 60,  "users": 50,   "spawn_rate": 10},   # normal baseline
        {"duration": 90,  "users": 2000, "spawn_rate": 500},  # sudden spike
        {"duration": 150, "users": 50,   "spawn_rate": 10},   # back to normal
    ]

    def tick(self):
        run_time = self.get_run_time()
        for stage in self.stages:
            if run_time < stage["duration"]:
                return (stage["users"], stage["spawn_rate"])
        return None
```

```text
Real-world triggers for spikes:
- A social media post going viral
- A marketing email blast landing in inboxes simultaneously
- A scheduled batch job (e.g., "send reminders to all users at 9 AM")
```

Spike testing reveals whether autoscaling (Chapter: Background Jobs) reacts fast enough, or whether the system needs a request queue/buffer to absorb the initial burst gracefully instead of dropping requests.

# Identifying the Bottleneck Component

When a load test reveals degraded performance, the next question is: **which specific component is actually the bottleneck?** Aggregate response time alone doesn't answer this.

```text
Total Response Time: 8 seconds
↓
Breakdown:
  Agent orchestration logic:  0.2s
  LLM API call:                5.5s   ← primary bottleneck
  Tool call (weather API):    1.8s
  Database write:              0.5s
```

```python
import time

async def run_agent_with_timing(user_input: str):
    timings = {}

    start = time.time()
    llm_response = await call_llm(user_input)
    timings["llm_call"] = time.time() - start

    start = time.time()
    tool_result = await call_tool(llm_response.tool_call)
    timings["tool_call"] = time.time() - start

    return {"result": tool_result, "timings": timings}
```

Instrumenting each stage separately (rather than only measuring total request time) shows exactly where to focus optimization effort — there's no point scaling application servers if the real bottleneck is a slow third-party API or an underprovisioned database.

# Best Practices

Test using realistic workloads.

Measure every important component.

Include both LLM and Tool latency.

Increase traffic gradually.

Use a real load-testing tool (like Locust) instead of custom scripts.

Mock the LLM layer for large-scale tests to control cost; validate real latency separately at smaller scale.

Run soak tests for hours, not just minutes, to catch memory leaks and slow degradation.

Run spike tests to validate autoscaling and burst-handling, not just gradual ramp-up.

Instrument each component separately to find the actual bottleneck.

Test recovery after failures.

Repeat performance tests after major architectural changes.

# Common Beginner Mistakes

### Mistake 1

Testing with only one user.

Production systems serve many users simultaneously.

---

### Mistake 2

Measuring only response time.

Resource utilization, error rates, and queue lengths are equally important.

---

### Mistake 3

Ignoring external dependencies.

Model APIs, databases, and external tools may become bottlenecks.

---

### Mistake 4

Stopping after Load Testing.

Stress Testing reveals failure limits that normal testing cannot.

---

### Mistake 5

Running large-scale load tests directly against a real, billed LLM API.

This can be extremely costly and may exhaust real rate limits — mock the LLM layer for high-volume tests.

---

### Mistake 6

Only running short bursts and never soak or spike testing.

Memory leaks and burst-handling failures often only appear under sustained load or sudden traffic spikes, not short, gradual tests.

# Interview Tip

A common interview question is:

> **What is the difference between Load Testing and Stress Testing?**

A good answer is:

Load Testing evaluates how an AI system performs under its expected workload, measuring metrics such as latency, throughput, and error rates, typically using a tool like Locust. Stress Testing intentionally exceeds the system's expected capacity to identify breaking points, understand failure behavior, and improve system resilience. Soak testing extends this over hours to catch memory leaks, while spike testing checks how the system handles sudden traffic bursts — and per-component timing is used to identify the actual bottleneck rather than just the aggregate response time.

---

# Key Takeaways

- Load Testing measures performance under expected workloads.
- Stress Testing identifies how the system behaves beyond its limits.
- Tools like Locust simulate realistic concurrent user behavior at scale.
- Mocking the LLM layer keeps large-scale load tests fast and affordable.
- Soak testing (hours of sustained load) catches memory leaks and slow degradation short tests miss.
- Spike testing validates how the system handles sudden, sharp traffic increases.
- Per-component timing reveals the actual bottleneck, not just overall response time.
- AI systems require additional metrics such as token usage, LLM latency, and tool execution time.
- Performance testing should include all components of the Agent architecture.
- Regular Load and Stress Testing improve reliability before production deployment.
