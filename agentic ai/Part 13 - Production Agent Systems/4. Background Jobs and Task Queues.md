# Introduction

In the previous chapter, we learned about **Asynchronous Execution**.

We saw that long-running Agent tasks should not block the user's request.

But this raises an important question:

> **If the user isn't waiting, who performs the work?**

The answer is:

**Background Workers**.

And how do these workers know what work to perform?

Through a **Task Queue**.

Together, Background Jobs and Task Queues form the backbone of most production AI systems.

---

# What is a Background Job?

A Background Job is a task that executes independently of the user's request.

Instead of making the user wait,

the application schedules the work,

returns immediately,

and processes the task later.

Examples include:

- Summarizing thousands of documents
- Generating reports
- Processing uploaded files
- Running AI evaluations
- Sending emails
- Large multi-agent workflows

---

# What is a Task Queue?

A Task Queue is a system that stores Background Jobs until a worker is ready to execute them.

Think of it as a waiting line.

```text
Job 1

↓

Job 2

↓

Job 3

↓

Worker Picks Next Job
```

Workers continuously pull jobs from the queue and execute them.

---

# Why Do We Need Task Queues?

Imagine 1,000 users simultaneously request:

```text
Generate Annual Financial Report
```

Without a queue,

the server might try to execute all requests immediately,

causing:

- High memory usage
- API failures
- Model overload
- System crashes

Instead,

each request becomes a Background Job.

The queue controls how quickly workers process them.

# Background Job Lifecycle

Every Background Job follows a lifecycle.

```text
Created

↓

Queued

↓

Picked by Worker

↓

Running

↓

Completed

↓

Result Stored
```

If something goes wrong,

the job may enter:

```text
Failed

↓

Retry

↓

Completed
```

# Multiple Workers

A queue can be processed by multiple workers simultaneously.

```text
Task Queue

├── Worker 1

├── Worker 2

├── Worker 3

└── Worker 4
```

This allows the system to process many jobs in parallel.

# Choosing a Queue Technology

Different queue systems suit different needs — the right choice depends on scale, durability requirements, and existing infrastructure.

|Technology|Strengths|Best For|
|---|---|---|
|**Celery + Redis**|Simple setup, mature Python ecosystem|Most small-to-mid Python AI applications|
|**RQ (Redis Queue)**|Very lightweight, easy to reason about|Small projects, simple job types|
|**RabbitMQ**|Robust routing, strong delivery guarantees|Complex routing rules, enterprise messaging|
|**Amazon SQS**|Fully managed, scales automatically|Cloud-native apps already on AWS|
|**Kafka**|High-throughput, event streaming, replay support|Large-scale event pipelines, not just job queues|

For most Agent applications, Celery or RQ backed by Redis is the practical default; Kafka is usually overkill unless you also need event streaming beyond simple job processing.

# Retry Policies with Backoff

Retrying a failed job immediately often just fails again (e.g., the external API is still down). A better approach uses **exponential backoff** — waiting progressively longer between attempts.

```python
from celery import Celery

app = Celery("tasks")

@app.task(
    bind=True,
    max_retries=5,
    retry_backoff=True,        # exponential backoff: 1s, 2s, 4s, 8s...
    retry_backoff_max=600,     # cap the wait at 10 minutes
    retry_jitter=True          # add randomness to avoid thundering herd
)
def summarize_document(self, document_id: str):
    try:
        return call_llm_summarize(document_id)
    except TransientAPIError as exc:
        raise self.retry(exc=exc)
```

`retry_jitter` matters at scale — if 1,000 failed jobs all retry at exactly the same backoff interval, they can overwhelm the recovering service all at once; jitter spreads retries out randomly.

# Job Priorities and Scheduling

Not all jobs are equally urgent. Task Queues typically support priority levels and delayed/scheduled execution.

```python
# Priority: higher-priority jobs are picked up first
summarize_document.apply_async(args=[doc_id], priority=9)  # urgent
summarize_document.apply_async(args=[doc_id], priority=1)  # low priority

# Delayed job: run 1 hour from now
summarize_document.apply_async(args=[doc_id], countdown=3600)

# Scheduled job: run at a specific time
from datetime import datetime, timedelta
summarize_document.apply_async(args=[doc_id], eta=datetime.utcnow() + timedelta(days=1))
```

```text
High Priority Queue:  [urgent_job_1, urgent_job_2]
Default Queue:        [normal_job_1, normal_job_2, normal_job_3]
```

A common pattern is running separate queues per priority level (e.g., `high_priority`, `default`) with more workers dedicated to the high-priority queue, rather than relying solely on a numeric priority field.

# Dead-Letter Queue

Sometimes,

a job fails repeatedly.

Instead of retrying forever,

the system moves it to a **Dead-Letter Queue (DLQ)**.

```text
Job

↓

Retry

↓

Retry

↓

Retry

↓

Dead-Letter Queue
```

Developers can inspect these failed jobs later.

# Monitoring Queue Depth

**Queue depth** — how many jobs are waiting — is one of the most important health signals for a background job system.

```python
def get_queue_depth(queue_name="celery"):
    import redis
    r = redis.Redis()
    return r.llen(queue_name)
```

```text
Queue depth: 12    → Healthy, workers are keeping up
Queue depth: 5,000 → Workers are falling behind, jobs are piling up
```

A steadily growing queue depth is an early warning sign — either traffic has spiked beyond current capacity, or something is causing jobs to process slower (or fail) than expected. This should be an alerted metric, not something discovered only when users complain.

---

# Autoscaling Workers

Rather than running a fixed number of workers at all times, production systems often scale worker count based on queue depth.

```text
Queue depth < 100   → 2 workers
Queue depth 100–1000 → 5 workers
Queue depth > 1000   → 10+ workers (scale up)
↓
Queue depth drops back down → scale down after a cool-down period
```

```python
def desired_worker_count(queue_depth: int) -> int:
    if queue_depth < 100:
        return 2
    elif queue_depth < 1000:
        return 5
    else:
        return 10
```

Cloud platforms (e.g., Kubernetes with a queue-based autoscaler, or managed services like AWS SQS + Lambda) can automate this scaling loop, avoiding both wasted cost (over-provisioned idle workers) and backlog (under-provisioned workers during spikes).

# Best Practices

Keep API requests short.

Move long-running work to Background Jobs.

Scale Workers independently from the API, based on queue depth.

Track job status throughout execution.

Store completed results.

Configure retry policies with exponential backoff and jitter.

Use separate queues (or priorities) for urgent vs routine jobs.

Use Dead-Letter Queues for repeatedly failing jobs.

Monitor queue depth as a first-class health metric.

---

# Common Beginner Mistakes

### Mistake 1

Performing long-running AI tasks inside an HTTP request.

Move expensive operations to Background Jobs.

---

### Mistake 2

Creating Background Jobs without tracking status.

Users should always know whether a job is queued, running, completed, or failed.

---

### Mistake 3

Retrying failed jobs forever.

Use retry limits and Dead-Letter Queues.

---

### Mistake 4

Assuming one worker is enough.

Production systems often require many workers to process jobs concurrently.

---

### Mistake 5

Retrying immediately without backoff or jitter.

This can overwhelm a struggling downstream service further, or cause synchronized retry storms across many failed jobs.

---

### Mistake 6

Never monitoring queue depth.

A silently growing backlog often goes unnoticed until users start complaining about delayed results.

# Interview Tip

A common interview question is:

> **Why do production AI systems use Task Queues?**

A good answer is:

Task Queues allow long-running AI operations to execute asynchronously. User requests create Background Jobs that are stored in a queue, often with priorities and retry policies using exponential backoff. Worker processes retrieve and execute these jobs independently, and worker count can scale based on queue depth — improving scalability, responsiveness, and reliability while preventing the API from becoming overloaded.

# Key Takeaways

- Background Jobs execute independently of the user's request.
- Task Queues manage pending work until a worker is available.
- Choosing the right queue technology (Celery/Redis, RQ, RabbitMQ, SQS, Kafka) depends on scale and infrastructure.
- Retry policies should use exponential backoff with jitter, not immediate or unlimited retries.
- Priorities and scheduled/delayed jobs let urgent work jump ahead of routine work.
- Queue depth is a critical health metric and should be actively monitored.
- Worker count can autoscale based on queue depth to balance cost and responsiveness.
- Production systems use retries, timeouts, priorities, and Dead-Letter Queues for reliability.
- Background Jobs are essential for scalable AI applications.
