# Introduction

Imagine you ask an AI Agent:

```text
Analyze 10,000 customer support tickets and generate a report.
```

The task may take:

- Several minutes
- Tens of API calls
- Multiple LLM invocations
- Database queries

Should the user wait with an open browser tab?

No.

Instead, the Agent starts the task in the background and immediately responds:

```text
Your request has been accepted.

Job ID: 2841

We'll notify you when it's complete.
```

This is called **Asynchronous Execution**.

---

# What is Asynchronous Execution?

Asynchronous Execution allows an Agent to start a task without making the user wait for its completion.

Instead of blocking the request,

the work continues independently in the background.

The user can retrieve the result later.

---

# Why Do We Need Asynchronous Execution?

Some AI tasks take too long to complete during a single request.

Examples include:

- Large document analysis
- Report generation
- Video processing
- Multi-Agent workflows
- Batch data processing
- Scheduled automation

Keeping the connection open for several minutes is inefficient and unreliable.

# The Job State Machine

Every async job moves through a defined set of states — treating this as an explicit state machine (rather than an ad hoc flag) makes status reporting consistent and predictable.

```text
pending → running → completed
                  ↘ failed
                  ↘ cancelled
```

```python
from enum import Enum

class JobStatus(str, Enum):
    PENDING = "pending"
    RUNNING = "running"
    COMPLETED = "completed"
    FAILED = "failed"
    CANCELLED = "cancelled"
```

|State|Meaning|
|---|---|
|`pending`|Job accepted, waiting for a worker|
|`running`|A worker has picked it up and is executing|
|`completed`|Finished successfully, result available|
|`failed`|Finished with an error|
|`cancelled`|User or system cancelled it before completion|

Every job should always be in exactly one of these states, which makes both the status API and monitoring dashboards straightforward to build.

# Job Status API (Polling)

The most common way for a Client to check on a job is to poll a status endpoint using the Job ID returned at creation.

```python
from fastapi import FastAPI, HTTPException

app = FastAPI()

@app.post("/jobs")
async def create_job(request: AnalysisRequest):
    job_id = create_background_job(request)
    return {"job_id": job_id, "status": "pending"}

@app.get("/jobs/{job_id}")
async def get_job_status(job_id: str):
    job = job_store.get(job_id)
    if not job:
        raise HTTPException(status_code=404, detail="Job not found")
    return {
        "job_id": job_id,
        "status": job.status,
        "progress": job.progress,
        "result": job.result if job.status == "completed" else None
    }
```

```text
Client:  POST /jobs           → { "job_id": "2841", "status": "pending" }
Client:  GET /jobs/2841        → { "status": "running", "progress": 40 }
Client:  GET /jobs/2841        → { "status": "completed", "result": {...} }
```

Polling is simple to implement but has a trade-off: too-frequent polling wastes requests, while too-infrequent polling delays the user learning the result — a common pattern is to poll with increasing intervals (e.g., 1s, 2s, 5s, 10s...).

# Webhooks (Push-Based Notification)

Instead of the Client repeatedly asking "is it done yet?", the Server can push a notification once the job finishes — this is called a **webhook**.

```python
@app.post("/jobs")
async def create_job(request: AnalysisRequest):
    job_id = create_background_job(request, callback_url=request.webhook_url)
    return {"job_id": job_id, "status": "pending"}

def on_job_complete(job_id: str, result: dict, callback_url: str):
    import httpx
    httpx.post(callback_url, json={"job_id": job_id, "status": "completed", "result": result})
```

```text
Job finishes
↓
Server sends POST to the Client's registered webhook URL
↓
Client receives notification immediately, no polling needed
```

Webhooks reduce wasted requests and give near-instant notification, but require the Client to expose a reachable endpoint — polling remains the simpler default for Clients that can't receive incoming webhooks (e.g., a mobile app behind NAT).

# Idempotency for Async Jobs

If a Client's request times out or the connection drops, it might retry job creation — without protection, this can create duplicate jobs doing the same expensive work twice.

```python
@app.post("/jobs")
async def create_job(request: AnalysisRequest, idempotency_key: str = Header(...)):
    existing_job_id = job_store.find_by_idempotency_key(idempotency_key)
    if existing_job_id:
        return {"job_id": existing_job_id, "status": "already_exists"}

    job_id = create_background_job(request, idempotency_key=idempotency_key)
    return {"job_id": job_id, "status": "pending"}
```

```text
Client sends: Idempotency-Key: client-generated-uuid-123
↓
Server checks: has this key been seen before?
↓
Yes → Return the existing job, don't create a new one
No  → Create a new job, remember the key
```

This mirrors the idempotency discussion from Chapter 56 (Checkpointing) — the same principle applies whenever an action might be retried and shouldn't be duplicated.

# Detecting Stuck or Dead Jobs

A worker can crash mid-execution, leaving a job stuck in `running` forever unless something actively checks for this.

```python
import time

def detect_stuck_jobs(timeout_seconds=600):
    for job in job_store.get_by_status("running"):
        if time.time() - job.last_heartbeat > timeout_seconds:
            job.status = "failed"
            job.error = "Job exceeded timeout with no heartbeat"
            job_store.save(job)
```

Workers should periodically update a `last_heartbeat` timestamp while running; a separate watchdog process (run on a schedule) can then flag jobs that stopped heartbeating as failed, freeing them up for a retry instead of leaving the user waiting on a job that will never finish.

# Python Example: Celery Task Queue

Here's what a more production-realistic setup looks like using Celery, a widely used distributed task queue.

```python
# tasks.py
from celery import Celery

celery_app = Celery("agent_tasks", broker="redis://localhost:6379/0")

@celery_app.task(bind=True)
def analyze_contracts_task(self, contract_ids: list[str]):
    self.update_state(state="RUNNING", meta={"progress": 0})

    results = []
    for i, contract_id in enumerate(contract_ids):
        results.append(analyze_single_contract(contract_id))
        self.update_state(state="RUNNING", meta={"progress": int((i + 1) / len(contract_ids) * 100)})

    return {"results": results}
```

```python
# api.py
from tasks import analyze_contracts_task

@app.post("/jobs")
async def create_job(contract_ids: list[str]):
    task = analyze_contracts_task.delay(contract_ids)
    return {"job_id": task.id, "status": "pending"}

@app.get("/jobs/{job_id}")
async def get_status(job_id: str):
    task = analyze_contracts_task.AsyncResult(job_id)
    return {"status": task.state, "info": task.info}
```

Celery handles the queueing, worker distribution, retries, and status tracking that would otherwise need to be built manually — which is why most production systems reach for a task queue rather than raw `asyncio` for background Agent work.

# Best Practices

Use asynchronous execution only for long-running tasks.

Provide users with a Job ID or task identifier.

Allow users to check job status through a well-defined state machine.

Support webhooks for Clients that can receive them, and polling as the fallback.

Use idempotency keys to prevent duplicate job creation on retry.

Detect stuck/dead jobs with heartbeats and timeouts.

Persist intermediate progress when appropriate.

Retry failed jobs safely.

---

# Common Beginner Mistakes

### Mistake 1

Using synchronous execution for every task.

Long-running operations should execute asynchronously.

---

### Mistake 2

Not tracking job status.

Users should always know whether a task is pending, running, completed, or failed.

---

### Mistake 3

Losing results after execution.

Completed results should be stored until the user retrieves them.

---

### Mistake 4

Ignoring failed background jobs.

Production systems must detect, retry, or report failures.

---

### Mistake 5

Not protecting job creation with idempotency keys.

A retried request without one can silently create duplicate, expensive jobs.

---

### Mistake 6

Having no mechanism to detect stuck jobs.

Without heartbeats and timeouts, a crashed worker can leave a job "running" forever, leaving the user waiting indefinitely.

# Interview Tip

A common interview question is:

> **When should an AI Agent use asynchronous execution?**

A good answer is:

Asynchronous execution is used for long-running operations that should not block the user's request. The Agent creates a background job with a defined state (pending/running/completed/failed), returns immediately with a job identifier, performs the work independently — often via a task queue like Celery — and allows the user to retrieve the result later through polling or a webhook notification, while idempotency keys and heartbeat-based timeout detection keep the system safe to retry and free of stuck jobs.

---

# Key Takeaways

- Asynchronous execution allows long-running Agent tasks to execute in the background.
- Users receive an immediate acknowledgement instead of waiting.
- A defined job state machine (pending/running/completed/failed/cancelled) keeps status reporting consistent.
- Polling and webhooks are the two common ways Clients learn when a job is done, each with trade-offs.
- Idempotency keys prevent duplicate jobs when a request is retried.
- Heartbeats and timeouts let the system detect and recover from stuck or crashed jobs.
- Task queues like Celery handle scheduling, retries, and distribution in production, rather than raw `asyncio`.
- Background workers process the task independently.
- This approach improves scalability and user experience.
- Production AI systems commonly use asynchronous execution for computationally expensive workflows.
