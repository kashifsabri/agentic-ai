
```text

```

The deployment pipeline hasn't changed.

What changed?

The **Prompt**.

Production AI systems treat prompts and models as versioned assets,

- Accuracy
- Tool selection
- Reasoning
- Safety

# Treat Prompts as Code, Not as a String Buried in Application Logic

This is the most practical addition to make here: the introduction's example (a developer "updates the system prompt") implies prompts live somewhere editable — worth being explicit about _where_ and _how_ they should actually live in a production codebase.

```text
Weak practice:
prompt = "You are a helpful customer support assistant."
→ hardcoded inline, buried inside application logic, easy to
  edit accidentally, no history of what it used to say

Strong practice ("prompt-as-code"):
→ Prompts live in their own dedicated files (e.g. prompts/support_v5.txt
  or a structured prompts/ directory), committed to the SAME
  version control system (e.g. git) as the rest of the codebase
```

Storing prompts as their own tracked files, rather than as inline strings, gives you the same benefits developers already rely on for code:

```text
- A full history of every change, and who made it, and when
- Diffs showing EXACTLY what changed between versions
  (not just "the prompt is different" but "this specific
  sentence was added/removed")
- Code review (pull requests) BEFORE a prompt change reaches
  production, the same as any other code change
- The ability to revert a single prompt change without touching
  unrelated code
```

This turns "prompt versioning" from an abstract policy into a concrete engineering practice: prompts get the exact same rigor as application code, because in a very real sense, a prompt _is_ code — it directly determines system behavior, the same way a function body does.

# What is Prompt Versioning?

Prompt Versioning is the practice of assigning a unique version to every significant prompt change.

Example

```text
Prompt v1.0

↓

Prompt v1.1

↓

Prompt v1.2
```

This allows teams to identify exactly which prompt generated a response.

# The Hidden Risk of Floating Model Aliases

This is a specific, very real production risk worth calling out directly, and it connects to the "version pins a configuration" point from the previous chapter.

Many providers offer both **pinned snapshot versions** and **floating aliases** for their models:

```text
Pinned snapshot (explicit, stable)
→ e.g. "claude-sonnet-4-6" or a dated snapshot identifier
→ This EXACT model version never silently changes underneath you

Floating alias (convenient, but risky in production)
→ e.g. "latest" or an unversioned alias that automatically
  points to whatever the provider's newest model currently is
→ The provider can update what "latest" points to at ANY time,
  WITHOUT you changing a single line of your own code
```

The risk: if your Agent config specifies a floating alias instead of a pinned version, your Agent's behavior can change — sometimes significantly — the moment the provider ships an update, with **zero corresponding version bump on your side**. This directly breaks the versioning discipline from the previous chapter: your logs might say "Agent Version 2.1, Model: latest" both before and after a real behavioral shift, making the version metadata actively misleading rather than helpful.

```text
Best practice: always pin an explicit model snapshot version in
production, and treat upgrading to a new model snapshot as its
own deliberate, evaluated, versioned change — not something that
happens automatically in the background.
```

Floating aliases are fine for casual experimentation or development, but production systems that care about reproducibility and safe rollback should avoid them for exactly the reason this whole chapter exists: to know precisely which configuration produced which behavior.

# Don't Just Version Changes — Gate Them With Evaluation First

The example above mentions "evaluation shows a drop in accuracy" almost in passing — worth making this a first-class step in the lifecycle rather than something that happens informally after the fact.

```text
Weak process:
Change prompt/model → deploy → wait for user complaints →
investigate

Strong process:
Change prompt/model → run against a fixed "golden" test set of
representative inputs with known-good expected outputs/behavior
→ compare new version's results against the CURRENT production
version's results on the SAME test set → only promote to
production if the new version doesn't regress on this test set
```

This is the same underlying idea as automated tests gating a traditional code deployment, applied to prompts and models specifically. A "golden dataset" — a curated, stable set of representative test cases — lets you catch a regression like "the new model handles refund requests worse than the old one" _before_ it reaches real customers, rather than discovering it through complaints. This connects prompt/model versioning directly to evaluation practices, and is exactly the kind of automated gate that belongs in the CI/CD pipeline covered in the next chapter.

# Best Practices

Version prompts independently from application code — and store them as their own tracked files in version control, reviewed like any other code change.

Track every model upgrade, and always pin an explicit model snapshot rather than a floating alias in production.

Record versions with every Agent execution.

Evaluate new prompt and model versions against a golden dataset before deployment, not just informally after release.

Maintain a history of previous versions.

# Common Beginner Mistakes

### Mistake 1

Editing prompts directly in production.

Every meaningful prompt change should receive a new version.

---

### Mistake 2

Upgrading models without evaluation.

Different models may produce different behavior.

---

### Mistake 3

Versioning only the application code.

Prompt and model changes are equally important.

---

### Mistake 4

Failing to record version information.

Without version metadata,

production debugging becomes much harder.

---

### Mistake 5

Storing prompts as inline strings buried in application code instead of dedicated, version-controlled files.

This loses diff history, code review, and independent rollback capability for prompt changes specifically.

---

### Mistake 6

Using a floating model alias (like "latest") in production instead of a pinned snapshot version.

This lets model behavior change silently, with no corresponding version bump, undermining the entire point of versioning.

# Interview Tip

A common interview question is:

> **Why should Prompts and Models be versioned separately from the Agent?**

A good answer is:

Prompts and models can significantly change an AI Agent's behavior even when the application code remains unchanged. Independent versioning allows teams to track exactly which prompt and model produced a response, compare performance across releases, perform safe rollbacks, and investigate production issues more effectively.

---

# Interview Tip

A stronger follow-up worth preparing for:

> **What's the risk of using a "latest" model alias instead of a pinned model version in production?**

Answer:

A floating alias like "latest" can be repointed to a new underlying model by the provider at any time, changing your Agent's behavior without any corresponding change or version bump on your side. This breaks the core purpose of versioning — knowing exactly which configuration produced a given response — since your own version metadata would remain unchanged even though the actual model behind it has changed. Production systems should pin an explicit model snapshot and treat any upgrade as its own deliberate, evaluated, versioned change.

# Key Takeaways

- Prompts and models directly influence Agent behavior.
- Prompts should be stored as version-controlled files ("prompt-as-code"), not inline strings, to get diff history, review, and independent rollback.
- Small prompt changes can produce significantly different responses.
- Model upgrades may affect accuracy, latency, and cost — and floating aliases like "latest" can change behavior silently, without a version bump, so production systems should pin explicit model snapshots.
- Prompt and model changes should be gated by automated evaluation against a golden dataset before deployment, not just discovered through user complaints afterward.
- Version prompts and models independently from Agent code.
- Recording version information improves debugging, evaluation, and deployment safety.
