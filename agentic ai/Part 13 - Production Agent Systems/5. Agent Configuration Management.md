# Introduction

Imagine you've built an AI Customer Support Agent.

Initially, your code looks like this:

```python
MODEL = "gpt-5"

TEMPERATURE = 0.7

MAX_TOKENS = 4000

TIMEOUT = 30
```

Everything works.

A few weeks later you need:

- A different model in production
- A lower temperature
- A longer timeout
- Different API endpoints
- New feature flags

Do you edit the source code every time?

No.

Production systems separate **configuration** from **application logic**.

This practice is called **Configuration Management**.

---

# What is Agent Configuration Management?

Agent Configuration Management is the practice of storing and managing configurable values separately from the application's source code.

Instead of hardcoding values,

the Agent loads them from external configuration sources.

This makes the system easier to deploy,

maintain,

and update.

---

# Why Do We Need Configuration Management?

AI Agents contain many settings that change over time.

Examples include:

- Model name
- Temperature
- Maximum tokens
- Timeout values
- Retry limits
- Tool permissions
- Feature flags
- API endpoints

Hardcoding these values makes maintenance difficult.

# Environment Variables

One of the most common approaches is using environment variables.

Example

```text
MODEL=gpt-5

TEMPERATURE=0.2

TIMEOUT=60
```

The application reads these values during startup.

---

# Python Example

Loading configuration from environment variables:

```python
import os

MODEL = os.getenv("MODEL", "gpt-5")

TEMPERATURE = float(
    os.getenv("TEMPERATURE", "0.2")
)

TIMEOUT = int(
    os.getenv("TIMEOUT", "30")
)
```

This allows configuration to change without modifying the source code.

---

# Typed Configuration with Pydantic Settings

Reading raw environment variables one by one (as above) works for small projects, but scales poorly — typos in variable names, missing type conversion, and no validation are all easy to miss until runtime. A typed settings class solves this.

```python
from pydantic_settings import BaseSettings
from pydantic import Field

class AgentConfig(BaseSettings):
    model: str = Field(default="gpt-5")
    temperature: float = Field(default=0.2, ge=0.0, le=2.0)
    max_tokens: int = Field(default=4000, gt=0)
    timeout: int = Field(default=30, gt=0)
    api_key: str  # required, no default — startup fails fast if missing

    class Config:
        env_file = ".env"

config = AgentConfig()  # raises a clear validation error if something is wrong
```

Benefits over manual `os.getenv` calls:

- Type conversion and range validation happen automatically (`ge`, `le`, `gt`)
- Required fields (like `api_key`) fail loudly at startup instead of causing a confusing error mid-request
- IDEs get autocomplete and type checking for `config.model`, `config.temperature`, etc.

# Configuration Precedence (Hierarchy)

When configuration can come from multiple sources, there needs to be a clear, predictable order for which one wins.

```text
1. Hardcoded defaults        (lowest priority)
2. Configuration file (.env, config.yaml)
3. Environment variables
4. Runtime overrides / command-line flags   (highest priority)
```

```python
config = AgentConfig(
    _env_file=".env",           # loaded first
    temperature=runtime_override_value  # explicit override wins
)
```

```text
Default:    temperature = 0.2
Config file: temperature = 0.3
Env var:     TEMPERATURE=0.5
Result:      0.5  (env var wins, since it's higher precedence than the file)
```

Documenting this precedence clearly (and keeping it consistent) prevents confusing situations where "I set it in the config file but it's not taking effect" — usually because something higher in the hierarchy is silently overriding it.

# Secret Managers

API keys and credentials shouldn't live in plain environment variables or `.env` files in production — dedicated secret managers provide encryption, access control, and audit logging.

```python
import boto3
import json

def load_secret(secret_name: str) -> dict:
    client = boto3.client("secretsmanager", region_name="us-east-1")
    response = client.get_secret_value(SecretId=secret_name)
    return json.loads(response["SecretString"])

secrets = load_secret("prod/agent/api-keys")
api_key = secrets["openai_api_key"]
```

```text
Options:
- AWS Secrets Manager / Parameter Store
- HashiCorp Vault
- Google Secret Manager
- Azure Key Vault
```

Unlike a `.env` file, these systems support automatic rotation, fine-grained access policies (who/what can read which secret), and an audit trail of every access — all things a plain environment variable can't provide.

# Hot-Reloading Configuration

Some settings (like a feature flag or a temperature tweak) shouldn't require a full redeploy and restart to take effect. Hot-reloading lets the application pick up changes while running.

```python
import time
import threading

class LiveConfig:
    def __init__(self, path: str):
        self.path = path
        self._config = self._load()
        threading.Thread(target=self._watch, daemon=True).start()

    def _load(self):
        return AgentConfig(_env_file=self.path)

    def _watch(self):
        while True:
            time.sleep(30)
            self._config = self._load()  # periodically refresh

    @property
    def current(self):
        return self._config

live_config = LiveConfig(".env")
# Elsewhere in the app: live_config.current.temperature
```

This is especially useful for feature flags and tunable parameters that operators want to adjust without triggering a full deployment pipeline — restart-required settings (like changing the database connection) are usually kept separate from hot-reloadable ones.

# Feature Flags in Practice

Sometimes,

new Agent features should be enabled only for certain users.

Example

```text
AI Search

↓

Enabled

-----------------

Auto Planner

↓

Disabled
```

Feature flags allow capabilities to be turned on or off without redeploying the application.

For anything beyond a couple of simple flags, teams typically move to a dedicated feature-flag service rather than managing flags as raw config values:

```python
import ldclient
from ldclient.config import Config

ldclient.set_config(Config("sdk-key"))
client = ldclient.get()

user = {"key": user_id}
if client.variation("auto-planner-enabled", user, False):
    use_auto_planner()
```

Services like LaunchDarkly or Unleash add capabilities plain config can't easily provide: gradual rollout percentages (enable for 10% of users), per-user targeting, and instant toggling without any deploy or restart at all.

# Best Practices

Never hardcode configuration values.

Use typed, validated configuration (e.g., Pydantic Settings) instead of scattered `os.getenv` calls.

Store secrets separately from normal configuration, using a dedicated secret manager.

Validate configuration during application startup — fail fast on missing required values.

Define and document a clear configuration precedence order.

Use environment-specific configuration.

Consider hot-reloading for frequently tuned, non-critical settings.

Use a dedicated feature-flag service for gradual rollouts and per-user targeting.

Keep configuration under version control where appropriate (excluding secrets).

# Common Beginner Mistakes

### Mistake 1

Hardcoding API keys or model names.

Configuration should be external.

---

### Mistake 2

Using the same configuration for every environment.

Development and production usually require different settings.

---

### Mistake 3

Not validating configuration values.

Invalid settings can cause production failures.

---

### Mistake 4

Storing secrets in source code.

Use environment variables or dedicated secret management systems.

---

### Mistake 5

Reading raw environment variables everywhere without a typed schema.

This leads to inconsistent type conversion, silent typos, and missing-value errors that only surface at runtime.

---

### Mistake 6

Having no clear precedence order across multiple configuration sources.

Without one, it's unclear which value "wins" when a default, a config file, and an environment variable disagree.

# Interview Tip

A common interview question is:

> **Why should AI Agents use Configuration Management?**

A good answer is:

Configuration Management separates configurable values such as model names, timeouts, retry limits, API endpoints, and feature flags from the application's source code, typically using a typed and validated schema (e.g., Pydantic Settings), a clear precedence hierarchy, and dedicated secret managers for credentials. This makes AI systems easier to maintain, deploy across multiple environments, and update — sometimes even hot-reloaded — without modifying or redeploying the application itself.

# Key Takeaways

- Configuration Management separates settings from application code.
- Typed configuration classes (e.g., Pydantic Settings) validate values and fail fast on errors.
- A clear precedence order (defaults → file → env vars → runtime overrides) avoids confusing conflicts.
- Secret managers (AWS Secrets Manager, Vault, etc.) provide rotation, access control, and auditing that plain env vars can't.
- Hot-reloading lets some settings update without a full restart or redeploy.
- Dedicated feature-flag services support gradual rollouts and per-user targeting beyond simple on/off flags.
- Production AI Agents rely on external configuration sources.
- Different environments typically use different configurations.
- Secrets should never be hardcoded.
- Good configuration management improves maintainability, security, and deployment flexibility.
