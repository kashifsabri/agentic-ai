# Introduction

Imagine you've built Version 2 of your AI Agent.

It includes:

- Better prompts
- Improved planning
- Faster tools
- Lower cost

You deploy it directly to Production.

Unfortunately,

an unexpected bug causes the Agent to generate incorrect responses for every user.

Now thousands of users are affected.

Could this have been avoided?

Yes.

Instead of deploying the new version to everyone at once,

production systems use **Deployment Strategies** to release changes safely.

---

# What are Deployment Strategies?

Deployment Strategies are controlled methods of releasing a new version of an application into production.

Instead of replacing the old version immediately,

the system gradually introduces the new version while minimizing risk.

---

# Why Do We Need Deployment Strategies?

Every deployment introduces risk.

Possible issues include:

- Software bugs
- Prompt regressions
- Model behavior changes
- Tool failures
- Performance degradation
- Higher costs

Deployment strategies reduce the impact of these problems.

# 1. Rolling Deployment

A Rolling Deployment updates servers one at a time.

```text
Server 1

↓

Update

↓

Server 2

↓

Update

↓

Server 3

↓

Update
```

Advantages:

- No downtime
- Gradual rollout

Disadvantages:

- Old and new versions temporarily run together.

---

# 2. Blue-Green Deployment

Two identical production environments exist.

```text
Blue

↓

Current Version

-------------------

Green

↓

New Version
```

Traffic is switched only after the new environment is verified.

Advantages:

- Very fast rollback
- Minimal downtime

Disadvantages:

- Requires duplicate infrastructure.

---

# 3. Canary Deployment

Only a small percentage of users receive the new version initially.

```text
100% Users

↓

5%

↓

Version 2

-------------------

95%

↓

Version 1
```

If everything works well,

the rollout gradually increases.

Advantages:

- Low deployment risk
- Real production testing

Disadvantages:

- Requires traffic routing and monitoring.

---

# Canary Rollouts Need Enough Traffic to Be Trustworthy

Worth adding a statistical caution here, since "monitor 5% of traffic" can be misleading if that 5% is too small a sample to actually detect a real problem.

```text
If a regression only affects, say, 1 in 500 requests,
and your canary is only receiving 5% of a modest traffic volume,
you might process very few "bad" requests during the canary
window purely by chance — not because the new version is fine,
but because the sample size hasn't caught the issue yet
```

This is the same underlying concern as statistical significance in any experiment: a small sample can fail to detect a real effect, producing false confidence ("no issues found!") when the truth is simply "not enough data yet." Practical implications: canary duration and traffic percentage should be chosen based on your actual traffic volume and the size of regression you need to reliably detect — a canary that runs for only a few minutes on low traffic gives much weaker evidence than one that runs long enough to accumulate a statistically meaningful sample. Don't treat "the canary looked fine" as equivalent to "the canary looked fine, on a large enough sample to trust that conclusion."

# 4. Shadow Deployment

The new Agent receives real production requests,

but its responses are **not** returned to users.

```text
User Request

↓

Version 1

↓

User Response

----------------------

Same Request

↓

Version 2

↓

Internal Comparison
```

This allows engineers to evaluate the new version safely.

---

# The Hidden Problem With Shadow Deployment: Side Effects

This deserves real attention, since it's a subtle but serious practical issue that the simple diagram above glosses over — and it connects directly back to the Idempotency chapter.

If Version 2 is a full, real Agent processing a genuine copy of the request, what happens when that request would normally trigger a **real-world side effect** — sending an email, charging a card, creating a database record, booking a flight?

```text
Naive shadow deployment (WRONG for side-effecting actions):
→ Version 1 processes the request → sends a REAL email → user
  gets it (correct, expected)
→ Version 2 ALSO processes the same request internally → if
  its tools aren't handled specially, it could ALSO send a
  REAL email → user gets a duplicate

This is a genuine "duplicate action" problem, similar in spirit
to the retry-without-idempotency problem covered earlier — except
here it's caused by intentionally running two versions on the
same request, not a network failure.
```

The standard solution: in shadow mode, any tool call with a genuine side effect must be **mocked or stubbed** for the shadow (Version 2) path — the Agent still runs its full reasoning and decides it _would_ call `send_email()`, and that decision gets logged and compared, but the actual email-sending code doesn't execute for the shadow copy. Read-only operations (search, retrieval, calculations) are generally safe to actually execute in both paths, since they have no side effects to duplicate — but anything that writes, sends, charges, or creates needs this careful handling, or shadow deployment silently causes real, duplicated production effects.

# 5. Feature Flags

Instead of deploying different applications,

specific features are enabled only for selected users.

```text
Feature

↓

Enabled

↓

Premium Users

--------------------

Disabled

↓

Everyone Else
```

Features can be activated without redeploying the application.

---

# Feature Flags Are the Concrete Mechanism Behind "Deployed ≠ Released"

The previous chapter (Agent Deployment) introduced the distinction between a version being _deployed_ (running in production infrastructure) and _released_ (actually receiving user traffic). Feature flags are the most direct, literal implementation of that distinction.

```text
Without feature flags:
"Deployed" and "released" are basically the same moment — the
code goes live, and it's immediately active for everyone hitting it

With feature flags:
The new code can be fully deployed, running, and verified — but
sit BEHIND a flag that's off for everyone, until someone
deliberately flips it on, for some users, at a chosen moment
```

This decoupling is powerful specifically because it separates two different kinds of risk: _deployment risk_ (did the code build and start correctly?) from _release risk_ (does the new behavior actually work well for real users?). You can fully resolve the first risk (confirm it's deployed and healthy) long before taking on the second (exposing it to any real user), and even then, exposure can be controlled precisely — by user segment, by percentage, or by specific accounts — independent of the deployment process itself.

---

# These Strategies Are Usually Combined, Not Chosen Exclusively

Worth correcting a natural misreading of the comparison table below: these five strategies aren't mutually exclusive alternatives where you pick exactly one — in practice, they're frequently layered together.

```text
A common real combination:
→ Blue-Green infrastructure (two full environments, ready to switch)
→ PLUS Canary-style gradual traffic shifting (not switching 100%
  at once, even within the "green" environment)
→ PLUS Feature Flags controlling specific new capabilities within
  that release, independent of the version rollout itself
→ PLUS Shadow Deployment run BEFORE any of the above, to validate
  behavior with zero user-facing risk first
```

Thinking of these as a toolbox to combine, rather than a single choice to make once, better reflects how mature production systems actually manage releases — different techniques address different, complementary risks (infrastructure risk, traffic-exposure risk, feature-specific risk, behavioral-validation risk), and a robust release process often uses several at once.

# Comparing Deployment Strategies

|---|---|---|---|
|Rolling|Low|Moderate|Medium|
|Blue-Green|Very Low|Very Fast|Low|
|Canary|None|Fast|Very Low|
|Shadow|None|Easy|Very Low|
|Feature Flags|None|Immediate|Very Low|

Different organizations choose different strategies based on their requirements.


Production systems often manage feature flags through dedicated services rather than hardcoded values.

# Industry Insight

Most large AI companies avoid deploying directly to all users.

Instead, they use strategies such as:

- Canary Releases
- Blue-Green Deployments
- Feature Flags
- Shadow Deployments

These approaches reduce production risk while allowing continuous delivery of improvements.

---

# Best Practices

Start with a small rollout.

Ensure canary sample sizes are large enough (in volume and duration) to actually detect the regressions you care about.

Monitor every deployment closely.

Mock or stub side-effecting tool calls during Shadow Deployment to avoid duplicated real-world actions.

Define rollback criteria before deployment.

Use automated deployment pipelines.

Compare new and old versions during rollout.

Combine strategies where it makes sense, rather than treating them as mutually exclusive choices.

Never assume a deployment is successful without monitoring.

---

# Common Beginner Mistakes

### Mistake 1

Deploying new versions to all users immediately.

Use gradual rollout strategies.

---

### Mistake 2

Deploying without a rollback plan.

Every deployment should have a recovery strategy.

---

### Mistake 3

Ignoring production metrics after deployment.

Monitor latency, errors, and user feedback continuously.

---

### Mistake 4

Assuming successful testing guarantees a successful deployment.

Production environments can reveal issues that testing environments do not.

---

### Mistake 5

Running Shadow Deployment without mocking side-effecting tools.

This can cause the shadow version to actually execute real-world actions (sending emails, charging cards) that duplicate what the live version already did.

---

### Mistake 6

Treating a small or short canary window as sufficient evidence of safety, without considering whether the sample size is large enough to detect the regression you're worried about.

# Interview Tip

A common interview question is:

> **What is the difference between Blue-Green and Canary Deployment?**

A good answer is:

Blue-Green Deployment maintains two complete production environments and switches all traffic from the old environment to the new one when ready. Canary Deployment gradually releases the new version to a small percentage of users, monitors its performance, and slowly increases traffic if no issues are detected.

---

# Interview Tip

A stronger follow-up worth preparing for:

> **What's a specific risk with Shadow Deployment that a simple diagram might not show?**

Answer:

If the shadow version's tools aren't specially handled, running a real copy of a request through it can cause genuine, duplicated real-world side effects — like sending a second email or creating a duplicate database record — even though its response is never shown to the user. The response being suppressed doesn't stop the underlying tool calls from actually executing. The fix is to mock or stub any side-effecting tool calls in the shadow path, while still letting the Agent's reasoning and decision-making run for real, so the comparison is meaningful without duplicating real-world effects.

# Key Takeaways

- Deployment Strategies reduce the risk of releasing new AI Agent versions.
- Rolling, Blue-Green, Canary, Shadow, and Feature Flag deployments are common production strategies, and are typically combined rather than chosen exclusively.
- A canary rollout's results are only trustworthy if the sample size (traffic volume and duration) is large enough to actually detect the regression being watched for.
- Shadow Deployment requires mocking or stubbing side-effecting tool calls, or it can cause real, duplicated production actions despite suppressing the response shown to users.
- Feature Flags are the concrete mechanism behind decoupling "deployed" from "released," introduced in the previous chapter.
- Gradual rollouts help identify issues before they affect all users.
- Monitoring and rollback are essential parts of every deployment strategy.
- Modern AI platforms rarely deploy directly to 100% of users.
