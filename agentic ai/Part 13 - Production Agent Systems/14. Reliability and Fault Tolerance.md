# What is Reliability?

Reliability is the ability of a system to consistently perform its intended function over time.

A reliable AI Agent:

- Produces correct results
- Handles expected workloads
- Recovers from temporary issues
- Operates consistently

Users trust reliable systems because they behave predictably.

# How Reliability Is Actually Measured

"Reliability" so far has been described qualitatively. In practice, production teams measure and commit to it with specific numbers — worth knowing this vocabulary for interviews.

```text
SLA (Service Level Agreement)
→ A formal, often contractual, commitment to customers about
  expected reliability (e.g. "99.9% uptime, or we issue credits")

SLO (Service Level Objective)
→ An internal target a team aims for, usually stricter than the
  SLA, giving some safety margin
  (e.g. internal target of 99.95% even if the SLA promises 99.9%)

Error Budget
→ The amount of "allowed failure" implied by an SLO — if your
  target is 99.9% uptime, you have an implicit budget of about
  0.1% downtime to "spend" before you're violating your own target
```

"Nines" is common shorthand for availability targets:

```text
99%      ("two nines")   ≈ 3.65 days of downtime per year
99.9%    ("three nines")  ≈ 8.76 hours of downtime per year
99.99%   ("four nines")   ≈ 52.6 minutes of downtime per year
99.999%  ("five nines")   ≈ 5.26 minutes of downtime per year
```

Each additional nine is dramatically harder (and more expensive) to achieve than the last — this is why teams pick a target deliberately rather than just aiming for "as reliable as possible." An error budget also gives teams a practical decision tool: if you're within budget, you can ship new features and take some risk; if you've exhausted your error budget, the priority shifts to stability work until you're back within target.

# What is Fault Tolerance?

Fault Tolerance is the ability of a system to continue operating even when one or more components fail.

Instead of stopping completely,

the system:

- Retries
- Falls back
- Uses alternative services
- Continues with partial functionality

The goal is graceful degradation instead of total failure.

---

# Reliability vs Fault Tolerance

|Reliability|Fault Tolerance|
|---|---|
|Consistent operation|Continues despite failures|
|Prevents failures|Handles failures|
|Focuses on stability|Focuses on recovery|

A production system needs both.

# Not All Failures Deserve a Retry: Transient vs Permanent

This is a critical distinction the chapter's retry examples gloss over, and it directly sets up the next chapter on idempotency.

```text
Transient failure (worth retrying)
→ Temporary network blip, momentary service overload, a
  timeout that might succeed on the next attempt
→ Examples: connection reset, 503 Service Unavailable, timeout

Permanent failure (retrying is pointless, or even harmful)
→ The request itself is fundamentally invalid, and retrying
  the exact same request will fail the exact same way every time
→ Examples: invalid API key (401), malformed request (400),
  insufficient permissions (403), resource genuinely doesn't
  exist (404)
```

Retrying a permanent failure doesn't just waste time and money — it can also delay surfacing a real problem (like an expired credential) that actually needs a human to fix, while your system quietly keeps retrying something that will never succeed. Well-designed retry logic checks the _type_ of failure (often via the HTTP status code or error type) before deciding whether a retry makes sense at all, rather than blindly retrying every failure the same way.

# Timeouts Are a Real Design Decision, Not Just "Add One"

The list above mentions timeouts, but choosing a timeout VALUE deserves its own attention — it's a genuine tradeoff, not a default you set once and forget.

```text
Timeout too SHORT
→ Slow-but-legitimate responses get killed prematurely and
  treated as failures, triggering unnecessary retries/fallbacks
→ This can actually make a slow-but-working system look broken

Timeout too LONG
→ A truly hung or dead connection ties up resources (worker
  threads, connection pool slots) far longer than necessary
→ This connects back to the abrupt-disconnect uncertainty
  discussed in the MCP Connection Lifecycle chapter — a long
  timeout means staying in that uncertain "did it succeed or
  not" state for longer before taking any recovery action
```

Good timeout values are typically informed by real observed latency data (e.g. "99% of successful responses complete within 3 seconds, so timeout at 8 seconds gives real margin without waiting forever on truly dead requests") rather than picked arbitrarily.

# The Bulkhead Pattern: Isolating Failures From Each Other

Worth introducing a named pattern not yet covered, which complements circuit breakers nicely: the **bulkhead pattern**, named after the watertight compartments in a ship's hull that stop one flooded section from sinking the entire vessel.

```text
Without bulkheads:
→ All requests share the same pool of resources (e.g. one
  shared connection pool, one shared thread pool)
→ If the Weather Tool starts hanging, it can exhaust the
  ENTIRE shared resource pool, starving unrelated requests
  to the Database Tool or Email Tool too

With bulkheads:
→ Each dependency (Weather Tool, Database Tool, Email Tool)
  gets its OWN isolated pool of resources (its own connection
  limit, its own thread pool, its own queue)
→ If the Weather Tool hangs and exhausts ITS pool, the
  Database and Email tools are completely unaffected, since
  they're drawing from separate pools
```

This is exactly the kind of protection a single circuit breaker doesn't fully provide on its own — a circuit breaker stops calling a _specific_ failing dependency, but without bulkheads, that dependency's failures could still have already exhausted shared resources before the circuit breaker even trips. The two patterns are complementary: bulkheads contain the blast radius of a failure, circuit breakers stop calling the failing thing once detected.

# Health Checks: Liveness vs Readiness

Briefly worth distinguishing, since "health checks" gets listed as a technique later without detail, and the two common types answer genuinely different questions.

```text
Liveness check
→ "Is this process still running at all, or has it hung/crashed?"
→ Failing this typically triggers a restart of the component

Readiness check
→ "Is this process running AND actually ready to accept new
  work right now?" (e.g. has it finished initializing, is it
  not currently overloaded)
→ Failing this doesn't necessarily restart anything — it just
  temporarily stops new traffic from being routed to it, until
  it reports ready again
```

A component can be "alive" (not crashed) but not "ready" (still starting up, or temporarily overloaded) — treating these as the same check leads to either restarting healthy-but-busy components unnecessarily, or routing traffic to components that are running but not actually able to help yet.

# Python Example

A simple retry:

```python
MAX_RETRIES = 3

for attempt in range(MAX_RETRIES):
    try:
        result = call_api()
        break
    except Exception:
        print("Retrying...")
```

Production systems usually combine retries with exponential backoff and timeout policies, and — per the point above — should also check whether the specific failure is even worth retrying in the first place.

# Best Practices

Design assuming failures will occur.

Define reliability targets explicitly (SLOs), and track an error budget rather than vaguely aiming for "as reliable as possible."

Implement retries with limits, and only for failures classified as transient — not permanent ones.

Choose timeout values based on real observed latency data, not arbitrary defaults.

Isolate dependencies using the bulkhead pattern so one failing component can't exhaust shared resources needed by others.

Use fallback services where appropriate.

Save progress for long-running workflows.

Distinguish liveness from readiness in health checks.

Fail gracefully instead of crashing.

Monitor recovery mechanisms continuously.

# Common Beginner Mistakes

### Mistake 1

Assuming external services are always available.

Every dependency can fail.

---

### Mistake 2

Retrying forever.

Always define retry limits.

---

### Mistake 3

Restarting long workflows from the beginning.

Checkpointing reduces wasted work.

---

### Mistake 4

Treating every failure as fatal.

Many failures can be recovered automatically.

---

### Mistake 5

Retrying permanent failures (like invalid credentials) the same way as transient ones.

This wastes resources and can delay a human noticing a real problem that needs fixing.

---

### Mistake 6

Sharing one resource pool across all dependencies, allowing one hanging dependency to exhaust resources needed by unrelated, healthy dependencies.

The bulkhead pattern isolates this.

# Interview Tip

A common interview question is:

> **What is the difference between Reliability and Fault Tolerance?**

A good answer is:

Reliability is the ability of a system to consistently perform its intended function over time. Fault Tolerance is the ability to continue operating even when components fail. Reliability focuses on stable operation, while Fault Tolerance focuses on recovering from failures using techniques such as retries, fallbacks, checkpointing, and graceful degradation.

---

# Interview Tip

A stronger follow-up worth preparing for:

> **Should every failed request be retried?**

Answer:

No — only failures classified as transient (timeouts, temporary overload, connection resets) are worth retrying, since a retry gives them a genuine chance to succeed. Permanent failures (invalid credentials, malformed requests, missing permissions) will fail identically every time, so retrying them wastes resources and can delay a human noticing and fixing the actual underlying problem. Good retry logic checks the failure type — often via status code — before deciding whether to retry at all.

# Key Takeaways

- Reliability ensures consistent system behavior, and is concretely measured using SLAs, SLOs, and error budgets, often expressed in "nines" of availability.
- Fault Tolerance enables systems to recover from failures.
- Retry logic should distinguish transient failures (worth retrying) from permanent ones (retrying is pointless or harmful).
- Timeout values are a real tradeoff — too short causes false failures, too long wastes resources on dead connections.
- The bulkhead pattern isolates each dependency's resources so one failing component can't starve others; it complements circuit breakers rather than replacing them.
- Liveness checks ask "is it running," readiness checks ask "is it able to accept work right now" — they're different questions.
- Production AI systems should assume failures will occur.
- Retries, fallbacks, checkpointing, and graceful degradation improve resilience.
- Reliable AI systems are designed to recover, not simply to avoid failure.
