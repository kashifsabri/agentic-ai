# Why Are AI Agents Expensive?

Unlike traditional software,

every AI request consumes computational resources.

Each request may involve:

- One or more LLM calls
- Tool executions
- Memory retrieval
- Vector database searches
- API requests
- Token generation

Every operation contributes to the overall cost.

---

# Where Does the Cost Come From?

A typical Agent workflow looks like:

```text
User Request

↓

Memory Retrieval

↓

LLM Call

↓

Tool Call

↓

Second LLM Call

↓

Final Response
```

Each step consumes resources.

More steps generally mean higher costs.

---

# What are Tokens?

Large Language Models process text as **tokens** rather than words.

For example,

the sentence:

```text
The weather is sunny today.
```

is broken into multiple tokens before being processed.

Most commercial LLM providers charge based on:

- Input Tokens
- Output Tokens

More tokens generally mean higher costs.

# Common Cost Drivers

Production AI systems commonly incur costs from:

- Large prompts
- Long conversation history
- Multiple LLM calls
- Expensive models
- Repeated tool calls
- Large context windows
- Long generated responses

Understanding these drivers is the first step toward optimization.

# Optimization Strategy 1 — Use the Right Model

Not every task requires the largest model.

Example:

```text
Greeting User

↓

Small Model

--------------------

Legal Analysis

↓

Large Model
```

Choosing an appropriate model can significantly reduce cost.

---

# Making "Use the Right Model" Concrete: Model Routing / Cascading

The example above shows choosing a model _upfront_ based on task type. A related, more dynamic pattern worth knowing by name: **model cascading** (or routing).

```text
Request arrives

↓

Try a small, cheap, fast model FIRST

↓

Is the response confident / high-quality enough?

├── Yes → return it (cheap path, most requests)

└── No  → escalate to a larger, more expensive model
          and use ITS response instead
```

Instead of deciding once per task category, cascading decides per-request, at runtime, based on some confidence or quality signal (this could be the model's own stated confidence, a classifier trained to judge output quality, or simple heuristics like response length or specific failure patterns). Since many real-world requests are actually simple, this can substantially reduce average cost — the expensive model is only invoked for the harder subset of requests that genuinely need it, rather than being used for every request "just in case."

```text
↓
```


Smaller prompts reduce both cost and latency.

# Optimization Strategy 3 — Cache Results

Suppose thousands of users ask:

```text
What are your business hours?
```

Instead of generating a new response each time,

the application can reuse a cached response.

```text
First Request

↓

Generate Response

↓

Cache

↓

Future Requests

↓

Return Cached Result
```

This avoids unnecessary model calls.

---

# Two Very Different Kinds of Caching Worth Distinguishing

"Cache results" undersells how much nuance is actually here — there are at least two distinct caching strategies with very different capabilities, and mixing them up is a common gap in understanding.

```text
Exact-Match Caching
→ Only works if a NEW query is character-for-character identical
  (or normalized-identical) to a previously cached query
→ "What are your business hours?" hits the cache
→ "What time do you open?" MISSES the cache entirely, even though
  it means the same thing — the text doesn't match

Semantic Caching
→ Uses embeddings (from the Vector Databases chapter) to compare
  the MEANING of a new query against previously cached queries
→ "What time do you open?" can be matched to the cached answer
  for "What are your business hours?" because their embeddings
  are highly similar, even though the wording differs
→ Requires a similarity threshold decision: how close is "close
  enough" to safely reuse a cached answer, without returning a
  wrong answer to a subtly different question
```

Semantic caching is strictly more powerful (it catches far more repeat questions than exact matching), but it's also riskier — an overly loose similarity threshold can return a cached answer to a question that was actually different in an important way. This is a direct, practical application of the vector similarity search concepts covered earlier, now used for cost optimization rather than document retrieval.

---

# Prompt Caching: A Different, More Specific Concept

Worth distinguishing from both of the above: many LLM providers also offer **prompt caching** (sometimes called context caching) as a distinct API-level feature — not something you build yourself, but something the provider offers.

```text
Without prompt caching:
Every request re-processes the ENTIRE prompt from scratch,
including a long, unchanging system prompt or document that's
included in every single call

With prompt caching:
The provider caches the internal processing state for a repeated,
UNCHANGING prefix (e.g. your system prompt + a large reference
document), so subsequent requests reusing that same prefix are
cheaper and faster, since that portion doesn't need to be
reprocessed from scratch
```

This is especially valuable for applications with a large, mostly-static system prompt or a big reference document included in every call (e.g. an agent with a long tool-definition list, or a RAG-heavy prompt with substantial fixed instructions) — prompt caching specifically discounts and speeds up the repeated, unchanged portion, distinct from either exact-match or semantic response caching described above, which cache the _final answer_, not the _processing of the input_.

Avoid calling tools when the information is already available.

Instead of:

```text

↓
```

# A Common Misconception: Streaming Doesn't Reduce Cost

Worth clarifying directly, since it's an easy thing to assume incorrectly: **streaming** (displaying the response token-by-token as it's generated, rather than waiting for the full response) improves _perceived_ latency — the user sees output starting almost immediately, rather than staring at a blank screen — but it does **not** reduce the actual number of tokens generated, and therefore does not reduce cost.

```text
Non-streaming: generate all 500 tokens → display all at once
Streaming:      generate all 500 tokens → display each as it arrives

Same 500 tokens generated either way → same cost either way
```

Streaming is a genuinely valuable user-experience optimization, but it belongs in a different category from the cost-reduction techniques in this chapter — it's solving a perceived-responsiveness problem, not a token-usage problem. Don't confuse "the response feels faster" with "the response was cheaper."

---

# Optimization Strategy 6 — Batch Requests

Instead of processing similar requests individually,

combine them.

```text
10 Requests

↓

Single Batch

↓

LLM

↓

10 Responses
```

Batching reduces repeated overhead.

# Cost vs Quality

Optimization often involves trade-offs.

|Lower Cost|Higher Quality|
|---|---|
|Smaller models|Larger models|
|Shorter prompts|Richer context|
|Fewer tool calls|More comprehensive reasoning|
|Lower latency|Better accuracy|

Production systems balance these factors based on business requirements.

Limiting generated output helps control cost while maintaining acceptable response quality.

# Best Practices

Use the smallest model that meets quality requirements — consider cascading/routing to make this decision dynamically per request.

Keep prompts concise.

Limit unnecessary output.

Cache repeated responses — choose exact-match or semantic caching deliberately, understanding the risk/coverage tradeoff of each.

Use provider-level prompt caching for large, unchanging prompt prefixes (system prompts, reference documents).

Avoid redundant tool calls.

Don't confuse streaming (a latency/UX improvement) with cost reduction — they solve different problems.

Continuously monitor token usage and cost trends.

# Common Beginner Mistakes

### Mistake 1

Using the largest model for every request.

Choose models based on task complexity, or use a cascading/routing approach.

---

### Mistake 2

Sending the entire conversation every time.

Include only relevant context.

---

### Mistake 3

Ignoring token usage.

Tokens directly affect operational cost.

---

### Mistake 4

Optimizing only for cost.

Excessive optimization may reduce response quality.

Balance cost, latency, and accuracy.

---

### Mistake 5

Treating "caching" as one single technique.

Exact-match caching, semantic caching, and provider-level prompt caching solve different problems and have different risk profiles — conflating them leads to picking the wrong tool for the situation.

---

### Mistake 6

Assuming streaming reduces cost.

It improves perceived responsiveness only — the same number of tokens are generated and billed either way.

# Interview Tip

A common interview question is:

> **How can production AI systems reduce LLM costs?**

A good answer is:

Production AI systems reduce costs by selecting appropriate models (or routing/cascading between them dynamically), minimizing prompt size, limiting output tokens, caching repeated responses (exact-match or semantic), using provider-level prompt caching for static prefixes, reducing unnecessary tool calls, batching requests, and continuously monitoring token usage while balancing cost, latency, and response quality.

---

# Interview Tip

A stronger follow-up worth preparing for:

> **What's the difference between semantic caching and prompt caching?**

Answer:

Semantic caching reuses a previously generated _final answer_ when a new query is judged similar enough in meaning (via embeddings) to a past query, even if the wording differs — it's about avoiding repeat generation for equivalent questions. Prompt caching is a provider-level feature that caches the internal processing of a repeated, unchanging _prompt prefix_ (like a long system prompt or reference document), making requests that reuse that same prefix cheaper and faster — it's about avoiding repeated processing of unchanged input, not about matching different questions to the same answer.

# Key Takeaways

- Every LLM call, tool execution, and token contributes to operational cost.
- Token usage is one of the primary cost drivers in AI systems.
- Model routing/cascading is a concrete, dynamic way to implement "use the right model" on a per-request basis.
- Exact-match caching, semantic caching (built on vector similarity), and provider-level prompt caching are three distinct techniques solving different problems.
- Streaming improves perceived latency but does not reduce actual token usage or cost.
- Cost optimization includes model selection, prompt optimization, caching, batching, and reducing unnecessary tool calls.
- Optimization should balance cost, quality, and latency.
- Continuous cost monitoring is essential for production AI systems.
