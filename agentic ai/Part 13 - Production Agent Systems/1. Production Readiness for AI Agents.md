# Introduction

Building an AI Agent is exciting.

Making it work for **thousands of users, 24 hours a day, every day** is a completely different challenge.

A prototype might work perfectly during development,

yet fail within minutes after deployment.

Why?

Because production systems must handle far more than answering user questions.

They must deal with:

- Concurrent users
- Network failures
- API outages
- Security threats
- High operational costs
- Software updates
- Monitoring
- Recovery from failures

Building an intelligent Agent is only the beginning.

Running it reliably is the real challenge.

# Defining SLAs and SLOs for AI Agents

Before you can call a system "reliable," you need to define what reliability actually means in measurable terms.

|Term|Meaning|
|---|---|
|**SLI** (Indicator)|A measured metric, e.g., response latency, error rate|
|**SLO** (Objective)|The internal target for that metric, e.g., "p95 latency under 3s"|
|**SLA** (Agreement)|The external promise to users/customers, often with consequences if missed|

Example for an AI Customer Support Agent:

```text
SLI: 95th percentile response latency
SLO: < 3 seconds, measured over a rolling 7-day window
SLA: 99.5% uptime per month, credits issued if breached
```

Without explicit SLOs, "reliable" is just a feeling — with them, it's something the team can actually measure, alert on, and improve against (tying directly into the latency and cost metrics from Chapters 38–39).

# A Production Readiness Checklist

Before launching an Agent to real users, teams typically walk through a checklist like this:

```text
☐ Error handling covers tool failures, API timeouts, and malformed input
☐ Retries and fallbacks defined for external dependencies
☐ Logging captures enough detail to debug a failed request after the fact
☐ Monitoring dashboards exist for latency, error rate, and cost
☐ Alerting is configured for SLO breaches, not just total outages
☐ Load testing has been run at expected (and 2–3x expected) traffic
☐ Rollback procedure is documented and has been tested
☐ Security review completed for all external integrations
☐ On-call rotation and escalation path defined
```

Treating this as a gate before launch — not an afterthought — is what separates teams that get paged at 3 AM from teams that don't.

# Deployment Strategies That Reduce Launch Risk

Shipping a new version of an Agent directly to 100% of users is risky — a subtle regression (like a worse system prompt) can affect everyone at once. Safer rollout patterns include:

### Canary Deployment

```text
New version → routed to 5% of traffic
↓
Monitor error rate, latency, quality metrics
↓
If healthy → gradually increase to 25%, 50%, 100%
↓
If unhealthy → automatically roll back
```

### Blue-Green Deployment

```text
Blue (current version)  → serving 100% of traffic
Green (new version)     → deployed, fully tested, idle
↓
Switch traffic to Green all at once
↓
Keep Blue running briefly for instant rollback if needed
```

Both patterns connect directly to Chapter 40 (Prompt Versioning) and Chapter 56 (Checkpointing) — a new "version" isn't just code, it can be a new prompt, model, or workflow, and it should be rolled out and monitored the same way.

# Incident Response and On-Call

Even a well-built system will fail sometimes — what matters is how quickly the team detects and responds.

```text
Alert fires (SLO breach)
↓
On-call engineer acknowledges
↓
Triage: Is it the model, a tool, infra, or a bad deploy?
↓
Mitigate (rollback, failover, disable a broken tool)
↓
Post-incident review: what happened, why, how to prevent recurrence
```

A short, honest post-incident review — without blaming individuals — is what turns a failure into a permanent improvement instead of a repeat incident three months later.

---

# Capacity Planning

Production systems need to plan for load, not just react to it.

```text
Current peak traffic: 500 requests/minute
Expected growth: 3x over next 6 months
↓
Ensure infrastructure, rate limits, and provider quotas
scale to 1,500 requests/minute before that growth arrives
```

This includes checking upstream limits too — LLM provider rate limits, third-party API quotas, and database connection limits all need headroom, not just your own application servers.

# Best Practices

Design for failure from the beginning.

Automate testing and deployment.

Monitor every important component.

Secure all external integrations.

Measure both quality and operational performance.

Define explicit SLIs, SLOs, and SLAs instead of relying on a vague sense of "reliable."

Roll out changes gradually (canary/blue-green) instead of shipping directly to all users.

Plan capacity ahead of expected growth, including third-party rate limits.

Plan for growth beyond the initial prototype.

# Common Beginner Mistakes

### Mistake 1

Assuming a working prototype is production-ready.

Production systems require much more than correct functionality.

---

### Mistake 2

Ignoring operational concerns.

Monitoring, logging, and security are essential from day one.

---

### Mistake 3

Optimizing only model quality.

Production systems must also optimize reliability, latency, and cost.

---

### Mistake 4

Treating deployment as the final step.

Deployment is the beginning of operating a production system.

---

### Mistake 5

Shipping every change to 100% of users at once.

Canary or blue-green rollouts catch regressions before they affect everyone.

---

### Mistake 6

Having no defined on-call or incident response process.

Without one, even a well-monitored system will recover slowly when something breaks.
