# What is Agent Versioning?

Agent Versioning is the practice of assigning unique versions to an AI Agent whenever its behavior changes.

Instead of treating the Agent as a single system,

each release becomes an identifiable version.

Example:

```text
v1.0

↓

v1.1

↓

v1.2

↓

v2.0
```

This makes every deployment traceable.

---

# What Do the Numbers Actually Mean? Semantic Versioning

The version numbers shown (v1.0, v1.1, v2.0) aren't arbitrary — they follow a widely-used convention worth knowing explicitly: **Semantic Versioning (semver)**, formatted as `MAJOR.MINOR.PATCH`.

```text
MAJOR (e.g. 1 → 2)
→ A significant, potentially breaking change in behavior
→ e.g. switching to a fundamentally different planning strategy,
  changing the Agent's core capabilities

MINOR (e.g. 1.1 → 1.2)
→ A meaningful new capability or improvement, without breaking
  existing behavior
→ e.g. adding a new tool, improving retrieval quality

PATCH (e.g. 1.1.0 → 1.1.1)
→ A small fix that doesn't change intended behavior, just
  corrects a bug
→ e.g. fixing a prompt typo, correcting a tool's parameter
  validation
```

Knowing this convention lets a team (and anyone debugging an incident) immediately gauge the _scale_ of a change just from the version number, before even reading the release notes — a jump from 1.4 to 2.0 signals "expect meaningfully different behavior," while 1.4.2 to 1.4.3 signals "should be a safe, low-risk fix."

# The AI-Specific Wrinkle: A Version Identifies a Configuration, Not a Guaranteed Output

This is genuinely different from traditional software versioning, and worth understanding clearly, since it's a distinction that separates people who've only versioned deterministic code from people who understand AI system versioning specifically.

```text
Traditional software versioning
→ "Version 2.1.0 of this function" means: given the same input,
  it will ALWAYS produce the same output, every single time
  (deterministic code behaves identically across runs)

AI Agent versioning
→ "Version 2.1.0 of this Agent" means: the same PROMPT, MODEL,
  and CONFIGURATION were used — but recall temperature and
  sampling (from earlier chapters) mean the same input can still
  produce DIFFERENT outputs across runs, even at temperature > 0
  on the identical version
```

So a version number for an AI Agent is best understood as **pinning the configuration** (which prompt, which model, which tools, which parameters) rather than promising identical output every time. This matters practically: if two users on the exact same Agent version get noticeably different responses to similar questions, that alone doesn't necessarily indicate a version mismatch or a bug — it could simply be expected sampling variation. Debugging AI systems requires holding this distinction in mind, where traditional software debugging doesn't have to.

# Running Multiple Versions Simultaneously: Canary and Blue-Green Deployment

The line above — "both versions may coexist during deployment" — is worth unpacking, since it references established deployment patterns from general software engineering that apply directly here.

```text
Canary Deployment
→ The new version is rolled out to a SMALL percentage of traffic
  first (e.g. 5% of users), while most traffic still goes to the
  proven old version
→ If the new version performs well (monitored via the metrics
  from earlier reliability chapters), traffic is gradually shifted
  toward it; if it performs badly, only a small fraction of users
  were ever affected

Blue-Green Deployment
→ Two complete, identical environments exist ("blue" = current
  live version, "green" = new version)
→ Traffic is switched from blue to green all at once, but blue
  remains fully available for an instant rollback if something
  goes wrong
```

Both patterns exist specifically to make "both versions may coexist" a controlled, low-risk state rather than an accident — and both depend entirely on the versioning discipline this chapter describes, since you can't safely route 5% of traffic to "the new version" if you don't have a precise, unambiguous way to identify which requests used which version.

# Deployed Versions Should Be Immutable

Worth stating as an explicit rule, since it's easy to accidentally violate: once a version has been deployed and requests have been logged against it, that version's underlying configuration (prompt, model, tools) should **never be silently edited in place**.

```text
WRONG:
"Version 2.1.0 is live, but let's just tweak the system prompt
slightly without bumping the version number — it's a small change"

RIGHT:
Any change, however small, gets a new version number (even just
a patch bump), so "Version 2.1.0" always means exactly the same
configuration, forever
```

If a version number can silently mean different things at different points in time, the entire point of versioning — being able to say "this exact behavior came from this exact configuration" — breaks down. Past logs referencing "Version 2.1.0" would become unreliable, since you could no longer be sure which actual configuration produced them. Treating each version as immutable once released is what makes historical debugging and auditing trustworthy.

# Best Practices

Assign a version to every production release, following a consistent scheme like semantic versioning.

Record the Agent version in logs and traces.

Keep previous versions available for rollback.

Document changes between versions.

Test each version before deployment.

Treat deployed versions as immutable — any change, however small, gets a new version number.

Use canary or blue-green deployment to limit exposure when rolling out a new version.

Remember a version pins a configuration, not a guaranteed identical output — account for expected sampling variation when debugging.

# Common Beginner Mistakes

### Mistake 1

Updating production Agents without assigning a version.

Every behavioral change should be traceable.

---

### Mistake 2

Overwriting old versions.

Previous releases are valuable for debugging and rollback.

---

### Mistake 3

Changing multiple components without documenting them.

Maintain clear release notes.

---

### Mistake 4

Deploying directly without comparing versions.

Evaluate new versions against previous baselines.

---

### Mistake 5

Silently editing a deployed version's configuration instead of bumping the version number.

This breaks the reliability of historical logs and undermines the entire purpose of versioning.

---

### Mistake 6

Assuming identical output is guaranteed within the same Agent version, and treating any variation as a bug.

Sampling-based variation is expected even within one fixed, unchanged version — this is different from traditional deterministic software versioning.

# Interview Tip

A stronger follow-up worth preparing for:

> **How does versioning an AI Agent differ from versioning traditional deterministic software?**

Answer:

Traditional software versioning implies that a given version will always produce the same output for the same input. AI Agent versioning instead pins a specific configuration — prompt, model, tools, and parameters — but doesn't guarantee identical output across runs, since factors like temperature and sampling can still produce different results even on the exact same version. So an Agent's version number identifies "which configuration generated this," not "this exact same response will always occur," which changes how you interpret variation when debugging.
